0. HOW TO USE THIS PLAYBOOK
====================================================================================================
This file is the operating manual for converting the DMF Pulse specifications into code with
Codex. It does not replace DMFP-00 through DMFP-20. It defines how to package context, select a
Codex model, constrain permissions, issue one ticket, validate the result, obtain an independent
review and retain acceptance evidence.
1. Complete Stage A0 and approve DMFP-20/ADRs.
2. Create the repository guidance and ticket/evidence schemas in Stage A1.
3. For each ticket, generate a context bundle and run the planning prompt.
4. Human reviews the plan and freezes the ticket contract.
5. Run the implementation prompt in an isolated branch/worktree.
6. Run tests and machine acceptance commands.
7. Run an independent Codex review using a fresh session and preferably Sol.
8. Resolve findings, generate the acceptance manifest, obtain human approval, merge and tag.
9. Do not release the next ticket until the current public contract is accepted.

====================================================================================================
1. IMPLEMENTATION AUTHORITY
====================================================================================================
    Highest authority:
      1. Active target-season FPL rules and signed provider contracts/rights profiles
      2. Approved DMFP-20 decisions and ADRs
      3. Approved DMFP module specification sections
      4. Approved stage/ticket contract and public schemas
      5. This Codex playbook and AGENTS.md
      6. Comments/examples/legacy documents
    
    Conflict behavior:
      - STOP; do not guess.
      - Record the conflict in evidence/tickets/<ticket>/BLOCKER.md.
      - Quote both requirements and their hashes/section locators.
      - Propose options, but make no production semantic choice.

====================================================================================================
2. NON-NEGOTIABLE DELIVERY PRINCIPLES
====================================================================================================
1. One bounded ticket, one reviewable outcome. A normal ticket changes one public contract or
   one cohesive capability.
2. Public contract and fixtures first. Implementation begins only after schemas, expected
   behavior and exclusions are frozen.
3. Tests before or alongside code. Critical deterministic behavior requires an
   oracle/golden/property test, not only implementation-shaped unit tests.
4. No future-stage logic. Foundational abstractions are permitted only when the active vertical
   slice needs them.
5. No network in ordinary implementation or test sessions. Live provider access is isolated to
   approved probe/capture tickets.
6. No production secrets in Codex context, repository, prompts, logs, fixtures or CI artifacts.
7. No uncontrolled dependency. Every new package needs purpose, licence, security/maintenance
   check, alternative and lock/SBOM update.
8. No numerical invention. Codex cannot fill missing rules, probabilities, weights, thresholds,
   provider fields or expected outputs.
9. No silent degradation. Missing/stale/blocked data must produce typed status and visible
   confidence/failure.
10. No same-agent self-acceptance. A fresh review plus human sign-off is required.
11. Reproducibility is an output. Every accepted ticket stores commands, versions, hashes,
    fixtures, seeds and results.
12. A plausible-looking output is not success. Public command/API, clean environment and
    accepted fixtures must demonstrate the capability.

3. CODEX MODEL ROUTING
====================================================================================================
Use the current GPT-5.6 Codex family by risk and task shape. Model names are configuration
examples and should be checked against the installed Codex version before automation.
    MODEL / REASONING             USE
    
    gpt-5.6-sol / high or xhigh   Architecture reconciliation, difficult domain contracts,
                                  numerical methods, optimiser formulations, security,
                                  migration design, incident analysis, final review.
    
    gpt-5.6-terra / medium-high   Default implementation model for normal tickets, adapters,
                                  services, tests, refactors and documentation.
    
    gpt-5.6-luna / low-medium     Clear repeatable work: fixture conversion, schema snapshots,
                                  mechanical tests, formatting, inventories, boilerplate and
                                  structured extraction. Never sole authority for critical math.
    
    gpt-5.3-codex-spark           Optional interactive micro-edits/research preview only.
                                  Do not use as sole implementation/reviewer for numerical core.

3.1 ROLE ASSIGNMENT
----------------------------------------------------------------------------------------------------
    Planner / architect         Sol, high or xhigh, read-only
    Implementer - normal        Terra, medium or high, workspace-write
    Implementer - critical      Sol, high/xhigh, workspace-write
    Fixture/test worker         Luna or Terra, low/medium, bounded files
    Reviewer                    Sol, high, read-only, fresh session
    Security reviewer           Sol, xhigh, read-only
    Release/evidence generator  Terra or Luna, medium, structured output schema

3.2 SUBAGENTS
----------------------------------------------------------------------------------------------------
- Use subagents for read-heavy parallel analysis: specification conflict review, security
  review, test-gap review, performance review or document extraction.
- Do not allow multiple agents to edit the same files concurrently.
- A lead agent must define partitions, wait for all agents and consolidate findings with
  file/line references.
- Use Ultra only when the task has genuinely separable workstreams; it consumes more
  context/tokens and is not the default.

====================================================================================================

4.2 TASK-SPECIFIC LAUNCH POLICY
----------------------------------------------------------------------------------------------------
    Architecture/review:
      model=Sol; reasoning=high/xhigh; sandbox=read-only; network=disabled
    
    Normal implementation:
      model=Terra; reasoning=medium/high; sandbox=workspace-write; network=disabled
    
    Critical algorithm/security:
      model=Sol; reasoning=high/xhigh; sandbox=workspace-write; network=disabled
    
    Provider live probe:
      isolated worktree/container; minimum credential; network only to approved host;
      read-only account; no production database; capture sanitised fixture; human approval
    
    CI review:
      read-only checkout; Codex output as patch/report artifact; no repository write token in
      the same job that holds an OpenAI/Codex credential

4.3 SECRET RULES
----------------------------------------------------------------------------------------------------
- Never include API keys, cookies, FPL login material, database passwords or auth.json in
  prompts or mounted ticket bundles.
- Use fake credentials in fixtures and golden leak-detection strings in tests.
- Provider probe credentials are injected at process invocation or through the host credential
  mechanism and removed before sanitised payload review.
- Codex may create credential interfaces and tests but must not read or echo real credential
  values.
- Any observed secret causes immediate stop, rotation and incident evidence.

6. INPUT FILE ARCHITECTURE
====================================================================================================
Codex should not receive all specifications as one prompt. Every ticket receives a generated
Context Bundle. The bundle is immutable and hash-addressed.

6.1 CONTEXT BUNDLE CONTENTS
----------------------------------------------------------------------------------------------------
    context_bundle/<ticket_id>/
      ticket.yaml
      authority.json
      decisions.json
      specification_excerpts.txt
      public_contracts/
      fixtures/manifest.json
      fixtures/<approved files>
      expected_outputs/
      current_tree.txt
      relevant_existing_files.txt
      dependency_manifest.txt
      acceptance_commands.txt
      exclusions.txt
      bundle.sha256

6.2 INPUT SELECTION RULES
----------------------------------------------------------------------------------------------------
1. Include only approved controlling sections plus directly relevant invariants and definitions.
2. Include full public schemas and fixture expected outputs; never summarise away contract
   details.
3. Include one previous accepted stage contract when compatibility matters.
4. Include current implementation files likely to change and interfaces they call.
5. Include relevant ADRs/DMFP-20 decisions in full.
6. Do not include large bibliographies unless the ticket is a research/evidence ticket.
7. Do not include secrets, licensed raw bodies without permission, private manager identifiers
   or irrelevant legacy documents.
8. Record every included file hash and the generator version.

8. ROOT AGENTS.md TEMPLATE
====================================================================================================
    # DMF Pulse agent instructions
    
    ## Mission
    Implement only the active approved ticket. Preserve temporal integrity, rules-as-data,
    canonical identity, joint-scenario semantics, rights controls and reproducibility.
    
    ## Authority
    1. `specs/manifests/authority_manifest.json`
    2. approved DMFP-20 decisions and ADRs
    3. the active ticket and public schemas
    4. approved DMFP excerpts
    5. this file
    Stop on conflict. Do not invent a resolution.
    
    ## Repository layout
    - production package: `src/dmf_pulse/`
    - migrations: `alembic/`
    - configuration: `config/`
    - fixtures: `fixtures/`
    - tests: `tests/`
    - ticket evidence: `evidence/tickets/<ticket_id>/`
    - approved specifications: `specs/approved/`
    
    ## Commands
    - bootstrap: `make bootstrap`
    - format: `make format`
    - lint: `make lint`
    - type: `make type`
    - fast tests: `make test-fast`
    - ticket tests: `make test-ticket TICKET=<id>`
    - integration: `make test-integration`
    - package: `make build`
    - acceptance: command listed in active ticket
    
    ## Engineering constraints
    - Python package is `dmf_pulse`; use `src/` layout.
    - Strict typing in production code; use canonical domain types.
    - UTC internally; no naive datetime.
    - Money/odds exact at boundaries; no binary float for affordability or raw odds.
    - No global RNG or clock; inject seed/RNG/Clock.
    - Unit tests perform no network or production database access.
    - PostgreSQL semantics are tested on PostgreSQL, never substituted by SQLite.
    - External IDs are provider-scoped mappings, never canonical primary keys.
    - Raw observations are immutable; corrections append/supersede.
    - No LLM-generated numerical truth.
    - No new dependency or migration unless ticket permits it.
    - No unrelated refactor.
    - No broad TODO/pass/NotImplementedError in accepted scope.
    
    ## Security and rights
    - Never read or print secrets.
    - Network disabled unless active ticket explicitly authorises a host and credential.
    - Respect the fixture rights manifest and provider Rights Profile.
    - Redact credentials, query keys, cookies and personal manager data from logs/artifacts.
    
    ## Work method
    1. Read ticket, authority, decisions, contracts and fixtures.
    2. Inspect relevant current code.
    3. Write/update execution plan for nontrivial work.
    4. Write failing tests or contract fixtures first.
    5. Implement smallest complete vertical slice.
    6. Run targeted tests, then required acceptance commands.
    7. Review diff for scope, invariants, time cutoff, security and rights.
    8. Write structured evidence and final response.
    
    ## Done means
    - public contract implemented exactly;
    - required tests/commands pass;
    - output is deterministic under stored seed;
    - no excluded feature is present;
    - evidence files exist and hashes validate;
    - independent review has no unresolved P0/P1 finding.
    
    ## Stop conditions
    Stop and report a blocker when requirements conflict, expected output is absent, a fixture
    is unlicensed, a required decision is unapproved, a public interface must change, a new
    dependency/migration is needed but forbidden, or a safe deterministic result is impossible.

    # Execution plan format
    
    ## Ticket
    ID, title, stage, branch, owner, reviewer.
    
    ## Goal
    One observable capability; state the public command/API and expected output.
    
    ## Authority and decisions
    Exact spec files/section locators/hashes and DMFP-20/ADR IDs.
    
    ## Current state
    Relevant files, existing interfaces, known limitations, failing tests.
    
    ## Constraints and exclusions
    Allowed files, dependency/migration/network rules, explicit non-goals.
    
    ## Invariants
    Temporal, mathematical, legal, security and rights invariants.
    
    ## Implementation steps
    Small ordered checkpoints, each leaving the repository testable.
    
    ## Tests first
    Unit/property/contract/integration/golden/performance/security tests and fixtures.
    
    ## Acceptance commands
    Exact commands and required results.
    
    ## Risks and fallback
    Ambiguities, numerical/runtime risk, rollback and safe degradation.
    
    ## Evidence
    Paths that will be written and fields required.
    
    ## Progress
    Timestamped checkboxes; update after every meaningful checkpoint.
    
    ## Decision log
    Any approved deviation; do not silently change the plan.

14. BRANCH, WORKTREE AND REVIEW WORKFLOW
====================================================================================================
    1. Create branch/worktree:
       stage/<stage>/<ticket>-<slug>
    
    2. Generate and commit the ticket Context Bundle before implementation.
    
    3. Run planner in read-only mode; save plan to:
       evidence/tickets/<ticket>/PLAN.md
    
    4. Human approves plan or edits ticket. Freeze ticket hash.
    
    5. Run implementer with workspace-write and no network.
    
    6. Run acceptance commands locally from a clean environment.
    
    7. Run fresh independent review:
       codex review --base <accepted-stage-tag>
       or review the exact commit with custom DMF checklist.
    
    8. Fix P0/P1 findings; reviewer re-runs targeted review.
    
    9. Generate acceptance manifest and human-readable report.
    
    10. Human signs; merge; tag ticket/stage; archive bundle and logs.

14.1 COMMIT POLICY
----------------------------------------------------------------------------------------------------
- Prefer one or a few coherent commits: contract/tests, implementation, evidence/docs.
- Do not mix formatting of unrelated files.
- Migration and its model/repository/tests belong to the same ticket, but large data backfills
  are separate.
- Generated lock/SBOM/schema snapshots are reviewed like source changes.
- Commit message includes ticket ID and observable capability.

    - python -m build

    PERMISSIONS

38. TEST STRATEGY
====================================================================================================

38.1 TEST PYRAMID BY RISK
----------------------------------------------------------------------------------------------------
    Pure deterministic rules/math:
      exhaustive/golden + property + mutation + differential/oracle
    
    Domain/application services:
      unit + property + contract + integration
    
    PostgreSQL/temporal/migrations:
      real PostgreSQL integration + concurrency + replay/as-of
    
    Provider adapters:
      recorded contract fixtures + schema drift + rights/quota; live smoke separate
    
    Predictive models:
      leakage/unit + deterministic training smoke + rolling evaluation + calibration
    
    Optimisers:
      constraint unit + exhaustive toy oracle + scenario integration + performance
    
    API/UI:
      schema/OpenAPI + golden view + accessibility/security/e2e
    
    Operations/security:
      fault injection + restore/replay + secret redaction + publication block drills

38.2 COVERAGE/MUTATION
----------------------------------------------------------------------------------------------------
    Critical deterministic/security/cutoff logic: target >=95% branch and meaningful mutation score.
    Core domain/application: target 85-90% branch by maturity.
    Provider/UI: target 75-85% branch plus strong contract/golden/accessibility tests.
    No broad pragma exclusions. Every surviving critical mutant is killed, proven equivalent or
    explicitly approved with rationale.

38.3 PROPERTY INVARIANTS
----------------------------------------------------------------------------------------------------
- Probabilities finite and within [0,1]; proper vectors sum within tolerance.
- Prices/bank/selling values are integer tenths and legal.
- Time intervals do not overlap where prohibited; as-of query is stable.
- Repeated ingestion has one canonical effect but preserves retrieval events.
- Score/player event conservation holds in every scenario.
- FPL component sum equals exact integer total.
- Every optimiser output passes independent legality validation.
- Same inputs/config/seed produce the same canonical outputs/hashes, subject to documented
  solver nondeterminism.
- Changing a post-cutoff input cannot alter a historical pre-cutoff prediction.

42. CONTEXT AND TOKEN MANAGEMENT
====================================================================================================
1. Keep root AGENTS.md concise; place specialised rules in local files.
2. Generate section excerpts with exact source locators and hashes; never copy whole specs by
   default.
3. Use one task session per ticket. Resume only for the same ticket; start a fresh session for
   review.
4. After planning, freeze a compact implementation context containing the plan, contracts and
   fixtures rather than the entire research history.
5. Use structured outputs for result/review/evidence so summaries do not lose required fields.
6. Ask subagents to return concise findings with paths/lines, not full duplicated document
   summaries.
7. Archive completed ticket context and do not let later tickets rely on hidden chat history.
8. When a repeated mistake occurs, add a narrow AGENTS.md rule or test rather than a longer
   prompt.

43. FAILURE AND STOP CONDITIONS
====================================================================================================
    Codex MUST stop and mark BLOCKED when:
    - approved requirements conflict;
    - target rule/field/expected output is unknown;
    - required fixture, mapping, rights profile or decision is missing;
    - a public interface must change outside the ticket;
    - a forbidden migration/dependency/network call is required;
    - a secret or unlicensed raw body appears;
    - deterministic acceptance cannot be reproduced;
    - solver/model result is invalid or only plausible-looking;
    - data cutoff cannot be proven;
    - safe fallback/degradation behavior is unspecified;
    - required acceptance command cannot run in the provided environment.
    
    Codex SHOULD continue with a documented partial result only when the ticket contract explicitly
    allows a nonaccepted research spike. It must never label that COMPLETE.
