# PRIVATE-V1-ONE-COMMAND-001M engineering acceptance

For each transfer count present in the already governed root action family, the implementation
selects the highest current-Gameweek Stage-10 expected points after the existing compiled hit,
using the existing canonical policy tie key. It does not regenerate actions, call Stage 10 again,
or alter canonical recommendation selection.

Each typed frontier point contains transfers, squad, tactics, formation, paired comparison versus
hold, hit, bank, explicit compiled FT transition state, and action/tactical/Stage-11 lineage. The
frontier binds exact action-space, Stage-9 projection/scenario, Stage-11 request/result and
candidate-policy hashes. The containing successful result and private decision hashes bind the
new frontier; legacy artifacts without the additive field retain their former hash convention.

Adjacent exact-count values are labelled frontier deltas. A strict set extension may name its
incremental move; otherwise the renderer must prominently state that plans are non-nested and
must not attribute the delta to a specific transfer.

Every comparison uses the same Stage-9 joint scenario identities and weights as hold and derives
exact weighted p10, median, p90 and probability statistics scenario by scenario. The renderer
performs formatting only and must prominently disclose that future FT value is absent and the
objective remains `ONE_GAMEWEEK_ZERO_TERMINAL_VALUE_OBJECTIVE`.

Acceptance requires focused RED-to-green tests for exact buckets, gaps, ties, order invariance,
negative uplift, hits, bank, FT=2 use 0/1/2, paired statistics, non-nested wording, hostile input,
hash/roundtrip, legacy parsing, recommendation equality, and zero repeated Stage-10 evaluations.
Run affected unit/property/contract/golden/integration tests, branch coverage, Ruff, strict mypy,
frozen sync, build, installed-wheel/CLI checks, repository and evidence validation, secret scan,
then require the pushed final exact SHA to pass the repository CI.
