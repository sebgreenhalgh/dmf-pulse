## 5.2 One-time setup command

Implement a user-friendly CLI such as:

`dmf credentials set-odds-key`

The command must:

1. Prompt securely without displaying the key.
2. Validate the supplied secret locally without contacting the provider.
3. Store it in Windows Credential Manager.
4. Report success without revealing the secret.
5. Never retain it in repo-owned files or command evidence.

Also provide commands such as:

`dmf credentials status`

`dmf credentials delete-odds-key`

A status check must disclose only whether a credential is configured.

Support secure rotation/replacement with explicit operator action.

Do not implement a `show-key` command.

## 5.3 Automatic retrieval

After the one-time setup:

**Neither `dmf pulse` nor an eligible Seb's Desk Refresh may require the owner to type the Odds API key again.**

Integrate retrieval into the actual accepted Odds acquisition path.

Current legacy environment variable:

`THE_ODDS_API_KEY`

Preserve backward compatibility where appropriate, but make the protected OS credential store the normal Windows path.

Document exact precedence if both an environment variable and an OS-vault entry exist.

Do not silently choose an unexpected credential.

The actual key must be resolved only when an authorized operation requires it.

In particular:

- no credential lookup during module imports;
- no credential lookup merely to open the dashboard;
- no credential lookup for demo runs;
- no credential lookup before source authorization;
- no credential lookup before the appropriate usage reservation, where required;
- no credential serialized into worker grants, IPC payloads or browser responses.

Prefer resolving the credential within the authorized worker or accepted transport boundary.

Do not use an unnecessary broad process-environment mutation that exposes the key to unrelated subprocesses.

Clear temporary references where practical.

Do not claim guaranteed memory erasure in Python.

## 5.4 FPL token handling

and current secure FPL credential-provider integration.

- explicit expiration;

- explicit secure replacement;

- no fabricated refresh token or unsupported renewal mechanism.

If automatic renewal is unavailable or unauthorized, the application must request a new token through an existing approved secure interaction only when necessary.

Do not make repeated Odds API key entry a dependency of an expiring FPL token.

## 5.5 Portability
