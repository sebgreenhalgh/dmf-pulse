PURPOSE
-------
This document defines the cross-cutting controls that make DMF Pulse observable,
reproducible, secure, recoverable and lawful enough for private production use.

It covers:

- structured logs;
- distributed trace correlation;
- metrics and pipeline-health monitoring;
- data-freshness alerts;
- model and calibration drift;
- secrets management;
- API-key handling;
- identity and access;
- host, network and database protection;
- backups and disaster recovery;
- model registry;
- dataset versioning;
- dependency locking;
- software-supply-chain evidence;
- deterministic simulations;
- test coverage and quality gates;
- provider licensing;
- terms-of-service compliance;
- data classification;
- personal-data minimisation;
- data-retention and deletion rules;
- incident response;
- vulnerability management;
- control evidence and assurance reporting.

The assurance question is:

    CAN PULSE PROVE WHAT RAN, WHAT IT KNEW, WHY IT DECIDED,
    WHETHER THE RESULT WAS HEALTHY, WHO COULD ACCESS IT,
    AND WHETHER EVERY INPUT AND OUTPUT WAS USED WITHIN ITS RIGHTS?

If the system cannot answer that question from immutable evidence, the affected
decision is not production trustworthy.

GOVERNING PRINCIPLE
-------------------
Pulse treats assurance as an engineered system, not a checklist.

Every material control must have:

- a control ID;
- an objective;
- a system owner;
- a technical implementation;
- a monitoring signal;
- a test;
- a failure response;
- retained evidence;
- a review frequency;
- a status.

The system will follow these operating principles:

1. TELEMETRY IS STRUCTURED AND CORRELATED.
2. DEADLINE READINESS IS A USER-FACING RELIABILITY OBJECTIVE.
3. SECURITY USES LEAST PRIVILEGE AND SHORT-LIVED EXPOSURE.
4. SECRETS NEVER BECOME CONFIGURATION, LOGS OR DATASETS.
5. MODELS, DATASETS, CODE AND DEPENDENCIES ARE IMMUTABLE VERSIONS.
6. SIMULATION RANDOMNESS IS EXPLICIT, HIERARCHICAL AND REPLAYABLE.
7. BACKUPS ARE ACCEPTED ONLY AFTER VERIFIED RESTORE.
8. PROVIDER RIGHTS ARE MACHINE-ENFORCED METADATA.
9. UNKNOWN LICENSING MEANS NO PERSISTENT OR PUBLIC USE.
10. PERSONAL DATA ARE MINIMISED, PSEUDONYMISED AND RETAINED ONLY FOR A
    JUSTIFIED PURPOSE.
11. A DRIFT ALERT DOES NOT AUTOMATICALLY RETRAIN OR PROMOTE A MODEL.
12. A HIGH TEST-COVERAGE NUMBER DOES NOT REPLACE CORRECTNESS TESTS.
13. A RELEASE WITHOUT DEPENDENCY, BUILD AND model/data provenance is not a
    production release.
14. AN INCIDENT MUST LEAVE A COMPLETE TIMELINE AND CORRECTIVE ACTION RECORD.

IMPORTANT LEGAL POSITION
------------------------
This document is an engineering and governance baseline, not legal advice.

Provider rights, privacy law, betting-data restrictions and public/commercial
use can depend on:

- jurisdiction;
- account;
- plan;
- access method;
- intended use;
- storage duration;
- redistribution;
- third-party rights.

Ambiguity is escalated for written provider or legal review.

The initial scope is:

    PRIVATE, INTERNAL, NON-BETTING FPL DECISION SUPPORT.

Public display, commercialisation, redistribution and multi-user service are
new purposes and require a new rights and privacy assessment.

======================================================================
0. EXECUTIVE CONTROL DECISIONS
======================================================================

0.1 OBSERVABILITY STACK
-----------------------
Selected zero-licence-cost baseline:

- JSON structured application logs;
- OpenTelemetry trace and log correlation;
- OpenTelemetry semantic conventions where stable/applicable;
- Prometheus-format metrics;
- systemd journal as local log transport;
- PostgreSQL audit/control records;
- optional OpenTelemetry Collector for routing/export;
- a local dashboard and alert process;
- no requirement for a paid observability service.

0.2 LOGGING DECISION
--------------------
Every first-party log is a structured event.

Required event fields include:

- event timestamp;
- observed timestamp where different;
- severity number/text;
- event name;
- message/body;
- service/module/version;
- environment/host/process;
- trace ID and span ID;
- run/task/operation ID;
- manager/Gameweek scope where permitted;
- information cutoff/deadline;
- outcome/status;
- error code;
- safe attributes.

Free-form strings may supplement the event.
They cannot replace machine-readable fields.

0.3 METRIC CARDINALITY DECISION
-------------------------------
Prometheus labels are limited to bounded dimensions such as:

- environment;
- service;
- queue;
- task type;
- run type;
- status;
- provider;
- severity.

Do not put:

- player ID;
- fixture ID;
- manager ID;
- run ID;
- task ID;
- email;
- URL;
- exception text;

into metric labels.

High-cardinality detail belongs in logs, traces and queryable tables.

0.4 DEADLINE RELIABILITY DECISION
---------------------------------
The primary operational service-level objective is not generic uptime.

It is:

    PRODUCE A LEGAL, FRESH, EXPLAINED AND PUBLISHABLE DECISION
    BEFORE THE EXECUTION SAFETY BUFFER.

Deadline readiness, freshness and decision legality are first-class metrics and
alerts.

0.5 SECRETS DECISION
--------------------
Initial Linux-host implementation:

- encrypted systemd service credentials via `systemd-creds` and
  `LoadCredentialEncrypted=` where the host supports them;
- service reads secret values from its credential directory;
- secrets are not placed in environment variables, command lines, Git,
  `.env` production files, database rows, model artifacts or logs;
- each service/environment/provider uses a separate credential;
- an offline recovery copy is encrypted to an `age` recipient and stored
  separately from the host;
- a documented root/recovery process exists.

Fallback where encrypted systemd credentials are unavailable:

- root-owned encrypted-at-rest secret file;
- decrypted only into a protected runtime credential file/tmpfs;
- `LoadCredential=`;
- immediate migration plan.

0.6 MODEL REGISTRY DECISION
---------------------------
PostgreSQL plus immutable artifacts is the authoritative model registry.

It supports:

- immutable model versions;
- aliases such as `champion` and `challenger`;
- tags;
- approval and withdrawal;
- complete training-data/code/environment lineage.

MLflow Model Registry MAY be added as an operator UI or compatibility layer.
It cannot become a second source of truth.

0.7 DATASET VERSIONING DECISION
-------------------------------
Every training, validation, test and production dataset is an immutable,
hash-addressed manifest over immutable Parquet/source artifacts.

No model may reference:

- `latest.parquet`;
- an unversioned database query;
- a mutable folder;
- a floating source alias.

0.8 DEPENDENCY DECISION
-----------------------
Python releases use:

- `pyproject.toml`;
- a standards-compatible `pylock.toml` when supported by the selected toolchain;
- exact artifact hashes;
- an archived wheelhouse/build manifest;
- an exact Python runtime version;
- operating-system/image identity;
- an SBOM;
- vulnerability and licence scans.

Production installation does not resolve new packages from the Internet.

0.9 SOFTWARE-SUPPLY-CHAIN DECISION
----------------------------------
Minimum production target:

- source in version control;
- protected production branch/tag;
- reproducible, documented build;
- build provenance equivalent to SLSA Build L1;
- SBOM;
- artifact hash verification.

Target when a suitable hosted build platform is used:

- signed, automatically generated provenance equivalent to SLSA Build L2.

Pulse does not claim a SLSA level until every formal requirement is verified.

0.10 DETERMINISTIC SIMULATION DECISION
--------------------------------------
Every stochastic run has one stored root seed.

NumPy `SeedSequence` creates named child streams for:

- model;
- fixture;
- Gameweek;
- structural world;
- parameter draw;
- simulation batch;
- worker;
- module.

No module uses the global NumPy random state.

0.11 BACKUP DECISION
--------------------
Production backup layers:

- continuous PostgreSQL WAL archiving;
- verified PostgreSQL base backups;
- nightly logical custom-format dumps;
- immutable artifact replication;
- encrypted off-host/offline copy;
- independent backup catalogue and hashes;
- monthly restore rehearsal;
- full preseason disaster-recovery rehearsal.

A backup that has not been restored is not accepted as evidence of recoverability.

0.12 PROVIDER-COMPLIANCE DECISION
---------------------------------
Every provider has a versioned Rights Profile controlling:

- automated access;
- quotas;
- caching;
- raw storage;
- derived storage;
- model training;
- internal use;
- public display;
- redistribution;
- backup;
- retention;
- termination deletion;
- attribution;
- geography.

The policy is enforced at ingestion, artifact creation, backup and export.

0.13 DATA-RETENTION DECISION
----------------------------
Retention is classification- and provider-specific.

Unknown right or retention period:

- no long-term raw storage;
- processing/quarantine only for the approved short window;
- no training or redistribution until review.

0.14 PERSONAL-DATA DECISION
---------------------------
Manager and rival data are minimised and pseudonymised.

The operational model uses internal manager UUIDs.
Names and external IDs are held in a separate restricted mapping.

No public leaderboard/rival dataset is created.

0.15 AUTOMATION DECISION
------------------------
No control silently auto-promotes a model, changes a provider right, extends
retention, rotates to an untested key or executes an FPL action.

Critical transitions require approval and evidence.

3.7 SEVERITY
------------
TRACE:
Local deep diagnostic; disabled in production by default.

DEBUG:
Detailed nonsecret diagnostic.

INFO:
Normal lifecycle event.

WARN:
Unexpected/degraded but recoverable.

ERROR:
Task/request failed or control violated.

FATAL:
Process/system cannot safely continue.

Alert severity is separate from log severity.

3.8 MESSAGE/BODY
----------------
Concise human-readable description.

Do not encode critical fields only in the message.

3.9 EXCEPTIONS
--------------
Capture:

- exception class;
- safe message;
- stack trace;
- code location;
- causal chain.

Before capture:

- redact URL query;
- redact request headers;
- redact SQL parameters where sensitive;
- truncate provider bodies;
- remove personal data not needed.

3.10 LOGGING FAILURES
---------------------
Application must not crash solely because a nonaudit log sink is unavailable.

Critical audit events use a durable database/outbox path.

3.11 LOG SAMPLING
-----------------
Never sample:

- ERROR/FATAL;
- security events;
- publication;
- overrides;
- model promotion;
- terms changes;
- backups/restores;
- deadline P0/P1 events.

High-volume successful source/request logs may be sampled after aggregate metrics
exist.

======================================================================
4. LOG REDACTION AND SECRET DETECTION
======================================================================

4.1 ALLOWLIST PRINCIPLE
-----------------------
Prefer explicitly safe logged fields over broad object serialization.

4.2 PROHIBITED VALUES
---------------------
- API keys;
- database passwords;
- cookies;
- bearer tokens;
- session IDs;
- private encryption/signing keys;
- full provider URLs containing key query parameters;
- secret environment/credential contents;
- unredacted private manager/rival payloads.

4.3 KEY-NAME REDACTION
----------------------
Automatically redact fields matching case-insensitive patterns:

api_key
apikey
token
secret
password
passwd
authorization
cookie
session
credential
private_key
client_secret.

4.4 VALUE DETECTION
-------------------
CI and runtime scanning for:

- known provider-key patterns;
- entropy/high-risk tokens;
- PEM/private-key markers;
- accidental `.env` content.

4.5 URL HANDLING
----------------
Store:

- scheme/host/path template;
- safe parameter names;
- request fingerprint.

Never log a provider key in query parameters.

The Odds API requires an `apiKey` query parameter, so its HTTP-client logging
adapter MUST strip query values before tracing/logging.

4.6 HTTP HEADERS
----------------
Only safe allowlisted response headers:

- status;
- content type;
- ETag;
- Last-Modified;
- quota fields;
- request IDs.

4.7 REDACTION TEST
------------------
Golden fake secrets injected into:

- exceptions;
- HTTP requests;
- Pydantic objects;
- trace attributes;
- CLI;
- SQL errors.

No sink may contain them.

4.8 SECRET-LEAK INCIDENT
------------------------
Any confirmed secret in a log:

- P0 security incident;
- revoke/rotate;
- isolate affected logs;
- identify access;
- purge where lawful/possible;
- preserve minimum incident evidence;
- add regression test.

5. AUDIT AND TAMPER-EVIDENT RECORDS
======================================================================

5.1 AUDIT EVENTS
----------------
- authentication/authorization;
- override creation/approval/revocation;
- model approval/promotion/withdrawal;
- dataset release;
- ruleset activation;
- terms/licence approval;
- retention deletion;
- secret rotation;
- decision publication/withdrawal;
- execution record;
- backup restore;
- administrator actions.

5.2 SEPARATE STORE
------------------
Audit events are append-only PostgreSQL rows with restricted writer function.

Application roles cannot update/delete audit rows.

5.3 HASH CHAIN
--------------
For each audit stream/day:

    event_hash =
      sha256(
        previous_hash
        + canonical_event_json
      )

Store:

- sequence;
- previous hash;
- event hash.

5.4 EXTERNAL ANCHOR
-------------------
Daily audit manifest/root hash copied to the separate backup destination.

This makes privileged retrospective tampering detectable unless both systems are
compromised.

5.5 LIMITATION
--------------
A hash chain is tamper-evident, not tamper-proof.

5.6 AUDIT ACCESS
----------------
Read limited to Sebastian/admin/auditor role.

5.7 AUDIT RETENTION
-------------------
Proposed minimum:

- two years for production security/control audit;
- longer where needed to reproduce a retained decision;
- personal fields minimised/pseudonymised.

Provider/right constraints can require shorter raw payload retention; audit
metadata may remain if permitted.

8. SERVICE-LEVEL OBJECTIVES AND ALERT SEVERITY
======================================================================

8.1 SEVERITY
------------
P0 — DECISION/SECURITY EMERGENCY

Examples:

- illegal or corrupted published decision;
- active secret leak;
- manager state compromised;
- rule/deadline integrity failure;
- final recommendation cannot complete before safety cutoff;
- database/artifact loss without verified recovery;
- unauthorised personal-data access.

P1 — MAJOR

- primary source stale near deadline;
- critical worker/queue failure;
- model output invalid;
- optimiser no feasible legal plan;
- backup/PITR unhealthy;
- terms change blocks source;
- severe model drift.

P2 — DEGRADED

- optional provider unavailable;
- reduced market coverage;
- moderate data/model drift;
- challenger failure;
- retention/access review overdue.

P3 — INFORMATIONAL

- routine schema additive change;
- approaching capacity;
- upcoming rotation/review;
- nonmaterial performance change.

8.2 ALERT PAYLOAD
-----------------
- alert ID;
- severity;
- opened/updated time;
- affected environment/run/source/model;
- user/decision impact;
- evidence/query link;
- current fallback;
- owner;
- runbook;
- acknowledgement;
- expiry/escalation;
- deduplication key.

8.3 DEDUPLICATION
-----------------
One incident per root condition.

Repeated observations update it.

8.4 INHIBITION
--------------
A database-down P0 inhibits hundreds of downstream task-failure alerts.

8.5 DEADLINE ESCALATION
-----------------------

8.6 ALERT DELIVERY
------------------
MVP:

- dashboard;

- email;
- local audible/desktop notification for P0/P1 if configured.

8.7 ACKNOWLEDGEMENT
-------------------

8.8 SLO REPORT
--------------

======================================================================
9. DATA-FRESHNESS POLICIES
======================================================================

9.1 FRESHNESS DEFINITION
------------------------
Use source update time when reliable, otherwise receipt time with lower
confidence.

Expose both:

- source_age;
- system_usable_age.

9.2 PHASES
----------
NORMAL:
more than 72h to deadline.

PREDEADLINE:
72h–6h.

CRITICAL:
6h–60m.

FINAL:
inside 60m.

9.3 PROPOSED THRESHOLDS
-----------------------
Thresholds are configuration and must be tuned to observed provider behaviour.

OFFICIAL FPL PLAYER/PRICE/OWNERSHIP:
- NORMAL warning 8h, hard 24h;
- PREDEADLINE warning 2h, hard 6h;
- CRITICAL warning 30m, hard 90m;
- FINAL warning 10m, hard 30m.

OFFICIAL DEADLINE/GAMEWEEK:
- exact current official value required;
- any unresolved conflict is P0;
- refresh at every deadline run.

MANAGER STATE:
- NORMAL warning 6h;
- PREDEADLINE warning 60m;
- CRITICAL warning 15m;
- FINAL warning 5m;
- prepublication hash mismatch blocks.

FIXTURES/GAMEWEEK ASSIGNMENTS:
- NORMAL warning 12h;
- PREDEADLINE warning 2h;
- CRITICAL warning 30m;
- material event triggers immediate refresh.

INJURY/AVAILABILITY SOURCES:
- NORMAL warning 12h;
- PREDEADLINE warning 3h;
- CRITICAL warning 45m;
- FINAL warning 15m;
- lower-quality source age never overrides official newer evidence.

TEAM ODDS:
- DMFP-06 market-specific half-life/hard cutoff;
- final current quote target 10–30m depending source cadence;
- delayed exchange carries explicit delay.

PLAYER PROPS:
- absence is a typed coverage state;
- stale thresholds by provider/market;
- no prop never treated as zero.

PRICE/TRANSFER FLOWS:
- daytime warning 90m;
- broad overnight window warning 20m;
- narrow learned update window warning 10m/target 5m;
- current official price required before transfer legality.

RANK/EO SAMPLE:
- early diagnostic warning 24h;
- near-deadline target 60m if available;
- rank-aware override blocked when cohort state is too stale.

9.4 SOURCE SILENCE
------------------
No update can mean:

- source stable;
- source failed;
- market closed;
- no new data.

Heartbeat/status checks distinguish them.

9.5 FRESHNESS BUDGET
--------------------
Decision Bundle lists:

- oldest critical input;
- weighted/maximum ages;
- expired optional inputs;
- freshness grade.

9.6 ACTION RESTRICTION
----------------------
Examples:

- stale price flow disables ACT NOW;
- stale manager state blocks transfer plan;
- stale player props degrade player allocation;
- stale rank cohort falls back to points mode.

======================================================================
11. MODEL-DRIFT FRAMEWORK
======================================================================

11.1 DRIFT TYPES
----------------
INPUT/DATA DRIFT:
Feature distribution changes.

MISSINGNESS DRIFT:
Source coverage/null reasons change.

PRIOR/LABEL SHIFT:
Outcome prevalence changes.

CONCEPT DRIFT:
Relationship between input and outcome changes.

CALIBRATION DRIFT:
Forecast probabilities cease to match outcomes.

RESIDUAL DRIFT:
Errors change by mean, variance, tails or subgroup.

PREDICTION DRIFT:
Model output distribution changes before labels arrive.

REGIME DRIFT:
Manager, rules, season or source structure changes.

MODEL-COMPOSITION DRIFT:
Ensemble weights/source coverage change.

OPERATIONAL DRIFT:
Latency, failures or fallback usage change.

11.2 TWO-STAGE MONITORING
-------------------------
PRE-LABEL:
available immediately.

- feature/missingness;
- source coverage;
- prediction distribution;
- confidence;
- model disagreement;
- out-of-distribution score.

POST-LABEL:
after outcome finality.

- log/Brier/RPS/CRPS;
- calibration;
- bias;
- interval coverage;
- decision utility/regret.

11.3 REFERENCE WINDOWS
----------------------
Compare against:

- training distribution;
- recent rolling window;
- same season stage;
- same manager/source regime;
- prior season;
- model's expected predictive distribution.

11.4 NUMERICAL DRIFT TESTS
--------------------------
Candidate measures:

- standardised mean/quantile shift;
- Wasserstein distance;
- Kolmogorov–Smirnov diagnostic;
- Jensen–Shannon divergence;
- population stability index as supplementary;
- unseen-category rate;
- missingness difference;
- posterior predictive checks.

No single threshold is universal.

11.5 PROPOSED INITIAL SIGNALS
-----------------------------
P2 investigation candidates:

- important feature missingness +5 percentage points;
- unseen critical category >1%;
- standardised Wasserstein distance >0.5;
- categorical JSD >0.10;
- confidence-grade mix changes >15 percentage points;
- fallback usage doubles from baseline.

These are alerts, not automatic model invalidation.

11.6 PERFORMANCE DRIFT
----------------------
Evaluate rolling and cumulative:

- proper-score skill versus baseline;
- calibration slope/intercept;
- prediction-interval coverage;
- subgroup performance;
- decision regret.

11.7 SMALL-SAMPLE POLICY
------------------------
FPL provides limited weekly outcomes.

Use:

- hierarchical pooling;
- block bootstrap/posterior intervals;
- cumulative evidence;
- high-signal failures;
- no one-Gameweek automatic retrain.

11.8 STRUCTURAL CHANGE
----------------------
Known change:

- new manager;
- rules;
- promoted club;
- provider schema;
- season start.

Create a new regime; do not label every shift as model failure.

11.9 RESPONSE
-------------
1. confirm telemetry/data integrity;
2. identify source/regime;
3. quantify user impact;
4. compare champion/baseline/challenger;
5. adjust confidence/degrade if needed;
6. shadow refit/recalibrate;
7. run DMFP-15 gates;
8. approve promotion or rollback.

11.10 NO AUTOMATIC PROMOTION
----------------------------
Drift can trigger training.
It cannot automatically make the newly trained model champion.

16. DETERMINISTIC SIMULATIONS
======================================================================

16.1 ROOT SEED
--------------
Every model training, backtest, simulation and optimiser SAA run stores a
128-bit-or-greater root seed.

16.2 SEED TREE
--------------
Use NumPy `SeedSequence`.

Conceptual spawn key:

    project
    / run_id
    / module
    / model_version
    / fixture_or_gameweek
    / structural_world
    / parameter_draw
    / batch
    / worker.

16.3 INDEPENDENT STREAMS
------------------------
Changing worker count/order must not change scenario identity.

Assign scenario/batch streams before scheduling.

16.4 NO GLOBAL RNG
------------------
Ban:

- `numpy.random.*` global convenience state in production modules;
- implicit unseeded framework estimators;
- Python `random` without injected instance;
- worker PID/time-derived seeds.

16.5 RNG VERSION
----------------
Store:

- library;
- BitGenerator;
- version;
- SeedSequence entropy/spawn key;
- scenario range.

16.6 SORTING
------------
Inputs and outputs have deterministic ordering:

- UUID/key sort;
- stable ties;
- explicit locale;
- no set/dict iteration dependence in hashed manifests.

16.7 FLOATING POINT
-------------------
Bitwise reproducibility is not guaranteed across:

- CPU architecture;
- BLAS;
- compiler;
- parallel reduction;
- library version.

Define grades:

A — BITWISE:
same supported environment, identical hashes.

B — NUMERIC:
same semantic output within declared tolerance.

C — STATISTICAL:
distribution/proper scores within Monte Carlo bounds.

Production/replay target:
A on same release environment; B cross-host; C cross-major environment.

16.8 THREADS
------------
Confirmatory/backtest runs:

- fixed thread count;
- deterministic solver settings where available.

Fast production can use parallelism but records settings and requires numeric
replay.

16.9 SOLVERS
------------
Store:

- solver/version;
- seed;
- threads;
- tolerances;
- time limit;
- incumbent/bound.

A timeout can change plan.
That is recorded as execution variation, not hidden randomness.

16.10 GPU
----------------
GPU is not required for V1.

If introduced:

- framework deterministic settings;
- device/driver/CUDA version;
- known nondeterministic operations;
- statistical replay.

16.11 REPRODUCTION TEST
-----------------------
Nightly/weekly sample:

- rerun same artifact;
- compare hash/tolerance;
- alert.

18.1 SECRET INVENTORY

18.3 ENCRYPTED CREDENTIALS
--------------------------

---------------------

- private identity held off host;

--------------------------
Not used for production secrets because they can leak through:

- process inspection;
- crash reports;
- child processes;
- debugging;
- accidental dumps.

18.6 COMMAND LINE
-----------------
Never pass secret values as CLI arguments.

18.7 FILE PERMISSIONS
---------------------
- dedicated service user;
- credential directory inaccessible to other users;
- no shared service account;
- no world/group read.

18.8 SECRET ACCESS
------------------
Audit metadata:

- service;
- credential ID;
- access/start event;
- success/failure.

Do not log value or hash that enables offline guessing.

18.9 ROTATION
----------------
Baseline:

- provider/API keys: 90 days where supported without service harm;
- database service credentials: 90 days;
- internal API tokens/certificates: short-lived/automated where possible;
- backup encryption identity: annual review/rotation according to cryptoperiod
  and recoverability;
- immediate rotation after suspected exposure, staff/host change or provider
  request.

Provider limitations can change cadence but must be documented.

18.10 ZERO-DOWNTIME ROTATION
----------------------------
Where provider supports two active keys:

1. create new;
2. deploy;
3. verify;
4. revoke old.

Where only one key:

- maintenance/retry plan;
- deadline blackout for planned rotation.

18.11 BREAK-GLASS
----------------
Emergency credential:

- sealed/encrypted;
- access logged;
- use triggers incident/review;
- rotated after use.

18.12 SECRET BACKUP
-------------------
Only minimum recovery secrets.
Never put plaintext secrets in general backups.
