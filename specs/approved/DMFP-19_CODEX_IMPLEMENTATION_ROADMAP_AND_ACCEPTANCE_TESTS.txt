PURPOSE
-------
This document converts the complete Pulse architecture into a staged coding,
testing and acceptance programme for Codex.

The required stages are:

1. Repository and configuration
2. FPL rules engine
3. Canonical data model
4. FPL API ingestion
5. One odds provider
6. Odds normalisation
7. Basic minutes model
8. Goal and clean-sheet distributions
9. FPL-points simulation
10. One-Gameweek squad selection
11. Multi-Gameweek transfer optimisation
12. Backtesting framework
13. Price prediction
14. Chip optimisation
15. Rank-aware strategy
16. User interface

For every stage this document defines:

- the user-visible vertical slice;
- prerequisites;
- files Codex should create or modify;
- database migrations;
- public interfaces;
- CLI/API surfaces;
- unit tests;
- property tests;
- integration tests;
- golden fixtures;
- acceptance criteria;
- explicit exclusions;
- completion evidence;
- the exact boundary before the next stage.

The central implementation rule is:

    DO NOT GIVE CODEX THE ENTIRE SYSTEM IN ONE REQUEST.

Codex receives one bounded, reviewable work unit at a time.

The next work unit is released only after the current unit:

- runs;
- passes its tests;
- satisfies its public contract;
- has no hidden stubs in accepted scope;
- records its evidence;
- is reviewed;
- is merged;
- is tagged as accepted.

GOVERNING DELIVERY PRINCIPLE
----------------------------
Every stage must form a VERTICAL SLICE.

A vertical slice reaches from:

    typed input
    -> domain logic
    -> persistence/artifact where applicable
    -> CLI/API entry point
    -> deterministic output
    -> tests
    -> acceptance evidence.

A stage is not complete because:

- classes exist;
- schemas compile;
- unit tests pass in isolation;
- an unconnected notebook produces a chart;
- a TODO says the difficult part comes later;
- mocked data never reaches a public interface;
- the code looks plausible.

A stage is complete only when its promised capability can be demonstrated from
the supported command/API with approved fixtures and reproducible evidence.

NORMATIVE LANGUAGE
------------------
MUST / MUST NOT:
A non-negotiable requirement.

SHOULD / SHOULD NOT:
The default. Any deviation requires an architecture decision record.

MAY:
Optional, provided no MUST requirement is violated.

======================================================================
0. EXECUTIVE IMPLEMENTATION DECISIONS
======================================================================

0.1 DEVELOPMENT MODEL
---------------------
Selected:

- one Git repository;
- Python modular monolith;
- `src/` package layout;
- PostgreSQL integration from Stage 3 onward;
- immutable file/Parquet artifacts;
- typed domain/application interfaces;
- Typer CLI;
- FastAPI introduced when a stage genuinely needs an HTTP surface;
- Alembic database migrations;
- Pyomo/HiGHS for optimisation;
- pytest/Hypothesis for tests;
- Ruff and mypy for static quality;
- branch coverage and mutation testing;
- locked, hash-verified dependencies;
- one stage per release milestone;
- one accepted public contract per stage.

0.2 REPOSITORY PACKAGE
----------------------
Canonical Python package:

    dmf_pulse

No alternate package names.

0.3 INITIAL PYTHON VERSION
--------------------------
Proposed conservative baseline:

    Python 3.13.x

Stage 1 performs a compatibility spike.

Python 3.14 MAY be selected instead only if every required runtime dependency,
solver interface, test tool and deployment target passes.

The selected minor version is then exact and locked for the implementation
release line.

0.4 DATABASE
------------
PostgreSQL is the only production relational database.

SQLite is not an integration-test substitute for PostgreSQL semantics.

Unit tests may use pure in-memory repositories where the domain boundary is
explicit.

Database integration tests use an ephemeral real PostgreSQL instance.

0.5 PACKAGE AND DEPENDENCY CONTROL
----------------------------------
Use:

- `pyproject.toml` for package/tool configuration;
- a standards-compatible `pylock.toml` or approved exact lock generated by the
  selected toolchain;
- artifact hashes;
- a reproducible wheelhouse/release bundle;
- exact Python version;
- source and build manifests.

The Python Packaging User Guide identifies `pyproject.toml` as the central
configuration surface for build and tooling, while the `pylock.toml`
specification is intended for reproducible environment installation.

0.6 CODE QUALITY TOOLING
------------------------
Selected baseline:

- Ruff formatter and linter;
- mypy strict mode for production package;
- pytest;
- Hypothesis;
- coverage.py branch coverage;
- mutmut for mutation testing;
- Schemathesis for OpenAPI property/stateful tests after the API exists;
- Testcontainers or a controlled local PostgreSQL service for integration tests.

0.7 CI
------
Selected default:

- GitHub Actions if repository hosting permits it;
- a self-hosted/local equivalent MAY be used;
- workflow definitions remain repository-controlled;
- production release does not depend on an unreviewed marketplace action.

0.8 TESTING PHILOSOPHY
----------------------
Tests are not one final phase.

Each implementation ticket begins with:

1. public contract;
2. fixture;
3. failing test;
4. minimal implementation;
5. refactor;
6. acceptance demonstration.

0.9 MIGRATION PHILOSOPHY
------------------------
Schema changes:

- Alembic revision in the same stage;
- upgrade tested from prior accepted stage;
- downgrade or explicit irreversible rationale;
- clean-database migration tested;
- current schema fingerprint stored.

Data migrations are separate application operations unless a small, safe,
idempotent metadata change genuinely belongs in schema migration.

0.10 OPTIMISATION TOOLING
-------------------------
Selected:

- Pyomo as the transparent algebraic modelling layer;
- HiGHS as initial open-source solver.

Pyomo supports structured symbolic optimisation models and open/commercial
solver integration. HiGHS supports large sparse LP/MIP models and exposes
solver status, limits and MIP options.

0.11 API CONTRACT TESTING
-------------------------
Once FastAPI is introduced:

- OpenAPI exported and versioned;
- tests call application through HTTP;
- dependency overrides replace external services;
- Schemathesis generates edge cases from the OpenAPI schema;
- RFC 9457 errors validated;
- CLI/API parity tested.

0.12 STAGE MERGE RULE
---------------------
No stage is merged with:

- failing required tests;
- unresolved critical type/lint errors;
- migration drift;
- unreviewed public-interface change;
- hidden network dependency in unit tests;
- production secret;
- `pass`, `NotImplementedError` or unconditional TODO inside accepted scope;
- fake numerical output;
- silently skipped acceptance case.

0.13 STAGE TAGS
---------------
After acceptance:

    dmfp-stage-01-accepted
    ...
    dmfp-stage-16-accepted

The tag points to the accepted commit and evidence manifest.

0.14 IMPLEMENTATION ORDER
-------------------------
The requested stage order is retained.

Codex may not build ahead into later-stage business logic.

Foundational abstractions may be created earlier only when required by the
current vertical slice and explicitly approved.

======================================================================
1. CODEX WORK-UNIT RULES
======================================================================

1.1 ONE REQUEST, ONE OUTCOME
----------------------------
A Codex request should normally implement one of:

- one domain aggregate;
- one migration;
- one provider endpoint;
- one public service;
- one CLI command group;
- one model baseline;
- one optimiser formulation;
- one acceptance fixture.

Do not ask Codex to "implement Stage 8" in a single unconstrained prompt.

1.2 MAXIMUM NORMAL DIFF
-----------------------
Guideline:

- 3–12 production files;
- 3–15 test files;
- one migration;
- one public-interface addition;
- one fixture family.

A larger diff requires an explicit reason.

1.3 REQUIRED PROMPT INPUT
-------------------------
Every Codex implementation prompt includes:

- stage and ticket ID;
- exact objective;
- parent architecture sections;
- files allowed to change;
- public interfaces;
- fixture IDs;
- tests that must pass;
- exclusions;
- completion command;
- no-future-stage instruction.

1.4 REQUIRED CODEX RESPONSE
---------------------------
Codex must report:

- files changed;
- interfaces implemented;
- tests added;
- commands run;
- test results;
- assumptions;
- exclusions;
- known risks;
- migration impact;
- exact acceptance evidence path.

1.5 NO SPECULATION
------------------
If architecture is ambiguous:

- Codex stops within the ticket;
- records the question;
- does not invent a new rule/model.

1.6 NO UNRELATED REFACTOR
-------------------------
Refactoring outside the permitted files/scope requires a separate ticket.

1.7 NO NEW DEPENDENCY WITHOUT REVIEW
------------------------------------
Any new runtime or development dependency requires:

- purpose;
- licence;
- maintenance state;
- security review;
- lock update;
- SBOM update;
- alternative considered.

1.8 PUBLIC CONTRACT FIRST
-------------------------
Public schemas/protocols are reviewed before implementation details.

1.9 ACCEPTANCE-FIRST BRANCH
---------------------------
Recommended branch:

    stage/<stage-number>/<ticket-id>-<short-name>

------------------

2. DEFINITION OF DONE
======================================================================

2.1 TICKET DEFINITION OF DONE
-----------------------------
A ticket is done when:

- accepted code exists;
- required tests pass;
- no excluded feature was smuggled in;
- documentation/docstrings are current;
- lock/SBOM updated if needed;
- migration tested if present;
- public contract snapshot updated;
- acceptance evidence written;
- reviewer approval recorded.

2.2 STAGE DEFINITION OF DONE
----------------------------
A stage is done when:

- all mandatory tickets accepted;
- vertical slice demo succeeds from clean environment;
- public interface is versioned;
- all stage unit/property/integration tests pass;
- acceptance fixtures pass;
- coverage/mutation gates pass;
- no P0/P1 defect remains;
- database can upgrade from prior accepted stage;
- stage exclusions remain absent;
- stage acceptance manifest validates;
- rollback/replay instructions exist;
- Sebastian signs the stage gate.

-----------------------

- tag;
- completed_at;

- test commands/results;
- coverage;
- mutation;
- migrations;
- public-contract hashes;
- fixture hashes;
- demo commands/results;

- known limitations;

2.4 HUMAN-READABLE REPORT
-------------------------
Path:

    evidence/stages/<NN>/STAGE_ACCEPTANCE.md

2.5 ACCEPTED DOES NOT MEAN PRODUCTION
-------------------------------------
Early stages are research/development capabilities.
