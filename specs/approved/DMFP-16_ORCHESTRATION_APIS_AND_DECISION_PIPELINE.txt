PURPOSE
-------
This document defines how every Pulse module runs together as one dependable,
deadline-safe decision system.

The canonical live cycle is:

    Collect latest data
    -> validate and snapshot
    -> update player availability and minutes
    -> normalise odds and build market consensus
    -> generate coherent football-event distributions
    -> generate FPL-points distributions
    -> quantify uncertainty and scenarios
    -> predict prices and selling-value paths
    -> optimise squad, transfers, lineup, captain and chips
    -> evaluate rank-aware alternatives where active
    -> generate explanations and confidence
    -> publish recommendations
    -> record the complete decision state
    -> run champion/challenger shadows and later evaluation.

This document specifies:

- deployment topology;
- scheduler and worker architecture;
- daily refresh cadence;
- deadline-day cadence;
- event-driven refresh;
- task dependency graph;
- run and task state machines;
- failure and degradation behaviour;
- retries, idempotency and recovery;
- stage caching and invalidation;
- internal HTTP APIs;
- operation resources for long-running work;
- API versioning and errors;
- CLI commands;
- manual overrides;
- historical Gameweek replay;
- champion/challenger execution;
- output and artifact versioning;
- decision publication;
- pre-execution validation;
- observability and service objectives;
- implementation tests and acceptance gates.

The control-plane question is:

    CAN PULSE REPRODUCIBLY TURN THE EXACT INFORMATION AVAILABLE
    BEFORE A DEADLINE INTO A LEGAL, EXPLAINED, VERSIONED DECISION
    BEFORE IT IS TOO LATE TO ACT?

If the answer is not demonstrably yes, the recommendation is not production
ready.

GOVERNING PRINCIPLE
-------------------
The control plane must be:

- deadline aware;
- deterministic where possible;
- idempotent;
- dependency explicit;
- restartable;
- content addressed;
- fail closed for critical integrity;
- degradable for optional evidence;
- observable;
- replayable;
- auditable;
- simple enough to operate privately at zero software-licence cost.

Pulse will begin as a MODULAR MONOLITH with separate scheduler, API and worker
processes sharing PostgreSQL and immutable artifact storage.

It will not begin as a fleet of microservices.

The architecture preserves module boundaries through:

- typed Python interfaces;
- versioned schemas;
- task contracts;
- immutable artifacts;
- explicit dependency signatures;
- OpenAPI-defined internal HTTP interfaces.

Services can be separated later without changing those contracts.

======================================================================
0. EXECUTIVE ARCHITECTURAL DECISIONS
======================================================================

0.1 INITIAL DEPLOYMENT
----------------------
Selected first production topology:

- one Linux host or small private server;
- PostgreSQL as operational state and job ledger;
- local or S3-compatible immutable artifact storage;
- one FastAPI internal API process;
- one scheduler process invoked every minute;
- a small set of queue-specific worker processes;
- Typer-based `dmf` CLI;
- systemd services and timers;
- OpenTelemetry-compatible traces/log correlation;
- Prometheus-format metrics;
- no compulsory external message broker;
- no public write access;
- no automatic execution of FPL transfers, chips or lineups.

0.2 CONTROL-PLANE SOURCE OF TRUTH
---------------------------------
PostgreSQL owns:

- planned jobs;
- task states;
- worker leases;
- dependency edges;
- operation state;
- run manifests;
- override state;
- publication pointers;
- outbox events;
- cache metadata;
- manager decision records.

Artifact files own:

- large scenario matrices;
- model outputs;
- explanation bundles;
- score grids;
- Parquet datasets;
- solver files;
- reports.

0.3 QUEUE DECISION
------------------
Workers claim PostgreSQL task rows using row locks with `SKIP LOCKED`.

Why:

- multiple workers can claim different queue rows without waiting;
- the database already provides durability and transactions;
- the workload is modest;
- run state and queue state remain atomic;
- no new operational dependency is required.

`SKIP LOCKED` is suitable for a queue-like table, not for ordinary consistent
business queries.

0.4 SINGLETON DECISION
----------------------
Transaction-scoped PostgreSQL advisory locks protect:

- scheduler planning tick;
- one final decision run per manager/deadline/mode;
- deadline freeze/publication;
- model promotion;
- historical replay namespace creation.

Session-scoped locks are avoided in pooled worker code unless deliberately
required.

0.5 WAKE-UP DECISION
--------------------
PostgreSQL `LISTEN/NOTIFY` is used only as a low-latency wake-up hint.

The durable task/outbox table remains truth.

Reasons:

- notifications are delivered after commit;
- payloads are small;
- identical notifications can be folded in one transaction;
- consumers can disconnect;
- table polling is still required for recovery.

0.6 EXTERNAL WORKFLOW PLATFORM
------------------------------
Airflow, Dagster, Prefect, Temporal, Celery, Kafka and RabbitMQ are not required
for V1.

A later migration is justified only by measured need such as:

- multi-host scale;
- thousands of concurrent jobs;
- complex human workflows;
- broker-supported external systems;
- unacceptable PostgreSQL queue pressure.

The task contracts and operation resources are designed to permit migration.

0.7 API DECISION
----------------
Internal API:

- HTTP/JSON;
- FastAPI;
- OpenAPI 3.1;
- JSON Schema 2020-12-compatible schemas;
- Pydantic validation;
- `/api/v1` major-version path;
- RFC 9457 problem details;
- RFC 3339 UTC timestamps;
- ETag/conditional GET for immutable resources;
- application-level idempotency keys for mutating requests.

0.8 LONG-RUNNING OPERATION DECISION
-----------------------------------
A model or decision run can take seconds or minutes.

POST creates an operation/run and returns:

- HTTP 202 Accepted;
- operation ID;
- state;
- status URI;
- result URI when available;
- retry/poll guidance.

The operation resource is durable and queryable.

The client does not hold one long HTTP connection for a full deep optimiser
run.

0.9 CLI DECISION
----------------
The `dmf` CLI and internal API call the same application-service layer.

The CLI MUST NOT contain a second implementation of the pipeline.

0.10 CACHING DECISION
---------------------
Stage results are reusable only under an exact dependency signature.

No cache lookup may rely solely on:

- Gameweek;
- player name;
- wall-clock recency;
- "latest" model.

Immutable artifact resources can be cached indefinitely by content hash.

Mutable aliases such as `latest` use short/no cache and ETag revalidation.

0.11 FAILURE DECISION
---------------------
Critical integrity failures produce BLOCKED, not a plausible recommendation.

Optional-source failures produce DEGRADED only when an approved fallback exists.

A previous recommendation is never silently relabelled current.

0.12 PUBLICATION DECISION
------------------------
Every published recommendation is an immutable Decision Bundle.

A mutable pointer may identify the latest publishable bundle, but the bundle is
never edited.

0.13 FINAL DEADLINE DECISION
----------------------------
Pulse produces:

- early previews;
- standard actionable runs;
- final fast actionable run before the execution safety buffer;
- an exact postdeadline audit freeze selecting only `usable_at <= deadline`.

The postdeadline audit bundle cannot create a new actionable recommendation.

0.14 REPLAY DECISION
--------------------
Historical reruns have distinct modes:

- REPRODUCE_ORIGINAL;
- CURRENT_CODE_STRICT_INFORMATION;
- RECONSTRUCTED_RESEARCH;
- COUNTERFACTUAL;
- FINAL_OUTCOME_RESCORE.

No rerun overwrites an original decision.

2. COMPONENT ARCHITECTURE
======================================================================

2.1 COMPONENTS
--------------
SCHEDULER:
Plans due work.

WORKER:
Claims and executes one task type.

API:
Creates runs, reads status/artifacts, manages approved overrides and exposes
recommendations.

CLI:
Operator interface.

POSTGRESQL:
Control-plane and canonical operational state.

RAW/ARTIFACT STORE:
Immutable large outputs.

MODEL REGISTRY:
Approved model/version metadata and artifacts.

RULE REGISTRY:
DMFP-02 compiled rulesets.

PUBLICATION SERVICE:
Checks and publishes Decision Bundles.

EVALUATION SERVICE:
Scores frozen forecasts and decisions after outcome finality.

2.2 PROCESS BOUNDARIES
----------------------
Suggested systemd units:

- `dmf-api.service`;
- `dmf-scheduler.service` or timer-triggered one-shot;
- `dmf-worker-ingest@.service`;
- `dmf-worker-model@.service`;
- `dmf-worker-sim@.service`;
- `dmf-worker-optimise@.service`;
- `dmf-worker-evaluate@.service`.

2.3 MODULAR MONOLITH
--------------------
All processes use one installed package and common contracts.

Benefits:

- shared types;
- simpler deployment;
- direct function execution for replay/tests;
- fewer network failure modes;
- easier tracing and version control.

2.4 RESOURCE POOLS
------------------
Queue classes:

INGEST_IO:
Network and file ingestion.

CANONICAL_CPU:
Parsing, mapping and validation.

MODEL_CPU:
Availability, markets and price models.

SIMULATION_CPU:
Football/FPL scenarios.

OPTIMISATION_CPU:
MILP and chip/rank evaluation.

REPORT_CPU:
Explanations and reports.

EVALUATION_LOW:
Backtests and nondeadline work.

2.5 PROCESS ISOLATION
---------------------
Large model/simulation/solver tasks run in separate worker processes so:

- memory is released;
- crashes do not kill API/scheduler;
- resource/time limits can be applied;
- native libraries are isolated.

2.6 NO HIDDEN GLOBAL STATE
--------------------------
Each task receives:

- task ID;
- run ID;
- input artifact IDs;
- cutoff;
- ruleset;
- model versions;
- config;
- random-seed namespace.

It must not read an unversioned global `latest` unless the task contract
explicitly resolves and records it before execution.

3.10 EVALUATION

3.11 REPAIR
-----------
Controlled reprocessing after:

- mapping fix;
- schema fix;
- orphan artifact;
- failed task.

3.12 MANUAL
-----------
Operator-requested run with explicit reason.

5.2 PRE-FLIGHT HARD DEPENDENCIES

No decision run proceeds without:

- healthy/verified clock;

- ruleset state;

- resolvable current squad;
- code/config identity.

5.3 PARALLELISM
---------------
Independent ingestion tasks run concurrently.

Availability and odds can run concurrently after their source subsets validate.

Price modelling can run concurrently with football simulations.

Rank modelling can begin once opponent sources and candidate plans exist.

5.4 JOIN POINTS
---------------

5.6 CONDITIONAL TASKS

6.1 RUN IDENTITY
----------------
Each logical run receives immutable UUIDv7:

- run_id;
- parent_run_id;
- run_type;
- manager_id;
- season;
- Gameweek;
- information_cutoff;
- created_at;

6.2 RESOLVED CONTEXT
--------------------
Before task planning, resolve and freeze:

- ruleset ID/hash;
- code commit/build;
- environment lock hash;
- configuration bundle/hash;
- model registry snapshot;
- active override set/hash;
- random-seed root;
- deadline source/version;
- manager-state hash.

6.3 RUN SIGNATURE
-----------------
    run_signature =
      sha256(
        run_type
        + manager_state_hash
        + cutoff
        + ruleset_hash
        + model_registry_hash
        + config_hash
        + override_hash
        + code_commit
      )

6.4 DUPLICATE RUN
-----------------
If an identical run signature exists:

- return existing run by default;
- create a new attempt only with explicit `force_new_attempt`;
- never duplicate publication.

6.5 PARENT/DERIVATION
---------------------
Examples:

- fast final derived from standard run;
- rank run derived from points candidate run;
- explanation derived from optimiser bundle;
- replay derived from original run.

7. DAILY REFRESH CADENCE
======================================================================

7.1 SCHEDULER TICK
------------------
Every minute, all year.

The tick is cheap:

- acquire scheduler advisory lock;
- inspect due schedules/events;
- create missing jobs;
- update deadlines;
- release lock.

7.2 OFF-SEASON/PRELAUNCH
------------------------
- daily rules/game-launch/status check;
- daily fixture/team/player source check;
- no aggressive polling;
- immediate run after game launch/schema detection.

7.3 IN-SEASON BASE CADENCE
--------------------------
Suggested Europe/London operational schedule, configurable:

CONTINUOUS:
- one-minute planning tick;
- worker heartbeats every 15 seconds;
- source health every 5 minutes.

PRICE OBSERVATIONS:
- hourly outside the learned overnight update window;
- every 15 minutes in the broad overnight window;
- every 5 minutes in the narrow calibrated update window when official access
  policy and rate limits permit.

POST-PRICE RECONCILIATION:
- once after a detected official update cycle.

MORNING FULL REFRESH:
- once after expected overnight prices settle.

MIDDAY INCREMENTAL:
- official FPL, fixture, injury, market and manager-state changes.

EVENING INCREMENTAL:
- team news, European/cup context, transfer flow and odds.

MODEL REFIT:
- according to each module's approved cadence, normally not every daily
  projection run.

7.4 NO FIXED PRICE MINUTE
-------------------------
DMFP-11 supplies the learned update window.

Orchestration uses that interval, not a hard-coded folklore timestamp.

7.5 DAILY FULL DECISION
-----------------------
When more than 72 hours from deadline:

- one complete daily preview is sufficient unless material events occur.

7.6 CACHE WARMING
-----------------
Daily work precomputes:

- current player features;
- score priors;
- model parameter loads;
- candidate pools;
- scenario templates;
- optimiser warm starts.

7.7 LOW-PRIORITY WORK
---------------------
Backtests, compaction and challengers yield to deadline queues.

8. DEADLINE-DAY REFRESH CADENCE
======================================================================

8.1 DEADLINE-RELATIVE PLANNING
------------------------------
All times relative to official deadline D.

Suggested full/incremental runs:

D-72h:
full preview.

D-48h:
full preview if material fixtures/news or configurable.

D-24h:
full decision run.

D-12h:
full decision run.

D-6h:
full decision run.

D-3h:
full decision run.

D-2h:
full decision run.

D-60m:
full or incremental decision run depending cache/source state.

D-30m:
incremental model and optimiser run.

D-15m:
FINAL STANDARD ACTIONABLE run.

D-5m:
FINAL FAST ACTIONABLE run.

D-2m:
health, manager-state and critical-source diff check; emergency tactical/plan
rerun only if a material input changed and execution remains safe.

D:
exact audit cutoff.

D+0 to D+2m:
DEADLINE_AUDIT_FREEZE may finish, selecting only information usable by D.

D+5 to D+30m:
capture official saved team/opponent state when permitted and register forecast
for evaluation.

8.2 FINAL STANDARD
------------------
The D-15 run should:

- have full model stack;
- allow standard optimiser depth;
- be the default human execution recommendation.

8.3 FINAL FAST
--------------
The D-5 run:

- ingests only high-value changed sources;
- reuses exact dependency caches;
- runs fast posterior projection;
- reoptimises current decision;
- produces a diff from D-15;
- targets completion before the configured safety buffer.

8.4 D-2 CHECK
-------------
No expensive broad research.

Checks:

- official deadline unchanged;
- manager state unchanged;
- new P0/P1 source;
- major injury/fixture/price update;
- recommendation state hash.

If material:
issue an explicit emergency update and time-risk warning.

8.5 EXECUTION BUFFER
--------------------
Configured separately from deadline.

Factors:

- official site reliability;
- user execution speed;
- API/source latency;
- clock offset;
- action complexity.

Pulse must not recommend waiting beyond its safe execution point.

8.6 QUOTA RESERVE
-----------------
Free API quota is preserved for D-6h onward according to DMFP-04/05.

8.7 DEADLINE MOVE
-----------------
If official deadline changes:

- cancel/supersede future deadline-relative tasks;
- replan;
- preserve old plans;
- alert.

======================================================================
9. EVENT-DRIVEN REFRESH
======================================================================

9.1 MATERIAL EVENTS
-------------------
- fixture postponed/rescheduled;
- Gameweek assignment changed;
- official player flag/status changed;
- official rule/schema changed;
- manager-state change;
- large market move;
- player market suspended/reopened;
- price rise/fall;
- model promotion/rollback;
- manual override activated.

9.2 MATERIALITY FILTER
----------------------
Not every source row triggers a full optimiser run.

Each event evaluates:

- affected players/fixtures;
- projection delta upper bound;
- current squad/captain/candidate relevance;
- time to deadline;
- cached descendants;
- likely action switch.

9.3 EVENT COALESCING
--------------------
Events within a short window are grouped.

A debounce window avoids repeated complete runs during source bursts.

9.4 IMMEDIATE P0
----------------
No debounce for:

- deadline change;
- fixture cancellation;
- official ineligibility of selected captain/transfer target;
- ruleset invalidation;
- manager-state mismatch.

9.5 OUTBOX
----------
Canonical state changes write an outbox row in the same transaction.

A dispatcher creates downstream jobs and marks the outbox item consumed.

`NOTIFY` wakes the dispatcher; the outbox guarantees durability.

10. JOB PLANNING AND DEPENDENCIES
======================================================================

10.1 JOB DEFINITION
-------------------
Fields:

- job key;
- task type;
- queue;
- schedule policy;
- dependency selector;
- input contract;
- output contract;
- priority;
- timeout;
- retry policy;
- cache policy;
- failure criticality;
- resource class;
- code/adapter version.

10.2 PLANNING
-------------
Planner:

1. resolves run context;
2. creates task DAG;
3. resolves applicable tasks;
4. calculates task input signatures;
5. marks valid cache hits;
6. marks ready roots;
7. commits tasks/edges atomically;
8. emits queue wake-up.

10.3 DEPENDENCY TYPES
---------------------
ALL_SUCCESS:
all parents pass.

ALL_SETTLED:
parents can succeed/warn/not-applicable; child decides.

ANY_SUCCESS:
at least one source succeeds.

CONDITIONAL:
predicate on output/state.

SOFT:
failure lowers confidence but does not block.

HARD:
failure blocks.

10.4 DEPENDENCY VERSION
-----------------------
DAG definition version stored with run.

10.5 DYNAMIC FAN-OUT
--------------------
Examples:

- one fixture per event-model task;
- one model challenger per shadow task;
- one plan per rank evaluation;
- one historical Gameweek per replay.

10.6 DYNAMIC FAN-IN
-------------------
Manifest task waits for expected children and verifies counts.

10.7 SUPERSESSION
-----------------
A newer equivalent run may supersede queued/running noncritical tasks.

Running source acquisition is not killed if its artifact remains useful.

Publication chooses newest complete eligible run, not simply newest started.

11. WORKER CLAIM, LEASE AND HEARTBEAT
======================================================================

11.1 CLAIM
----------
Worker transaction:

- select READY task by priority/due time;
- `FOR UPDATE SKIP LOCKED`;
- set CLAIMED/RUNNING;
- assign worker;
- set lease expiry;
- commit.

11.2 LEASE
----------
Long tasks heartbeat and extend lease.

11.3 EXPIRED LEASE
------------------
Reaper checks:

- worker heartbeat;
- task process;
- output artifact;
- idempotency state.

Then:

- recover success;
- requeue;
- mark failed;
- quarantine.

11.4 DUPLICATE EXECUTION
------------------------
At-least-once execution is expected.

Effectively-once output through:

- task input signature;
- output uniqueness;
- atomic artifact publication;
- database constraints.

11.5 TASK ATTEMPT
-----------------
Every execution has an attempt record.

11.6 CANCELLATION
-----------------
Cooperative:

- cancellation requested;
- task checks safe points;
- solver receives termination;
- partial artifact not published;
- final state recorded.

11.7 RESOURCE LIMITS
--------------------
Per task:

- memory;
- CPU;
- wall time;
- open files;
- worker concurrency.

13.1 CACHE KEY

    stage_cache_key =

        stage_name
        + stage_version
        + sorted(input_artifact_hashes)
        + information_cutoff
        + ruleset_hash
        + model_version_ids
        + config_hash
        + override_hash
        + random_seed_policy
        + output_schema_version
      )

13.2 CONTENT CACHE
------------------
Immutable artifact addressed by SHA-256.

13.3 STAGE CACHE
---------------
Maps exact stage signature to validated output artifact.

13.4 QUERY CACHE
---------------
Short-lived API cache for expensive read queries.

13.5 CACHE VALIDITY
-------------------
Requires:

- artifact exists/hash verifies;
- schema compatible;
- source retention permits;
- task version exact;
- no invalidation/correction;
- random policy compatible.

13.6 CUTOFF
-----------
Same source data but different information cutoff can change eligibility.

Cutoff is in the key.

13.7 MANAGER STATE
------------------
Decision cache includes manager-state hash.

13.8 OVERRIDE
-------------
Any active override-set change invalidates dependent stages.

13.9 MODEL PROMOTION
--------------------
New champion does not delete old cache.

It creates a new key/version.

13.10 INVALIDATION GRAPH
------------------------
Lineage marks affected cache entries stale after:

- provider correction;
- entity mapping fix;
- rules change;
- model withdrawal;
- artifact corruption.

13.11 HTTP CACHE
----------------
Immutable resources:

- strong ETag from content hash;
- long `max-age`;
- `immutable` where appropriate.

Mutable aliases:

- ETag;
- `no-cache`/revalidation;
- no long stale serving.

Sensitive/private manager responses:

- `Cache-Control: private, no-store` unless a narrowly approved internal cache
  exists.

13.12 NO STALE DISGUISE
-----------------------
A cached decision always exposes:

- issue time;
- cutoff;
- age;
- supersession state.

14. FAILURE CRITICALITY
======================================================================

14.1 CRITICAL / FAIL CLOSED
---------------------------

- clock materially unhealthy;
- manager squad/bank/FT invalid;
- identity/mapping conflict affecting action;
- source-bundle corruption;
- FPL-points scenario invalid;
- optimiser illegal/infeasible without safe fallback;
- publication hash/lineage failure;
- current state changed after run;
- final actionable run completes after safe execution time.

14.2 IMPORTANT / DEGRADE WITH APPROVAL
--------------------------------------
- player-prop odds absent;
- exchange unavailable;
- price model unavailable;
- rank cohort unavailable;
- one injury source unavailable;
- challenger fails;
- explanation enrichment fails.

14.3 OPTIONAL
-------------
- noncandidate player deep scenarios;
- historical compaction;
- exploratory model;
- secondary report.

14.4 DEGRADED LABEL
-------------------
A degraded decision states:

- missing dependency;
- fallback;
- estimated impact;
- confidence reduction;
- action restrictions.

14.5 NO IMPLIED SUCCESS
-----------------------
`SUCCEEDED_WITH_WARNINGS` does not automatically make a run publishable.

Readiness gate decides.

======================================================================
15. FAILURE AND FALLBACK MATRIX
======================================================================

15.1 OFFICIAL FPL SOURCE DOWN
-----------------------------
If last healthy snapshot age <= approved threshold:

- use with explicit age;
- do not assume manager-state changes;
- disable price/ownership-sensitive action if counters stale;
- reduce confidence.

If manager state cannot be verified:
BLOCK.

15.2 FIXTURE SOURCE CONFLICT
----------------------------
Use official/authoritative source hierarchy.

Unresolved deadline/Gameweek assignment:
BLOCK affected decision or branch scenario if rules permit uncertainty.

15.3 INJURY SOURCE DOWN
-----------------------
Use other sources + prior availability model.

Reduce confidence and avoid hard availability claim.

15.4 MARKET SOURCE DOWN
-----------------------
Use remaining sources/team historical prior.

Label MARKET_DEGRADED.

No market = unknown, not zero.

15.5 PLAYER PROPS MISSING
-------------------------
Use DMFP-08 team-to-player model.

15.6 PRICE MODEL FAILS
----------------------
Optimise at current actual prices.

Disable price-motivated early execution and future price advantage.

15.7 RANK MODEL FAILS
---------------------
Use pure/robust expected-points plan.

15.8 CHIP MODEL FAILS
---------------------
Use no-chip ordinary captain/vice plan unless chip decision is manually locked
and can be legally evaluated.

15.9 OPTIMISER TIMEOUT
----------------------
Use best feasible incumbent if:

- legal;
- gap/status shown;
- confidence acceptable.

Otherwise:

- deterministic/no-transfer tactical fallback;
- BLOCK transfer recommendation.

15.10 SIMULATION FAILS
----------------------
Use last healthy same-cutoff-compatible scenario only if dependency signature
matches except for an approved nonmaterial source.

Otherwise BLOCK.

15.11 EXPLANATION FAILS
-----------------------
Numeric bundle can publish only if structured reason fields exist.

Natural-language rendering may be regenerated.

15.12 API DOWN
--------------
CLI can operate locally through application service.

Publication still recorded in database/artifact store.

======================================================================
16. RETRIES, BACKOFF AND CIRCUIT BREAKERS
======================================================================

16.1 READ/SAFE REQUESTS
-----------------------
Use DMFP-05 bounded retry policy.

16.2 NONIDEMPOTENT REQUESTS
---------------------------
Do not blindly retry.

Use:

- idempotency key;
- operation lookup;
- request fingerprint;
- unique database constraint.

16.3 DATABASE
-------------
Retry entire transaction for:

- serialization failure;
- deadlock;
- transient connection.

Do not retry bad constraints/schema as transient.

16.4 MODEL NUMERICAL FAILURE
----------------------------
- one deterministic retry with safer numerical settings if approved;
- then fallback/challenger;
- no endless loop.

16.5 CIRCUIT BREAKER
--------------------
Per provider/service:

CLOSED
OPEN
HALF_OPEN.

16.6 DEADLINE-AWARE RETRY
-------------------------
Do not schedule a retry whose expected completion is after the action safety
window unless it is for audit/evaluation.

16.7 RETRY-AFTER
----------------
Respect provider/server guidance.

16.8 FAILURE BUDGET
-------------------
Repeated failure escalates severity and blocks source-dependent actions.

39. ACCEPTANCE CRITERIA
======================================================================

A. CONTROL PLANE
[ ] PostgreSQL is the durable run/task/operation truth.
[ ] Worker claims use queue-safe locking.
[ ] Advisory locks protect singleton operations.
[ ] LISTEN/NOTIFY is not the only delivery mechanism.
[ ] No external broker is required for V1.

B. SCHEDULING
[ ] Daily and deadline-relative cadences are configurable.
[ ] D-15 and D-5 actionable runs exist.
[ ] Exact audit freeze uses deadline cutoff.
[ ] Quota reserve and safety buffer are represented.
[ ] Deadline changes replan all work.

C. DEPENDENCIES/FAILURE
[ ] DAG dependencies are explicit/versioned.
[ ] Critical failures block.
[ ] Optional failures have approved fallbacks.
[ ] No incompatible run outputs are merged.
[ ] Retry is bounded/idempotent/deadline-aware.
[ ] Worker crash recovery is tested.

D. CACHING/VERSIONING
[ ] Cache keys include every material dependency.
[ ] Immutable content/artifacts are hash-addressed.
[ ] Manager state/cutoff/override changes invalidate.
[ ] Published Decision Bundles are immutable.
[ ] Latest is only a pointer.
[ ] Every output carries complete lineage.

E. API/CLI
[ ] API is OpenAPI-defined and versioned.
[ ] Long work uses operation resources.
[ ] Mutating requests are idempotent.
[ ] Errors use RFC 9457.
[ ] ETag/conditional reads exist.
[ ] CLI and API share one service layer.
[ ] No official FPL write action is exposed.

F. OVERRIDES/REPLAY
[ ] Overrides are scoped, evidenced, approved and expiring.
[ ] Raw data are not rewritten.
[ ] Every replay mode is separate.
[ ] Historical clock and information cutoff are injected.
[ ] Original decisions cannot be overwritten.

G. PUBLICATION
[ ] Readiness gate verifies rules/data/models/legality/time.
[ ] State hash is rechecked before publication.
[ ] Late outputs are audit-only.
[ ] Recommendation, alternatives, reasons and confidence exist.
[ ] Execution is recorded separately.

H. OPERATIONS
[ ] Traces, logs and low-cardinality metrics exist.
[ ] Deadline dashboard and P0 alerts exist.
[ ] Full synthetic pipeline and failure injection pass.
[ ] Reproducible replay is possible.
[ ] Champion/challenger outputs are isolated.
