PURPOSE
-------
This document defines how data enters, survives, changes, fails, recovers and
becomes historically usable inside DMF Pulse.

It covers:

- scheduled ingestion;
- quota-aware and deadline-aware orchestration;
- raw immutable snapshots;
- PostgreSQL operational storage;
- Parquet analytical archives;
- timestamp standards;
- odds snapshot frequency;
- idempotent jobs;
- retries and circuit breaking;
- HTTP/API caching;
- schema validation;
- semantic and temporal validation;
- missing-data treatment;
- player and fixture matching;
- postponed fixtures;
- provider corrections;
- data-quality alerts;
- retention and deletion;
- backup and recovery;
- historical dataset construction;
- trustworthy backtesting.

The controlling question is:

    WHAT DID DMF PULSE GENUINELY KNOW, IN A USABLE FORM,
    AT THE EXACT FPL DEADLINE?

If the system cannot answer that question precisely, it cannot produce a
scientifically trustworthy backtest.

GOVERNING PRINCIPLE
-------------------
Pulse must preserve three different truths:

1. SOURCE TRUTH
   What the provider returned, byte-for-byte or as closely as the access method
   and licence permit.

2. SYSTEM-KNOWN TRUTH
   What Pulse had successfully received, validated, mapped and made usable at a
   particular time.

3. FINAL OUTCOME TRUTH
   The eventual corrected result after official review and provider corrections.

These truths are related but not interchangeable.

A correction published after an FPL deadline may improve the final label.
It must never be allowed to travel backwards into the features that supposedly
existed before the deadline.

------------------

SHOULD / SHOULD NOT:
The default. Deviations require an architecture decision record.

======================================================================
0. EXECUTIVE CONTROL SUMMARY
======================================================================

0.1 THE PIPELINE IN ONE SENTENCE
--------------------------------
DMF Pulse uses at-least-once retrieval, immutable source observations,
transactional canonical promotion, bitemporal facts and immutable deadline
bundles to achieve effectively-once analytical results and time-travel-safe
backtests.

0.2 CONTROLLING ARCHITECTURAL DECISIONS
---------------------------------------
DO-05-01. Retrieval is at-least-once.
Networks, schedulers and workers can duplicate a request. The system is designed
to tolerate this rather than claiming impossible end-to-end exactly-once
delivery.

DO-05-02. Canonical effects are effectively once.
Unique constraints, request fingerprints, immutable source IDs, transactional
promotion and deterministic transformations ensure duplicate retrievals do not
create duplicate domain facts.

DO-05-03. Raw durability precedes transformation.
Where storage rights permit, the source body and request metadata are durably
captured before parsing and canonical promotion.

DO-05-04. Raw observations are immutable.
A provider correction creates a new observation. No prior raw snapshot is
edited or overwritten.

DO-05-05. Identical content does not erase repeated observation.
The raw byte blob may be deduplicated by content hash, but every retrieval event
is recorded because receipt time, cache validation, freshness and quota usage
matter.

DO-05-06. PostgreSQL is the operational source of canonical truth.
PostgreSQL owns:

- canonical entities;
- temporal mappings;
- current/as-of facts;
- orchestration state;
- quality results;
- source metadata;
- deadline bundles;
- dataset manifests.

DO-05-07. Parquet is the immutable analytical archive.
Parquet stores versioned, columnar historical datasets for research,
backtesting and model training. It is not the only copy of orchestration or
canonical identity state.

DO-05-08. No raw API dump is hidden inside mutable database JSON.
Raw bodies live in a licensed object/file store. PostgreSQL stores metadata,
hashes, URIs and selected structured fields.

DO-05-09. Usable-at time controls historical features.
A record becomes eligible for a live decision only when it is:

- received;
- durably stored or handled according to retention policy;
- structurally valid;
- semantically valid enough;
- identity-mapped;
- promoted to canonical state;
- marked usable.

The strict feature cutoff uses `usable_at <= deadline`.

DO-05-10. Provider time is not system-known time.
A source timestamp before the deadline does not make late-received data
historically available.

DO-05-11. Corrections are bitemporal.
The system records when a corrected fact was valid in the domain and when Pulse
learned it.

DO-05-12. Deadline bundles are immutable.
Each FPL deadline produces a hash-addressed manifest of the exact eligible
source snapshots, canonical versions, model inputs, ruleset and code context.

DO-05-13. Cache reuse never disguises age.
A cached response carries original source/receipt age and cache-validation
status. A stale response cannot masquerade as a new observation.

DO-05-14. Missing is a typed state.
`NOT_OFFERED`, `NOT_YET_OPEN`, `RATE_LIMITED`, `SOURCE_DOWN`, `MAPPING_FAILED`,
`NOT_APPLICABLE`, `UNKNOWN` and numerical zero are different values.

DO-05-15. Raw data are never imputed.
Imputation occurs only in derived datasets or models, with method, version and
uncertainty.

DO-05-16. Entity matching is centralised.
Provider adapters emit raw aliases and external IDs into staging. They do not
independently perform irreversible name joins.

DO-05-17. Fixture identity survives schedule changes.
Postponement, kickoff change and Gameweek reassignment create new temporal facts
around the same canonical fixture unless official evidence establishes a new
match identity.

DO-05-18. Provider corrections invalidate descendants.
Affected current views, Parquet datasets, projections and backtests are marked
impacted through lineage. Historical decisions remain immutable.

DO-05-19. Quota is an operational resource.
Free API quotas are stored and allocated by decision value. Retry logic cannot
consume quota blindly.

DO-05-20. The initial scheduler is deliberately simple.
A one-minute planner tick, PostgreSQL job state, transaction-level advisory
locks and a small worker pool are preferred to an early distributed workflow
platform.

DO-05-21. No silent backfill.
Retrospectively acquired history is labelled `RECONSTRUCTED`, never mixed with
data genuinely captured live without explicit dataset mode.

DO-05-22. Quality gates are layered.
Transport, syntax, schema, identity, semantic, temporal, cross-source and
decision-readiness checks have separate outcomes and severity.

DO-05-23. Every alert is actionable.
A quality warning must state dataset, affected decision, evidence, severity,
owner, expiry and the safe fallback.

DO-05-24. Restore testing is part of storage.
A backup that has not been restored and verified is not accepted as a recovery
control.

0.3 CORE DATA LAYERS
--------------------
LAYER 0 — TRANSPORT
HTTP/file/manual acquisition metadata.

LAYER 1 — RAW / BRONZE
Immutable source bodies and exact observation envelopes.

LAYER 2 — STAGING
Parsed provider-shaped records awaiting validation/mapping.

LAYER 3 — CANONICAL / SILVER
Typed, mapped, bitemporal domain records.

LAYER 4 — DEADLINE KNOWLEDGE
Immutable "known and usable by cutoff" bundles.

LAYER 5 — ANALYTICAL / GOLD
Versioned feature, training and backtest datasets.

LAYER 6 — FINAL OUTCOMES
Official/corrected labels kept separate from historical features.

0.4 REQUIRED SUCCESS PROPERTY
------------------------------
For any decision run, Pulse MUST be able to reconstruct:

- the exact FPL deadline;
- the machine clock health;
- every source request and response used;
- every source and usable timestamp;
- cache status;
- provider quota state;
- schema version;
- entity-mapping version;
- canonical records;
- missing-data reasons;
- ruleset;
- code commit;
- dataset manifest;
- source-bundle hash;
- later corrections that were deliberately excluded.

-------------------
One observed provider response, file, stream message group or manual entry,

- request/context;
- provider/source time;
- receipt time;
- headers;
- raw body reference;
- hash;
- storage policy;
- validation state.

1.4 RAW BLOB
------------
Immutable stored body bytes referenced by one or more source snapshots.

1.5 INGESTION RUN
-----------------
One logical execution of a defined ingestion job for a scheduled time/window.

1.6 ATTEMPT
-----------
One network/storage/database attempt within an ingestion run.

1.7 USABLE RECORD
-----------------
A canonical record that passed the required gates for its intended decision
role.

1.8 INFORMATION CUTOFF
----------------------
Latest instant at which an input may be used in a decision or historical
simulation.

1.9 DEADLINE BUNDLE
-------------------
Immutable manifest of inputs eligible for one FPL deadline.

1.10 AS-OF QUERY
----------------
A query evaluated using facts and mappings known by a specified system time and
valid for a specified domain time.

1.11 CORRECTION
---------------
A later source or system action that supersedes a previously accepted value.

1.12 QUARANTINE
---------------
Durable storage of a rejected/unresolved record outside canonical use.

1.13 FRESHNESS
--------------
Age of the most relevant source/update observation at a decision time.

1.14 COMPLETENESS
-----------------
Observed coverage relative to an explicit expected denominator.

======================================================================
2. END-TO-END DATA FLOW
======================================================================

2.1 NORMAL FLOW
---------------
1. Scheduler creates a logical run.
2. Worker claims the run.
3. Quota and provider-health gates execute.
4. Request is constructed deterministically.
5. Cache validators are attached where supported.
6. Request begins; timing starts with a monotonic clock.
7. Response metadata and body are received.
8. Body is streamed to a temporary spool file.
9. Body hash and size are calculated.
10. File is flushed and made durable.
11. Temporary file is atomically published to immutable raw storage.
12. Source-snapshot metadata are committed.
13. Parser creates provider-shaped staging rows.
14. Structural/schema validation runs.
15. Entity resolution and semantic validation run.
16. Valid rows are transactionally promoted to canonical tables.
17. Quality metrics and alerts are emitted.
18. Eligible canonical rows receive `usable_at`.
19. Parquet export/compaction occurs asynchronously.
20. Deadline bundle includes only eligible records.
21. Run is finalised with counts, timings, hashes and quota usage.

2.2 RAW-STORAGE-FORBIDDEN FLOW
------------------------------
If source policy forbids body retention:

1. Request/response metadata are captured.
2. Body is held only in permitted volatile memory/temp storage.
3. Hash and permitted derived/canonical values are calculated.
4. Body is securely discarded.
5. `raw_storage_policy = FORBIDDEN`.
6. Source snapshot records:
   - body hash if permitted;
   - schema fingerprint;
   - row counts;
   - selected metadata;
   - deletion confirmation.
7. Canonical promotion continues only if allowed.

2.3 FAILURE AFTER RAW STORAGE
-----------------------------
If the database fails after raw persistence:

- raw sidecar manifest remains;
- run remains recoverable;
- orphan scanner registers or reconciles the blob later;
- no re-download is required unless policy demands.

2.4 FAILURE BEFORE RAW STORAGE
------------------------------
No canonical records are promoted.
Attempt is retryable according to policy.

2.5 FAILURE DURING CANONICAL PROMOTION
--------------------------------------
The database transaction rolls back.
Raw/staging records remain for replay.
A new attempt reuses the same source snapshot where appropriate.

3. STORAGE TOPOLOGY
======================================================================

3.1 INITIAL DEPLOYMENT
----------------------
Recommended zero-software-cost topology:

- one PostgreSQL instance;
- one local append-only raw/archive filesystem;
- one separate backup destination;
- Parquet datasets on local or S3-compatible filesystem;
- Python workers;
- one minute scheduler tick;
- encrypted secrets;
- Git for code/configuration, never raw data.

3.2 DIRECTORY STRUCTURE
-----------------------
Example:

data/
  spool/
    <ingestion_run_id>/
      response.partial
      envelope.partial.json

  raw/
    provider=<provider>/
      resource=<resource>/
        observed_date=YYYY-MM-DD/
          <sha256_prefix>/
            <body_sha256>.bin.zst
            <source_snapshot_id>.envelope.json

  parquet/
    silver/
      dataset=<dataset_name>/
        schema_version=<version>/
          season=<season>/
            observed_date=YYYY-MM-DD/
              part-<run_id>-<uuid>.parquet

    gold/
      dataset=<dataset_name>/
        dataset_version=<version>/
          ...

  manifests/
    source_bundles/
    deadline_bundles/
    dataset_versions/
    parquet_files/

  quarantine/
    provider=<provider>/
      date=YYYY-MM-DD/

  backups/
    manifests_only/

3.3 RAW CONTENT ADDRESS
-----------------------
The body path uses SHA-256 of the stored logical entity body.

Store separately:

- body_sha256:
  hash of source entity body after HTTP transfer decoding;

- stored_blob_sha256:
  hash of compressed/encrypted stored bytes;

- canonical_json_sha256:
  optional hash of canonicalised JSON for semantic duplicate detection.

3.4 RAW ENVELOPE
----------------
Each source snapshot envelope includes:

- source_snapshot_id;
- ingestion_run_id;
- attempt_id;
- provider;
- resource;
- request method;
- sanitized URL and parameter hash;
- request start;
- first byte;
- response complete;
- provider generated/update time;
- HTTP status;
- selected response headers;
- content type/encoding;
- quota headers;
- cache validators;
- body hash;
- body size;
- storage URI;
- storage policy;
- terms version;
- adapter version;
- schema fingerprint;
- clock health;
- error state.

Secrets and authentication headers MUST be removed.

3.5 IMMUTABILITY
----------------
Published raw files:

- are never opened for in-place modification;
- use unique content paths;
- are made read-only;
- are referenced through immutable metadata;
- are deleted only by an authorised retention workflow;
- produce a deletion tombstone if removed for rights/privacy reasons.

3.6 ATOMIC PUBLISH
------------------
Write protocol:

1. write `.partial`;
2. flush application buffers;
3. `fsync` file;
4. verify size/hash;
5. atomically rename into final path on the same filesystem;
6. `fsync` directory where supported;
7. commit metadata.

Parquet files use the same temporary-publish pattern because file metadata is
written at the end of the file.

3.7 DEDUPLICATION
-----------------
`raw_blob` is content-addressed and may have one stored copy.

`source_snapshot` is never deduplicated away.

Example:
Three API requests returning identical bytes create:

- one raw blob;
- three source snapshots;
- three request/receipt times;
- three quota/cache observations.

4. ORCHESTRATION ARCHITECTURE
======================================================================

4.1 COMPONENTS
--------------
SCHEDULER TICK:
Runs every minute and plans due jobs.

JOB PLANNER:
Expands schedule templates relative to FPL deadlines and fixture kickoff.

JOB TABLE:
Persistent source of work.

WORKER:
Claims and executes jobs.

QUOTA MANAGER:
Approves, reserves and reconciles API usage.

PROVIDER HEALTH:
Circuit-breaker and freshness state.

DEADLINE FREEZER:
Creates immutable deadline bundle.

4.2 WHY NOT A LARGE WORKFLOW PLATFORM INITIALLY
-----------------------------------------------
The initial workload is:

- low to moderate volume;
- small team;
- highly provider-specific;
- quota constrained;
- deadline critical.

A database-backed scheduler is easier to audit and recover.

Celery/Airflow/other orchestration MAY be introduced after the interfaces and
operational need are proven.

4.3 SCHEDULER DEPLOYMENT
------------------------
A Linux `systemd` timer or cron invokes:

    dmf ingest tick

once per minute.

The tick:

- obtains a PostgreSQL transaction-level advisory lock;
- reads schedule definitions;
- creates missing logical jobs;
- updates/cancels future jobs after fixture/deadline changes;
- exits quickly.

4.4 JOB CLAIMING
----------------
Workers claim due jobs using row locks and `SKIP LOCKED` or equivalent.

A job claim records:

- worker ID;
- claim time;
- lease expiry;
- heartbeat;
- attempt number.

Expired leases return to the queue only after safety checks.

4.5 ADVISORY LOCKS
------------------
PostgreSQL advisory transaction locks are used for:

- one scheduler tick;
- one provider quota update;
- one deadline bundle;
- one canonical promotion partition/window.

Locks are transaction-scoped where possible so failure releases them
automatically.

4.6 JOB PRIORITY
----------------
P0:
FPL deadline, rules and manager legality.

P1:
Current squad, captaincy, transfer targets and core market snapshots.

P2:
All EPL fixtures and availability.

P3:
Future-horizon context and redundant sources.

P4:
Historical compaction, exploratory markets and research.

4.7 JOB STATES
--------------

4.8 JOB DEPENDENCIES
--------------------
Examples:

    -> schedule_replan

    -> parse
    -> validate

4.9 MISSED RUNS
---------------
Do not blindly execute every missed poll after downtime.

Policy by job:

LATEST_ONLY:
Run once now.

CATCH_UP_EACH_WINDOW:
Run each missing logical window.

DEADLINE_EXPIRED:
Mark missed, alert and do not fabricate.

HISTORICAL_BACKFILL:
Queue separate reconstructed job.

6. PROVIDER-SPECIFIC INGESTION SCHEDULE
======================================================================

6.1 OFFICIAL FPL
----------------
Prelaunch:
- daily launch/status probe;
- no aggressive polling.

Preseason after launch:
- bootstrap and fixtures every 6 hours;
- daily full snapshot at a fixed UTC time;
- immediate snapshot after detected schema/rules change.

In-season, more than 72h before deadline:
- every 6 hours.

72h to 24h:
- every 2 hours.

24h to 6h:
- hourly.

6h to deadline:
- every 15 minutes.

Additional:
- D-5 minutes;
- D-1 minute only if provider health/terms/request policy permit;
- deadline freeze after D, selecting only `usable_at <= D`.

Live event/official points:
- event-specific cadence during matches;
- slower when not needed for user display;
- final/correction checks after last fixture.

All FPL calls are shared and cached. No per-user duplicate requests.

6.2 API-FOOTBALL FREE
---------------------
Limits documented in DMFP-04:

- 100 requests/day;
- 10 requests/minute.

Baseline daily planning:

- fixture/schedule sync: 2–4;
- injuries/sidelined: 2–4;
- lineup requests for active fixtures: up to 20;
- pre-match odds: up to 20;
- result/event/statistics: up to 20;
- transfer/player context: up to 5;
- reserve: minimum 20.

The planner must aggregate by league/date where supported.

Hard client rate:
<= 8 requests/minute.

Quota headers are captured from every response.

6.3 THE ODDS API FREE
---------------------
Free events endpoint:
- call no more than every 6 hours normally;
- every 60 minutes within 24h of FPL deadline if needed;
- endpoint is quota-free but must not be abused.

Event-market discovery:
- T-24h or first market window;
- T-6h for priority fixtures;
- one credit per qualifying call under current documentation.

Player-prop broad snapshot:
- one per fixture before the FPL deadline where markets exist.

Priority second snapshot:
- current-squad/captaincy/transfer/DGW fixtures only.

Monthly planner must keep:
- at least 75 credits emergency reserve;
- expected month usage <= 80% before reserve;
- actual usage reconciled from response headers.

If the FPL deadline occurs before the prop opens:
- record `NOT_YET_OPEN_AT_DEADLINE`;
- do not retrieve postdeadline data for that decision.

6.4 BETFAIR DELAYED
-------------------
Conditional and noncritical:

- T-24h;
- T-6h;
- T-2h where before FPL cutoff;
- nearest approved predeadline snapshot;
- no high-frequency hammering.

Every record is labelled:
- delayed;
- receipt time;
- source/provider time where present;
- possible maximum delay.

6.5 BETFAIR BASIC HISTORY
-------------------------
Manual or scheduled import after download:

- verify file/package hash;
- parse to staging;
- map market/selection;
- store dataset metadata;
- no live-decision role.

6.6 FOOTBALL-DATA.CO.UK
-----------------------
Weekly or after published update:

- conditional download if validators exist;
- hash;
- parse notes/columns;
- season-scoped import;
- historical research only.

6.7 MANUAL ODDS
---------------
Event-driven.

Manual record becomes usable only after:
- validation;
- operator/market/selection mapping;
- timestamp check;
- settlement status;
- optional second review for critical inputs.

======================================================================
8. IDEMPOTENCY
======================================================================

8.1 PRINCIPLE
-------------
Exactly-once retrieval across the Internet cannot be assumed.

Pulse provides:

- at-least-once request attempts;
- immutable observation;
- deterministic transform;
- effectively-once canonical effects.

8.2 REQUEST FINGERPRINT
-----------------------
Hash of:

- provider;
- HTTP method;
- normalized endpoint;
- sorted nonsecret query parameters;
- safe request-body hash;
- relevant representation headers;
- logical scope;
- adapter version where semantics differ.

Secrets are excluded.

8.3 SOURCE SNAPSHOT IDENTITY
----------------------------
A source snapshot is one observation, not one unique body.

Uniqueness may use:

- provider message/event sequence;
- provider update ID;
- request/attempt;
- response/body hash;
- provider timestamp.

8.4 CANONICAL UPSERT
--------------------
Use natural/provider mapping keys and `INSERT ... ON CONFLICT` where appropriate.

Append-only facts:
`DO NOTHING` on exact duplicate source identity.

Current materialized state:
create new temporal version, not destructive overwrite.

8.5 DATABASE TRANSACTION
------------------------
One canonical promotion transaction:

1. lock relevant identity/window;
2. verify snapshot still eligible;
3. insert facts;
4. close superseded system-time intervals where needed;
5. insert new temporal facts;
6. record validation/provenance;
7. set usable time;
8. commit.

8.6 SERIALIZATION
----------------
High-contention state transitions such as quota reservation and deadline bundle
may use PostgreSQL Serializable isolation.

Applications must retry SQLSTATE `40001` serialization failures.

8.7 TRANSFORM IDEMPOTENCY
-------------------------
Transformation ID:

hash(
  source_snapshot_ids,
  transform_name,
  transform_version,
  configuration_hash,
  mapping_version
)

A repeated transform produces the same output set/hash.

8.8 PARQUET IDEMPOTENCY
-----------------------
Parquet file names are unique, but dataset manifests deduplicate logical content.

A compaction does not change dataset semantics:
- new physical file set;
- same logical dataset version or explicit storage revision;
- old files retired through manifest, not overwritten.

======================================================================
11. PARQUET ANALYTICAL ARCHIVE
======================================================================

11.1 PURPOSE
------------
Parquet provides compact columnar storage for:

- large odds histories;
- FPL snapshot history;
- model features;
- deadline datasets;
- simulation inputs;
- backtest outputs.

Apache Parquet organizes files into row groups, column chunks and pages, with
file metadata used to locate relevant columns. PyArrow supports partitioned
datasets on local or object filesystems.

11.2 WHAT DOES NOT GO TO PARQUET
--------------------------------
Parquet is not the authoritative store for:

- worker leases;
- current quota;
- unresolved mappings;
- activation state;
- mutable incident workflow;
- secret material.

11.3 DATASET LEVELS
-------------------
SILVER:
Canonical append-only facts exported from PostgreSQL.

Examples:
- odds_quotes;
- price_snapshots;
- player_status_observations;
- fixture_revisions;
- lineup_observations.

GOLD:
Immutable research products.

Examples:
- deadline_player_features;
- deadline_market_features;
- training_minutes;
- backtest_inputs;
- final_outcome_labels.

11.4 PARTITIONING
-----------------
Use low-cardinality, query-relevant partitions.

Example odds dataset:

dataset=odds_quotes/
schema_version=1/
season=2026_27/
competition=EPL/
observed_date=2026-08-20/

Do not partition by:
- player;
- selection;
- market;
- fixture;
unless measured volume requires it.

11.5 FILE SIZE
--------------
Target practical file size:

- 64–256 MB for this project;
- avoid thousands of tiny files;
- compact daily/weekly depending volume.

Parquet guidance often recommends larger row groups in distributed/HDFS
environments; Pulse should tune for local memory and workload rather than copy a
1 GB rule blindly.

11.6 ROW GROUP
--------------
Initial target:
64–128 MB uncompressed logical row groups.

Measure:
- scan performance;
- memory;
- predicate pruning;
- compaction cost.

11.7 COMPRESSION
----------------
Default:
Zstandard at a moderate level, subject to benchmark.

Fallback:
Snappy for maximum compatibility.

Record codec/version in manifest.

11.8 EXACT TYPES
----------------
- timestamps as UTC Arrow timestamps;
- odds/prices as Decimal where exact source reproduction matters;
- canonical UUID as fixed/string representation;
- enums as dictionary-encoded strings where useful;
- no mixed-type columns.

11.9 SCHEMA EVOLUTION
---------------------
Each dataset root/version has one declared schema.

Breaking type/semantic change:
new schema version and dataset version.

Additive field:
allowed only after compatibility review.

11.10 WRITE PROTOCOL
--------------------
1. build Arrow table;
2. validate schema;
3. write temporary Parquet;
4. reopen and verify metadata/schema/row count;
5. hash;
6. atomically publish;
7. insert Parquet file record;
8. publish dataset manifest;
9. only then mark export complete.

11.11 MANIFEST
--------------
Includes:

- dataset version;
- schema version;
- file paths/hashes;
- row counts;
- min/max event/source/system time;
- source bundles;
- code/configuration;
- partition values;
- licence;
- compaction lineage;
- creation time.

11.12 COMPACTION
----------------
Compaction creates a new physical manifest.

It must not:

- alter values;
- remove rows without a documented duplicate rule;
- change time precision;
- silently apply corrections.

Old files remain until the new manifest verifies and retention policy allows
removal.

13. DEADLINE KNOWLEDGE BUNDLES
======================================================================

13.1 PURPOSE
------------
The deadline bundle is the evidence package for one decision point.

13.2 STRICT ELIGIBILITY
-----------------------
A source/canonical record is eligible only if:

- response/manual observation was available before cutoff;
- required raw handling completed before cutoff;
- validation passed before cutoff;
- mapping passed before cutoff;
- canonical promotion completed before cutoff;
- `usable_at <= cutoff`;
- source was not quarantined/blocking;
- licence permits use;
- relevant valid-time predicate holds.

13.3 NOT ENOUGH
---------------
These do NOT make a record eligible:

- provider timestamp before cutoff but receipt after;
- historical API retrieved later;
- correction published later with an earlier valid time;
- manual note entered later claiming it was seen earlier, unless a
  contemporaneous approved source snapshot exists;
- cached content with unknown age presented as current;
- record mapped after cutoff.

13.4 BUNDLE CREATION TIME
-------------------------
The freezer may run just after the deadline.

Its query cutoff is the exact official deadline.

13.5 BUNDLE CONTENT
-------------------
- deadline/gameweek;
- official deadline source;
- ruleset hash;
- clock-health record;
- source snapshot IDs;
- canonical record versions;
- mapping versions;
- missing-data inventory;
- quality issues;
- provider health;
- quota state;
- cache state;
- dataset schema;
- code commit;
- manifest hash;
- created_at.

13.6 BUNDLE MODES
-----------------
LIVE_OPERATIONAL:
What the live system could actually use.

RAW_OBSERVED:
What raw information was received, even if mapping/processing was not ready.

RECONSTRUCTED:
Historical data obtained later.

FINAL_OUTCOME:
Corrected labels after the event.

Only LIVE_OPERATIONAL supports claims about the live engine's historical
decision.

13.7 BUNDLE IMMUTABILITY
------------------------
A later correction creates:

- new outcome dataset;
- optional corrected/reconstructed research bundle;
- lineage relation.

It does not alter the live deadline bundle.

======================================================================
14. RETRY POLICY
======================================================================

14.1 PRINCIPLE
--------------
Retries are bounded, classified and quota-aware.

14.2 HTTP CLASSIFICATION
------------------------
200:
Process.

204:
Valid empty response if endpoint contract permits.

304:
Successful cache revalidation.

400:
No automatic retry; request bug.

401/403:
Disable provider/job and alert. Do not loop.

404:
Usually no retry.
May map to `NOT_YET_AVAILABLE` only for an endpoint whose contract permits it.

408:
Retry with bounded backoff.

409:
Provider-specific; retry only if documented safe.

425:
Retry after delay where relevant.

429:
Respect `Retry-After` and provider quota headers.

500/502/503/504:
Retry with exponential backoff and full jitter.

TLS/certificate:
No blind retry; security alert.

DNS/connect reset/timeout:
Retry.

Invalid/truncated body:
Retry retrieval, but retain invalid response metadata.

Schema/semantic failure:
Do not repeat the same request as a generic network retry.
Quarantine and alert.

14.3 RETRY-AFTER
----------------
HTTP semantics allow `Retry-After` as an HTTP date or delay seconds.

Pulse parses both.

14.4 BACKOFF
------------
Default GET:

- attempt 1: immediate;
- attempt 2: 1–3 seconds;
- attempt 3: 3–10 seconds;
- attempt 4: 10–30 seconds;
- attempt 5: 30–60 seconds;

with full jitter and provider-specific cap.

Do not retry beyond the information cutoff if the result would no longer be
eligible.

14.5 DEADLINE-CRITICAL POLICY
-----------------------------
Inside 30 minutes of deadline:

- shorter bounded retry;
- reserve quota;
- alternate provider in parallel after first material failure;
- alert earlier;
- never create a request storm.

14.6 DATABASE RETRY
-------------------
Retry whole transaction for:

- serialization failure `40001`;
- deadlock `40P01`, with investigation if repeated;
- transient connection loss.

Do not retry:
- constraint violations caused by bad data;
- missing mapping;
- invalid schema.

14.7 CIRCUIT BREAKER
--------------------
States:

CLOSED
OPEN
HALF_OPEN

Open after configurable failures or stale-duration breach.
Fallback routing activates.
Half-open probe is quota-aware.

15. API CACHING
======================================================================

15.1 PURPOSE
------------
Caching reduces:

- provider load;
- free quota consumption;
- repeated bytes;
- latency.

It must not erase observation history or fabricate freshness.

15.2 HTTP VALIDATORS
--------------------
Use where provided:

- ETag / If-None-Match;
- Last-Modified / If-Modified-Since.

HTTP caching defines ETag as a validator that can be sent with conditional
requests, and a 304 allows reuse of the stored representation with updated
metadata.

15.3 CACHE CONTROL
------------------
Honor:

- no-store;
- no-cache;
- max-age;
- must-revalidate;
- private;
- Vary.

Source contract/retention policy remains a separate legal control.

15.4 CACHE KEY
--------------
- provider;
- method;
- normalized URL;
- sorted parameters;
- representation headers;
- authentication/account context where representation varies;
- API version.

15.5 CACHE STATES
-----------------
MISS
FRESH_HIT
REVALIDATED_NOT_MODIFIED
REVALIDATED_CHANGED
STALE_ALLOWED_DEGRADED
STALE_PROHIBITED
BYPASSED
NO_STORE

15.6 STALE USE
--------------
Stale data may be used only if:

- source/contract permits;
- application policy explicitly permits;
- age is shown;
- decision confidence is reduced;
- no fresh critical source is required.

Near deadline, a stale odds quote cannot be described as a current quote.

15.7 CACHE IS NOT ARCHIVE
-------------------------
HTTP cache lifecycle and immutable research archive are separate.

A cached response can expire while its licensed historical source snapshot
remains archived.

Historical as-of view uses system time.

23.4 DESCENDANT INVALIDATION
----------------------------
Lineage identifies affected:

- Parquet files;
- dataset versions;
- projection runs;
- decisions;
- backtests;
- reports.

Status options:

UNAFFECTED
IMPACTED_NONMATERIAL
STALE
INVALID
RECOMPUTED
SUPERSEDED

23.5 DECISION IMMUTABILITY
--------------------------
A historical decision is never overwritten.

A correction may produce:
- corrected retrospective analysis;
- revised regret/outcome;
- explanatory note.

23.6 FINAL LABELS
-----------------
Official corrections after deadline may be used as final target labels.

The feature bundle remains unchanged.

24. DATA-QUALITY ALERTING
======================================================================

24.1 SEVERITY
-------------
P0 — DECISION BLOCKER
Examples:
- official deadline unknown;
- active ruleset/hash wrong;
- system clock materially wrong;
- manager state invalid;
- critical fixture/player mapping conflict;
- source-bundle corruption.

P1 — MAJOR
Examples:
- primary source down near deadline;
- odds stale beyond threshold;
- monthly quota unexpectedly exhausted;
- schema critical field removed;
- all player props unavailable;
- fixture assignment conflict.

P2 — DEGRADED
Examples:
- bookmaker coverage drop;
- missing assist markets;
- injury source stale;
- cross-source disagreement.

P3 — INFORMATIONAL
Examples:
- additive schema field;
- delayed noncritical backfill;
- planned compaction failure.

24.2 ALERT PAYLOAD
------------------
- alert ID;
- severity;
- dataset/provider;
- first/last occurrence;
- deadline impact;
- affected entities;
- expected/actual;
- evidence links;
- fallback;
- owner;
- acknowledgement;
- resolution;
- deduplication key.

24.3 DEDUPLICATION
-----------------
Repeated identical failures update one incident instead of sending unlimited
alerts.

24.4 ESCALATION
---------------
Near deadline:
- P0 immediate;
- P1 immediate;
- P2 summarised unless it changes recommendation.

Normal:
- P2 daily digest;
- P3 weekly.

24.5 ALERT CHANNELS
-------------------
MVP:
- terminal;
- dashboard;
- email;
- local log.

Later:
- Slack/mobile.

24.6 ALERT QUALITY
------------------
Every alert must answer:

- what broke?;
- why does it matter?;
- what is affected?;
- what fallback is active?;
- what human action is required?;
- when does it expire/escalate?

======================================================================
26. HISTORICAL DATASET CREATION
======================================================================

26.1 DATASET MODES
------------------
LIVE_OBSERVED:
Captured and usable before the original cutoff.

RAW_OBSERVED:
Captured before cutoff but not operationally usable then.

RECONSTRUCTED:
Obtained/processed later from historical sources.

FINAL_OUTCOME:
Official corrected label.

COUNTERFACTUAL:
Research scenario unavailable to the live engine.

Every dataset version declares one mode.

26.2 BRONZE DATASET
-------------------
Raw source-snapshot manifest and licensed bodies.

26.3 SILVER DATASET
-------------------
Canonical, typed, mapped observations with:

- source ID;
- valid/system time;
- usable time;
- correction lineage;
- quality flags;
- missing reason.

26.4 GOLD DEADLINE DATASET
--------------------------
One row universe per deadline/horizon.

Inputs are joined using:

- `usable_at <= cutoff`;
- valid-at target time;
- mapping as known at cutoff;
- fixture assignment as known at cutoff;
- latest eligible observation selected by explicit source policy.

26.5 AS-OF JOIN
---------------
For each feature:

1. identify subject and target;
2. filter eligible system/usable time;
3. filter valid time;
4. apply source preference;
5. select latest eligible observation;
6. preserve age/source/missing reason.

Never use an unrestricted current table.

26.6 LABEL JOIN
---------------
Outcomes may be final/corrected after the event.

Labels are joined only after features are frozen.

26.7 DATASET VERSION
--------------------
Includes:

- dataset_version_id;
- mode;
- purpose;
- source bundles;
- cutoff policy;
- season/Gameweeks;
- ruleset;
- mapping version;
- code commit;
- transform/config hash;
- schema;
- row count;
- file manifest;
- quality report;
- licence;
- created_at;
- parent/supersedes;
- split definition.

26.8 TRAIN/VALIDATION/TEST
--------------------------
Time-based splits only for live forecasting evaluation.

No random row split that leaks later matches, prices or corrections into earlier
periods.

26.9 BACKFILL
-------------
Backfill is a separate run with:

- reason;
- historical source;
- retrieval date;
- mode RECONSTRUCTED;
- no claim of live availability;
- mapping/version;
- comparison to live archive where overlapping.

26.10 SNAPSHOT FREQUENCY BIAS
-----------------------------
Providers observed more often create more rows.

Feature construction must use:
- time-aware selection;
- provider weighting;
- one observation per defined point;
not raw row counts.

26.11 DATASET FREEZE
--------------------
After manifest publication:

- no file mutation;
- correction creates new dataset version;
- old version retained according to rights;
- models reference exact dataset version.

======================================================================
27. TRUSTWORTHY BACKTESTING RULES
======================================================================

27.1 STRICT FEATURE RULE
------------------------
Feature eligible only if:

    usable_at <= simulated_cutoff

and the valid-time/domain predicate is satisfied.

27.2 LIVE SYSTEM BACKTEST
-------------------------
Uses LIVE_OBSERVED deadline bundle only.

27.3 RESEARCH RECONSTRUCTION
----------------------------
May use RECONSTRUCTED data but must be labelled and evaluated separately.

27.4 NO FUTURE MAPPING
----------------------
A player mapping resolved later cannot silently improve old live features.

A counterfactual rerun may use it only under a new labelled mode.

27.5 NO FUTURE FIXTURE ASSIGNMENT
---------------------------------
Use fixture/Gameweek assignment known at cutoff.

27.6 NO CLOSING ODDS
--------------------
Postdeadline or kickoff closing odds are evaluation features only, never input
to the earlier decision.

27.7 NO FINAL INJURY KNOWLEDGE
------------------------------
Retrospective injury duration/return dates cannot enter historical features.

27.8 NO FINAL POINTS AS FEATURE
-------------------------------
Final FPL points can be labels, not same-Gameweek predeadline inputs.

27.9 PIPELINE LATENCY
---------------------
If raw arrived before cutoff but became usable after cutoff:

- excluded from LIVE_OPERATIONAL;
- may appear in RAW_OBSERVED research.

27.10 CLOCK ERROR
-----------------
A material uncorrected clock error invalidates or downgrades affected deadline
bundles.

27.11 TEST
----------
Automated leakage test deliberately inserts a postcutoff correction and proves
it cannot appear in the deadline feature dataset.

======================================================================
30. BACKUP AND DISASTER RECOVERY
======================================================================

30.1 POSTGRESQL
---------------
PostgreSQL documentation identifies SQL dumps, filesystem-level backups and
continuous archiving as distinct approaches.

Recommended production controls:

- continuous WAL archiving for point-in-time recovery;
- regular base backups;
- nightly logical custom-format dump for selective recovery;
- backup manifests/hashes;
- separate storage destination.

30.2 RAW/PARQUET
----------------
- immutable copy to a second physical destination;
- checksum verification;
- incremental sync;
- retain manifests separately.

30.3 RECOVERY OBJECTIVES
------------------------
Proposed:

RPO:
- <=15 minutes for PostgreSQL during deadline week;
- <=1 completed ingestion window for raw data.

RTO:
- <=2 hours normal;
- <=30 minutes for last healthy deadline input/read-only mode.

30.4 RESTORE TEST
-----------------
Monthly:

- restore PostgreSQL into isolated environment;
- verify raw/Parquet hashes;
- recreate one deadline bundle;
- run one historical query;
- record duration/errors.

Before GW1:
full recovery rehearsal.

30.5 BACKUP IS NOT SOURCE RETENTION PERMISSION
----------------------------------------------
A source deletion obligation includes backups unless the agreement permits
otherwise.

32. DATA-QUALITY TOOLING DECISION
======================================================================

32.1 SELECTED INITIAL TOOLS
---------------------------
- Pydantic for request/record boundaries;
- Pandera for batch dataframe validation;
- PostgreSQL constraints for persisted integrity;
- custom domain and temporal checks;
- pytest/property tests;
- OpenTelemetry-compatible instrumentation.

32.2 WHY NOT RELY ON ONE TOOL
-----------------------------
A dataframe schema cannot enforce:

- bitemporal nonoverlap;
- fixture identity;
- decision cutoff;
- cross-source reconciliation;
- provider rights.

Database constraints cannot fully validate:

- complex batch distribution;
- provider response shape;
- market coverage.

Layering is required.

32.3 LAZY VALIDATION
--------------------
Batch validation SHOULD collect multiple errors in one run where safe, rather
than fail on the first row, to improve diagnosis.

Critical records remain quarantined.

38. ACCEPTANCE CRITERIA
======================================================================

A. TEMPORAL INTEGRITY
[ ] Provider time, receipt time and usable time are distinct.
[ ] Live historical features require usable_at <= cutoff.
[ ] Late corrections cannot enter prior features.
[ ] Deadline bundles are immutable.
[ ] Live/reconstructed/final modes are separate.

B. INGESTION
[ ] At-least-once retrieval is accepted.
[ ] Canonical effects are idempotent.
[ ] Raw durability precedes promotion where permitted.
[ ] Every attempt and quota effect is recorded.
[ ] Missed-run behaviour is explicit.

C. STORAGE
[ ] Raw observations are immutable.
[ ] Blob dedupe does not remove observation history.
[ ] PostgreSQL is canonical operational truth.
[ ] Parquet is versioned analytical archive.
[ ] Partial files cannot be published.
[ ] Manifests and hashes are mandatory.

D. QUALITY
[ ] Layered validation exists.
[ ] Missing reasons are typed.
[ ] No raw imputation.
[ ] Entity matching is centralised.
[ ] Unresolved critical records are quarantined.
[ ] Alerts are severity-based and actionable.

E. FIXTURES/CORRECTIONS
[ ] Postponement uses fixture revisions.
[ ] Schedule jobs are replanned.
[ ] Corrections preserve history and invalidate descendants.
[ ] Decisions are never overwritten.

F. OPERATIONS
[ ] Quota-aware retries and caching are implemented.
[ ] Retry-After and 429 are respected.
[ ] Clock health is monitored.
[ ] Backup/PITR and restore tests are required.
[ ] Provider retention policies control storage.
