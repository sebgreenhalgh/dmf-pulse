PURPOSE
-------
This document is the living architectural memory for DMF Pulse.

It records:

- accepted architectural decisions;
- provisional decisions;
- blocked target-season decisions;
- rejected alternatives;
- assumptions;
- known weaknesses;
- unresolved research questions;
- temporary shortcuts and technical debt;
- reasons for architectural changes;
- superseded decisions;
- review triggers;
- ownership and validation actions.

Its purpose is to stop ChatGPT, Codex and human contributors from repeatedly
reopening settled decisions or silently changing architecture.

Before proposing or implementing a change, every contributor MUST:

1. search this document for the relevant decision, assumption, weakness and
   open question;
2. read the authoritative module specification referenced by that entry;
3. determine whether the proposal is compatible, an experiment or a breaking
   architectural change;
4. update this record before treating a changed decision as accepted;
5. preserve the prior entry and its rationale.

This document is not a substitute for the detailed module specifications.
It is the authoritative index of what is settled, what is provisional and what
remains unresolved.

GOVERNING PRINCIPLE
-------------------
An architecture decision is not changed because a later conversation finds a
plausible alternative.

A settled decision changes only when:

- new official FPL rules invalidate it;
- new provider rights or technical constraints invalidate it;
- prospective or locked-holdout evidence materially favours another approach;
- implementation proves it infeasible or disproportionate;
- Sebastian explicitly changes the product objective or risk tolerance;
- a security, privacy or compliance issue requires replacement.

A change requires:

- a new or amended ADR entry;
- evidence;
- affected-module analysis;
- migration and rollback plan;
- acceptance-test changes;
- Sebastian's approval when the decision is production material.

SHOULD / SHOULD NOT:
The accepted default. A deviation requires an explicit record.

MAY:

0.2 STATUS VALUES
-----------------
ACCEPTED:
The default architecture. Implementation must follow it.

PROVISIONAL:
Selected for the first implementation but still requires empirical validation.
Codex implements it behind a version/config boundary where practical.

BLOCKED_TARGET_RULES:
Cannot activate until the 2026/27 game or rules are verified.

EXPERIMENTAL:
May run as a challenger or research branch. It cannot drive production output.

DEFERRED:
Valid future possibility, deliberately outside the current roadmap.

REJECTED:
Considered and not selected. Do not reintroduce without new evidence.

SUPERSEDED:
Previously selected but replaced. Kept for history.

WITHDRAWN:
Invalidated by evidence, rules, rights or security.

ADR-PROD-001 — Private decision support, not automatic FPL execution
----------------------------------------------------------------------
Status: ACCEPTED
Decision date: 2026-07-18
Supersedes: None

Decision:
Pulse provides recommendations, explanations and an execution checklist. Sebastian performs official FPL transfers, lineups, captaincy and chip activation manually. No official FPL write credential or automated action endpoint is part of V1.

Reason:
This materially reduces account, security, terms-of-service and deadline-execution risk while preserving the analytics objective.

Alternatives rejected or not selected:
Automated browser control; private undocumented write endpoints; stored FPL login/session automation.

Key assumptions:
Manual execution remains feasible and the official game does not provide an approved write API for this use.

Known weaknesses / consequences:
A correct recommendation can still be executed incorrectly or too late; execution state must be recorded separately.

Revisit when:
An official, documented, permitted write API becomes available and a separate security/compliance review approves its use.

Authoritative references:
DMFP-00, DMFP-16, DMFP-17, DMFP-18.

----------------------------------------------------------------------
ADR-PROD-002 — Expected remaining-season points is the default objective
----------------------------------------------------------------------
Status: ACCEPTED
Decision date: 2026-07-18
Supersedes: None

Decision:
Outside an explicitly selected rank or competition objective, Pulse maximises expected cumulative FPL points over the remaining season using rolling-horizon approximation and future-state value.

Reason:
The product exists to improve season performance, not weekly entertainment, team value or short-term rank volatility.

Alternatives rejected or not selected:
Maximise current-Gameweek points only; maximise team value; minimise variance; maximise expected rank at all times.

Key assumptions:
Expected points is the appropriate default utility for a manager seeking the strongest long-run finish.

Known weaknesses / consequences:
Terminal-value and horizon approximation can bias the practical objective; this must be validated sequentially.

Revisit when:
Sebastian selects a different explicit utility, or backtesting shows another declared objective improves the desired outcome.

Authoritative references:
DMFP-00, DMFP-10, DMFP-12, DMFP-14.

----------------------------------------------------------------------
ADR-PROD-003 — Raw projections remain independent of rank strategy
----------------------------------------------------------------------
Status: ACCEPTED
Decision date: 2026-07-18
Supersedes: None

Decision:
Football, minutes, price and FPL-points distributions are identical across points, protection and chasing modes for the same information and model versions. Rank affects only decision utility and opponent comparison.

Reason:
Changing forecasts because Sebastian is behind would mix belief with preference and make calibration impossible.

Alternatives rejected or not selected:
Inflating differential projections; reducing popular-player xP; rank-adjusted player forecasts.

Key assumptions:
The same physical football outcome distribution applies regardless of Sebastian’s league position.

Known weaknesses / consequences:
Users may misunderstand why a lower-xP player appears in a rank-aware plan; the UI must show the points sacrifice and target gain.

Revisit when:
A formally specified causal interaction exists between public ownership and football outcomes, which is currently outside scope.

Authoritative references:
DMFP-09, DMFP-14, DMFP-18.

ADR-PROD-004 — Modular monolith before microservices
----------------------------------------------------------------------
Status: ACCEPTED
Decision date: 2026-07-18
Supersedes: None

Decision:
Implement Pulse as one typed Python package with separate scheduler, API and worker processes sharing PostgreSQL and immutable artifacts.

Reason:
The workload is private and moderate. A modular monolith minimises deployment, network and schema complexity while preserving module contracts.

Alternatives rejected or not selected:
Kubernetes-first microservices; one service per model; distributed event bus as the initial architecture.

Key assumptions:
One host or small private server can satisfy the first-season workload and deadline objectives.

Known weaknesses / consequences:
A single codebase can still become tightly coupled; dependency rules and public contracts must be enforced.

Revisit when:
Measured scale, fault isolation or organisational boundaries make process/service separation materially beneficial.

Authoritative references:
DMFP-00, DMFP-16, DMFP-19.

ADR-DATA-003 — Immutable raw observations and effectively-once canonical effects
----------------------------------------------------------------------
Status: ACCEPTED
Decision date: 2026-07-18
Supersedes: None

Decision:
Retrieval is at least once. Every retrieval event is recorded. Raw source observations are immutable where rights permit. Canonical promotion is idempotent/effectively once.

Reason:
Retries and provider ambiguity are unavoidable; deleting duplicate retrieval evidence destroys operational truth.

Alternatives rejected or not selected:
Exactly-once network retrieval; overwrite latest payload; deduplicate away retrieval attempts.

Key assumptions:
Content hashing and database constraints can prevent duplicate canonical effects.

Known weaknesses / consequences:
Storage grows and provider retention may restrict raw persistence.

Revisit when:
Provider rights or storage capacity require a different retention implementation, without changing the logical immutability model.

Authoritative references:
DMFP-05.

7. ARCHITECTURAL CHANGE HISTORY
======================================================================

This section records why the architecture evolved. It is not a substitute for
individual supersession fields.

----------------------------------------------------------------------
CHANGE-001
----------------------------------------------------------------------
Change:
Source strategy changed to a zero-cost core.

Reason:
Early ecosystem concepts considered broader paid/commercial data. DMFP-04 made zero paid subscription a hard constraint and selected a free, market-anchored source stack.

Resulting decisions:
ADR-SRC-001 through ADR-SRC-004.

----------------------------------------------------------------------
CHANGE-002
----------------------------------------------------------------------
Change:
Market architecture changed from seeking completeness to market-anchored allocation.

Reason:
Free player-prop history/coverage was insufficient. Team markets now anchor probabilities and Pulse allocates player outcomes.

Resulting decisions:
ADR-SRC-002, ADR-EVT-004.

----------------------------------------------------------------------
CHANGE-003
----------------------------------------------------------------------
Change:
Historical truth changed from current cleaned data to temporal usable-at bundles.

Reason:
Leakage/reproducibility analysis showed provider timestamp and current database state were insufficient.

Resulting decisions:
ADR-DATA-004 through ADR-DATA-006.

----------------------------------------------------------------------
CHANGE-004
----------------------------------------------------------------------
Change:
Lineup model changed from minutes point estimates to START/BENCH/OUT distributions and coherent XI scenarios.

Reason:
FPL thresholds and team constraints require full role/minute uncertainty.

Resulting decisions:
ADR-MIN-001 through ADR-MIN-004.

----------------------------------------------------------------------
CHANGE-005
----------------------------------------------------------------------
Change:
Football modelling changed from independent player projections to a score-first coherent event engine.

Reason:
Team totals, clean sheets, scorer/assist competition and correlations must reconcile.

Resulting decisions:
ADR-EVT-001 through ADR-EVT-005.

----------------------------------------------------------------------
CHANGE-006
----------------------------------------------------------------------
Change:
FPL points changed from component expectation to exact scenario scoring with joint BPS.

Reason:
Rules, thresholds and bonus ties make independent mean addition invalid.

Resulting decisions:
ADR-PTS-001 through ADR-PTS-004.

----------------------------------------------------------------------
CHANGE-007
----------------------------------------------------------------------
Change:
Risk strategy changed from generic variance aversion to epistemic robust regret.

Reason:
Ordinary football variance includes valuable upside; uncertainty about the model and irreversible actions is the correct robustness target.

Resulting decisions:
ADR-UNC-001 through ADR-UNC-007.

----------------------------------------------------------------------
CHANGE-008
----------------------------------------------------------------------
Change:
Price prediction changed from inferred fixed threshold to recurrent latent-pressure hazards.

Reason:
The algorithm is proprietary, transfers are contaminated and multiple changes occur.

Resulting decisions:
ADR-PRC-001 through ADR-PRC-004.

----------------------------------------------------------------------
CHANGE-009
----------------------------------------------------------------------
Change:
Optimisation changed from squad picker to rolling stochastic control.

Reason:
Future transfers, prices, injuries, FTs, chips and information make one-shot optimisation insufficient.

Resulting decisions:
ADR-OPT-001 through ADR-OPT-006.

----------------------------------------------------------------------
CHANGE-010
----------------------------------------------------------------------
Change:
Chip advice changed from heuristic weeks to finite-inventory opportunity cost.

Reason:
Current gross points do not measure the value of consuming a scarce future option.

Resulting decisions:
ADR-CHIP-001 through ADR-CHIP-006.

----------------------------------------------------------------------
CHANGE-011
----------------------------------------------------------------------
Change:
Rank strategy was separated from raw projections.

Reason:
Beliefs must remain calibrated; only utility changes with competition position.

Resulting decisions:
ADR-PROD-003 and ADR-RANK-001 through ADR-RANK-004.

----------------------------------------------------------------------
CHANGE-012
----------------------------------------------------------------------
Change:
Backtesting changed from model-error reporting to a scientific trust gate.

Reason:
Deadline-specific vintages, proper scoring, sequential policy replay and multiple-testing controls are required before recommendations are trusted.

Resulting decisions:
ADR-EVAL-001 through ADR-EVAL-006.

----------------------------------------------------------------------
CHANGE-013
----------------------------------------------------------------------
Change:
Operations changed from scripts to a durable PostgreSQL control plane and immutable Decision Bundles.

Reason:
Deadline reliability, failure recovery and audit require explicit run/task state and lineage.

Resulting decisions:
ADR-OPS-001 through ADR-OPS-006.

----------------------------------------------------------------------
CHANGE-014
----------------------------------------------------------------------
Change:
UI changed from recommendation output to an uncertainty-aware Decision Cockpit.

Reason:
Human decisions need comparator value, assumptions, alternatives, change reasons and knowledge limits.

Resulting decisions:
ADR-UI-001 through ADR-UI-007.

----------------------------------------------------------------------
CHANGE-015
----------------------------------------------------------------------
Change:
Implementation changed from a monolithic Codex request to 16 stage-gated vertical slices.

Reason:
The complete architecture is too large to implement and validate safely in one pass.

Resulting decisions:
ADR-IMPL-001 through ADR-IMPL-003.

Why does this best serve the product objective?

Evidence:
Official rules, primary research, prospective tests, locked backtests or
implementation measurements.

Alternatives:
What was considered and why not selected?

Assumptions:
What must be true?

Consequences:
Benefits, costs, risks and migration requirements.

Affected components:
Documents, schemas, APIs, datasets, models, tests, UI and operations.

Revisit trigger:
Specific event or measurable threshold.

Rollback:
How to return to the prior accepted architecture.

Approval:
Sebastian and required technical/security reviewer.

8.2 EXPERIMENTS
---------------
A challenger does not alter an ACCEPTED decision.

The experiment record must specify:

- hypothesis;
- champion;
- challenger;
- data cutoff;
- primary metric;
- decision metric;
- promotion threshold;
- duration;
- result;
- whether an ADR change is proposed.

8.3 IMPLEMENTATION DISCOVERY
----------------------------
If Codex finds an accepted interface infeasible:

1. stop the ticket at a safe boundary;
2. provide minimal reproducer/evidence;
3. propose alternatives;
4. create an OPEN question or ADR change;
5. do not silently redesign the system.

8.4 EMERGENCY CHANGE
--------------------
A P0 security/rules/decision-integrity incident may require immediate temporary
withdrawal or fallback.

The emergency change must be recorded within the incident and converted into a
normal ADR review afterward.

11. MAINTENANCE AND VERSIONING
======================================================================

11.1 APPEND-OR-AMEND
--------------------
Never delete historical decisions.

A material change:

- amends the entry with version/date;
- adds a CHANGE record;
- marks alternatives/supersession;
- updates affected modules.

11.2 MACHINE-READABLE FUTURE
----------------------------
DMFP-19 may later implement a structured ADR registry in YAML/JSON/PostgreSQL.

This text remains the human-readable authority until an explicit migration is
accepted.

11.3 OPEN-QUESTION CLOSURE
--------------------------
When an OQ is resolved:

- record evidence;
- create/amend ADR;
- mark question RESOLVED with date and ADR;
- update implementation tests.

11.4 ASSUMPTION FAILURE
-----------------------
When an assumption fails:

- open incident/change if material;
- identify affected decisions/models/datasets;
- block/degrade affected output;
- update ADRs and roadmap.

11.5 TEMPORARY DEBT EXPIRY
--------------------------
Every TEMP item is reviewed at the stage or evidence trigger stated.
Temporary shortcuts do not become permanent by neglect.
