PURPOSE
-------
This document defines the central DMF Pulse decision engine.

It selects and explains:

- squad composition;
- transfers in and out;
- transfer timing;
- number of transfers;
- use or preservation of free transfers;
- transfer hits;
- bank;
- buying and selling prices;
- starting XI;
- legal formation;
- goalkeeper and outfield bench;
- bench order;
- captain;
- vice-captain;
- future squad paths;
- future lineup recourse;
- price and affordability paths;
- injury/rotation protection;
- fixture postponement responses;
- future flexibility;
- rolling re-optimisation.

The engine must return more than one answer:

- recommended_plan;
- conservative_plan;
- high_upside_plan;
- no_transfer_baseline;
- marginal_value_of_each_move;
- reasons;
- confidence.

It must also return:

- solver status and optimality gap;
- assumptions and binding constraints;
- scenario/uncertainty sensitivity;
- expected and robust utility;
- points, price and flexibility decomposition;
- alternative transfer timing;
- action-switch thresholds;
- full current-Gameweek tactical plan;
- future contingent policy.

The optimiser is not a static "best XV" generator.

It is a sequential decision system for a game where:

- transfers alter future squads;
- free transfers accumulate;
- buying and selling prices are path dependent;
- players can be injured or rotated;
- fixtures move;
- blanks and doubles appear;
- new information arrives;
- the manager can re-optimise every deadline;
- current choices preserve or destroy future options.

GOVERNING PRINCIPLE
-------------------
Pulse optimises the complete manager state, not a list of player projections.

The selected architecture is:

    EXACT RULE CONSTRAINTS
    + JOINT PLAYER-POINT SCENARIOS
    + MULTISTAGE TRANSFER RECOURSE
    + ROLLING-HORIZON MODEL PREDICTIVE CONTROL
    + ROBUST REGRET AND FLEXIBILITY VALUE
    + EXACT CURRENT-GAMEWEEK TACTICAL EVALUATION

The optimiser MUST NOT:

- select transfers using only one-Gameweek expected points;
- treat buying price and selling price as identical;
- ignore purchase-price history;
- approximate bench value as the fourth-highest mean only;
- ignore automatic substitutions;
- choose captain independently of vice-captain fallback;
- ignore player correlations;
- add price value after transfer selection;
- assume fixtures cannot be postponed;
- spend free transfers merely because they exist;
- roll transfers merely because rolling feels safe;
- hide a solver failure behind a plausible-looking plan;
- return one answer without decision alternatives and sensitivity.

0. EXECUTIVE OPTIMISATION DECISION
======================================================================

0.1 SELECTED PRODUCTION METHOD
------------------------------
The production engine is a hybrid multistage stochastic mixed-integer system:

A. MODEL-PREDICTIVE-CONTROL WRAPPER
At every FPL deadline:

- observe current state;
- solve a finite-horizon stochastic decision problem;
- execute only the immediate transfer/tactical action;
- retain the future contingent policy as explanation;
- ingest new information;
- re-solve at the next deadline.

B. SCENARIO-BASED STOCHASTIC OPTIMISATION
Use DMFP-09/10 coherent scenarios and scenario trees.

Expected utility is approximated by a weighted sample-average objective.

C. MIXED-INTEGER LINEAR MASTER
Select:

- squad;
- transfer path;
- bank;
- free-transfer transitions;
- purchase-price ownership spells;
- legal future manager state.

D. EXACT TACTICAL SUBPROBLEM
For a fixed current squad, evaluate exactly:

- every legal starting XI;
- outfield bench order;
- captain;
- vice-captain;
- automatic substitutions;
- captain fallback;

against the full current-Gameweek scenario matrix.

E. ROBUSTNESS AND ALTERNATIVE PLANS
Apply DMFP-10:

- robust regret;
- chance constraints;
- flexibility/terminal value;
- upside/downside modes;
- ACT-versus-WAIT.

0.2 WHY MILP IS PRIMARY
-----------------------
FPL decisions contain exact discrete constraints:

- own/not own;
- transfer in/out;
- fixed squad counts;
- club limits;
- position counts;
- formation;
- captain/vice;
- integer budget units;
- integer free-transfer inventory;
- transfer hits.

Mixed-integer linear programming provides:

- explicit constraints;
- reproducible solutions;
- solver bounds/gaps;
- infeasibility diagnosis;
- counterfactual re-solves;
- warm starts;
- mature open-source solvers.

Fantasy-sports research has repeatedly formulated roster/lineup selection using
integer programming. Hunter, Vielma and Zaman demonstrate how constrained
fantasy lineups and correlation/variance considerations can be expressed through
integer optimisation. Recent FPL-specific work also formulates deterministic and
robust lineup/captain models.

0.3 WHY STOCHASTIC PROGRAMMING IS PRIMARY
-----------------------------------------
Expected player points are not sufficient because:

- future injuries change transfer recourse;
- price paths change affordability;
- future free transfers depend on current moves;
- postponements create blanks/doubles;
- lineup uncertainty changes bench value;
- player points are correlated.

Sample Average Approximation replaces an intractable expectation by a finite
weighted scenario objective and solves the resulting discrete optimisation
problem. Kleywegt, Shapiro and Homem-de-Mello provide foundational convergence
and stopping analysis for stochastic discrete optimisation via SAA.

0.4 WHY MODEL PREDICTIVE CONTROL IS PRIMARY
--------------------------------------------
A full-season open-loop plan is brittle.

Model predictive control/receding-horizon control repeatedly:

- predicts;
- optimises over a horizon;
- executes the first control;
- updates state;
- re-optimises.

This matches FPL's deadline structure and makes future policy conditional rather
than pretending today's exact eight-week transfer sequence will be executed
unchanged.

0.5 WHY DYNAMIC PROGRAMMING IS NOT THE V1 CORE
-----------------------------------------------
An exact dynamic-programming state would include:

- 15-player squad from hundreds of players;
- purchase prices/ownership spells;
- bank;
- free transfers;
- chips;
- injuries;
- fixtures;
- rank;
- information state.

The state/action space is subject to the curse of dimensionality.

Dynamic programming remains valuable for:

- small toy validation;
- free-transfer state transitions;
- terminal-value approximation;
- reduced candidate pools;
- approximate value functions.

0.6 WHY MONTE CARLO TREE SEARCH IS NOT THE V1 CORE
---------------------------------------------------
MCTS is useful for sequential decisions with simulation, but FPL has:

- enormous transfer branching;
- highly constrained legal actions;
- expensive stochastic evaluations;
- many near-duplicate actions;
- need for auditable optimality bounds;
- long horizons and sparse observations.

MCTS surveys note that complex, high-branching practical domains usually need
substantial domain-specific modification.

MCTS remains a challenger after:

- action pruning;
- strong MILP policy priors;
- learned terminal value;
- progressive widening;
- reproducible simulation budgets.

0.7 SELECTED SOLVER STACK
-------------------------
Initial zero-licence-cost production stack:

- Pyomo or a thin native model layer;
- HiGHS through `highspy`/Pyomo APPSI;
- optional CBC/SCIP fallback after benchmark;
- exact enumerator/vectorised NumPy for tactical subproblem.

HiGHS officially supports linear programming, mixed-integer programming and
quadratic programming and provides a Python interface.

A commercial solver MAY be benchmarked later, but the architecture must not
depend on one.

0.8 SELECTED V1 DECOMPOSITION
-----------------------------
V1 uses:

1. candidate player/action pruning;
2. rolling-horizon stochastic transfer master;
3. top-K candidate squad/transfer plans;
4. exact current tactical evaluator;
5. scenario-based utility re-evaluation;
6. local improvement/neighbourhood search;
7. alternative-plan generation;
8. SAA replication/stability checks.

V2 may use logic-based Benders decomposition:

- master: squad/transfer path;
- subproblem: tactical/scenario evaluation;
- cuts: no-good, dominance and value cuts.

Logic-based Benders is appropriate when fixing strategic variables decomposes a
hard combinatorial subproblem.

0.9 OPTIMISATION HORIZON
------------------------
Default from DMFP-10:

- early season: 6–8 explicit Gameweeks plus terminal value;
- stable middle: 5–7;
- before blanks/doubles: extend through the relevant event;
- late season: all remaining Gameweeks;
- chip planning: include the candidate chip window.

The horizon is selected by information maturity and fixture structure, not one
fixed number.

0.10 OUTPUT MODES
-----------------
RECOMMENDED:
DMFP-10 robust-points policy.

CONSERVATIVE:
downside/availability protected, subject to a bounded expected-utility sacrifice.

HIGH_UPSIDE:
maximise defined upper-tail/rank-relevant utility subject to a minimum expected
utility and fragility constraint.

NO_TRANSFER_BASELINE:
zero current transfers, but optimised XI, bench, captain and vice.

If no materially distinct conservative/upside plan exists, say so rather than
forcing artificial diversity.

1. DECISION PROCESS AND STATE

1.1 DEADLINE EPOCH
------------------
Decision epoch t is an official FPL Gameweek deadline.

1.2 MANAGER STATE
-----------------
S_t includes:

- current 15-player permanent squad;
- ownership-spell/purchase price per player;
- current market price;
- current selling price;
- bank;
- free transfers available;
- chip inventory/status;
- current Gameweek;
- fixture assignments known;
- ruleset;
- rank/ownership objective mode;
- source/model confidence;
- prior transfer commitments;
- pending price/news events.

1.3 BELIEF STATE
----------------
B_t includes posterior/scenario distributions for:

- FPL points;
- minutes/availability;
- future prices;
- fixture postponement/reassignment;
- manager/team regimes;
- information revelation;
- model/source/rule uncertainty.

1.4 ACTION
----------
At current node:

- zero or more permanent transfers;
- optional transfer timing decision;
- starting XI;
- bench goalkeeper;
- ordered outfield bench;
- captain;
- vice-captain;
- chip interface state.

At future nodes:

- contingent transfers;
- lineups;
- captain/vice;
- chip actions where DMFP-13 integrates them.

1.5 TRANSITION
--------------
After action and Gameweek:

- points realized;
- prices change;
- purchase-price spells update;
- bank changes;
- free transfers transition;
- injuries/news/fixtures reveal;
- squad remains or changes;
- next decision state created.

1.6 REWARD
----------
- manager Gameweek points after auto subs/captain;
- minus transfer hits;
- plus terminal/future-state approximation at horizon;
- optional explicit rank utility later.

1.7 POLICY
----------
A policy maps observable decision-node state to action.

Future actions cannot use information unavailable at that node.

======================================================================
5. SQUAD CONTINUITY
======================================================================

5.1 BALANCE
-----------
For non-chip permanent squads:

    x[p,n]
      =
      x[p,par(n)]
      + tin[p,n]
      - tout[p,n]

5.2 TRANSFER CONSISTENCY
------------------------
- cannot buy an already owned player;
- cannot sell an unowned player;
- no player both bought and sold at same node unless rules/transaction semantics
  deliberately support same-deadline churn, which is normally prohibited in the
  canonical plan;
- number in equals number out for permanent transfers.

5.3 POSITION CONSISTENCY
------------------------
For each FPL position:

    sum_{p in position} tin[p,n]
      =
    sum_{p in position} tout[p,n]

or, equivalently, exact squad position counts at every node.

5.4 OWNERSHIP COHORT
--------------------
If retained:

    own[p,r,n] follows parent cohort.

If sold:

    cohort ends.

If bought:

    own[p,n,n] = 1.

A later repurchase creates a new cohort.

5.5 FREE HIT
------------
Free Hit temporary squad is a separate layer.

Permanent squad/ownership spells return afterward.
DMFP-13 controls chip activation, while DMFP-12 exposes the exact state
transition interface.

======================================================================
6. SQUAD COMPOSITION CONSTRAINTS
======================================================================

6.1 TOTAL
---------
    sum_p x[p,n] = configured squad size

6.2 POSITIONS
-------------
For each position q:

    sum_{p:position(p)=q} x[p,n]
      =
      configured squad count[q]

6.3 CLUB
--------
For each club c:

    sum_{p:club(p,n)=c} x[p,n]
      <= max_per_club

subject to grandfathered violation rules.

6.4 PLAYER AVAILABILITY
-----------------------
A formally ineligible/nonexistent player cannot be bought.

An injured/rotation-risk player is normally not prohibited; their distribution
and robust utility decide.

6.5 TRANSFER WINDOW / LEFT LEAGUE
---------------------------------
Use canonical current FPL catalogue status.

A player no longer purchasable cannot be transferred in.

======================================================================
7. BUYING, SELLING, BANK AND OWNERSHIP SPELLS
======================================================================

7.1 BUY PRICE
-------------
At node n/scenario state:

    buy_price[p,n]

integer tenths.

7.2 SELL PRICE
--------------
For cohort r:

    sell_price[p,r,n]

precomputed exactly from:

- purchase price at r;
- current scenario price at n;
- active ruleset.

Precomputation keeps the master linear.

7.3 BANK TRANSITION
-------------------
    bank[n]
      =
      bank[par(n)]
      + sum_{p,r} sell_price[p,r,n] tout_cohort[p,r,n]
      - sum_p buy_price[p,n] tin[p,n]

7.4 NONNEGATIVE
---------------
    bank[n] >= 0

7.5 PATH DEPENDENCE
-------------------
Two managers owning the same player can have different selling prices.

The optimiser MUST not use current price as universal sale proceeds.

7.6 PRICE UNCERTAINTY
---------------------
Future tree nodes contain price-path values from DMFP-11.

Current root transfer legality uses actual current prices, not expected future
prices.

7.7 AFFORDABILITY CHANCE
------------------------
A proposed delayed transfer must be affordable in the scenario states where the
policy promises execution.

If action is "wait then buy if affordable," affordability is a branch condition,
not a guaranteed action.

8. FREE TRANSFERS AND HITS
======================================================================

8.1 STATE TRANSITION TABLE
--------------------------
For every:

- FT before k;
- permanent transfer count m;
- chip state c;
- special event e;

configuration supplies:

- FT used;
- paid transfers;
- hit points;
- FT next.

8.2 ARC MODEL
-------------
Exactly one transition arc selected per node.

Link:

    transfer_count[n] = sum_p tin[p,n]

and transition arc transfer count.

8.3 HIT COST
------------
Scenario/Gameweek manager reward subtracts:

    paid_transfers[n] x hit_cost

Hit is not assigned to an individual player unless explanatory allocation is
computed later.

8.4 ROLL VALUE
--------------
Zero transfers can increase next state free-transfer inventory.

The optimiser values the resulting state through:

- future recourse;
- terminal value;
- explicit FT marginal value.

8.5 SPEND VALUE
---------------
Using a free transfer is rational only if the action utility exceeds the value
of preserving it.

8.6 TRANSFER CAP
----------------
Use configured maximum practical transfer count.

Unlimited Wildcard/Free Hit transfers are chip-specific.

======================================================================
9. CURRENT-GAMEWEEK TACTICAL SUBPROBLEM
======================================================================

9.1 WHY EXACT ENUMERATION
-------------------------
For a fixed 15-player squad, the tactical action space is finite and relatively
small compared with transfer selection.

Exact enumeration/vectorised evaluation avoids approximating:

- auto subs;
- captain fallback;
- legal formations;
- bench order;
- joint distributions.

9.2 LEGAL XI ENUMERATION
------------------------
Enumerate all subsets of 11 satisfying:

- exactly one goalkeeper;
- configured minimum/maximum position counts;
- every starter belongs to squad.

With 15 players, exhaustive legal enumeration is feasible after position
filtering.

9.3 BENCH
---------
The nonstarting goalkeeper is fixed as bench goalkeeper.

The three nonstarting outfield players have at most:

    3! = 6

orders.

9.4 CAPTAIN/VICE
----------------
For each XI:

- captain is one starter;
- vice is a different starter.

At most:

    11 x 10 = 110

ordered pairs.

9.5 VECTORISED PRUNING
----------------------
Before full scenario evaluation:

- upper-bound tactical expected utility;
- remove dominated XI/bench orders;
- shortlist captain candidates by expected/tail utility;
- retain any candidate within configured bound.

Pruning must be certified not to remove a possible optimum under the active
objective, or labelled heuristic.

9.6 EXACT SCENARIO SCORE
------------------------
For each scenario:

1. take selected XI;
2. determine appearance;
3. process goalkeeper substitution;
4. process outfield bench in official priority order;
5. preserve legal formation;
6. calculate scoring XI points;
7. apply captain extra if captain appears;
8. otherwise apply vice extra if vice appears;
9. if neither appears, no captain extra;
10. record bench/autosub outcomes.

9.7 CAPTAIN EXTRA
-----------------
Raw DMFP-09 player points already include one copy.

Manager score adds one extra copy for the active captain under normal captaincy.

Triple Captain is DMFP-13.

9.8 TACTICAL OUTPUT
-------------------
- XI;
- formation;
- bench GK;
- bench order;
- captain;
- vice;
- expected manager points;
- point PMF;
- threshold/tail;
- probability fielding 11;
- expected bench contribution;
- captain fallback probability;
- tactical covariance.

======================================================================
11. BENCH STRENGTH AND BENCH ORDER
======================================================================

11.1 BENCH VALUE
----------------
Bench value is not simply:

    sum expected bench points

because bench points score only through:

- automatic substitution;
- future lineup use;
- Bench Boost later;
- future squad flexibility.

11.2 CURRENT AUTO-SUB VALUE
---------------------------
For bench player p/order k:

    E[realised_auto_sub_points_p]
      =
      sum_s w_s
      x points[p,s]
      x 1[p enters under saved order]

11.3 COVERAGE
-------------
Metrics:

- P(field 11);
- P(field 10 or fewer);
- P(no goalkeeper);
- expected number of starters;
- expected lost starter points recovered;
- formation-block probability.

11.4 ORDER DECISION
-------------------
The first bench player is not always the highest expected-points bench player.

Order depends on:

- appearance correlation;
- starter nonappearance positions;
- formation constraints;
- point distribution;
- captain/vice interactions only indirectly.

11.5 FUTURE BENCH STRENGTH
--------------------------
Value through future:

- likely starts;
- fixture rotation;
- injury resilience;
- price/transfer flexibility;
- chip route.

11.6 BENCH OVERINVESTMENT
-------------------------
The optimiser can spend on bench only where marginal future utility exceeds
starting-XI opportunity cost.

Do not hard-code "cheap bench" or "strong bench" as doctrine.

11.7 CHANCE CONSTRAINT
----------------------
Optional conservative policy:

    P(field at least 11) >= target

or:

    P(field fewer than 10) <= epsilon.

Configuration and price-of-constraint must be reported.

======================================================================
12. CAPTAIN AND VICE-CAPTAIN
======================================================================

12.1 CONSTRAINTS
----------------
- exactly one captain;
- exactly one vice;
- distinct;
- both in selected XI;
- both in squad.

12.2 JOINT EVALUATION
---------------------
Use joint scenario points and appearance.

Expected captain extra:

    E[
      captain_points x 1[captain appears]
      +
      vice_points x 1[captain not appears, vice appears]
    ]

12.3 HIGH P_START IS NOT EVERYTHING
-----------------------------------
Vice selection depends on:

- captain nonappearance probability;
- vice points conditional on captain missing;
- correlation between their availability/events;
- vice own appearance;
- lineup legality.

12.4 CAPTAIN MODE
-----------------
DMFP-12 supplies normal captain/vice optimum.

DMFP-13 may change:

- chip;
- rank utility;
- horizon;
- ownership strategy.

12.5 NO EXPECTED-POINT DOUBLE COUNT
-----------------------------------
Do not double captain's expected points in the player projection upstream.

Captain multiplier is manager-scenario transformation.

13. TRANSFER MASTER OBJECTIVE
======================================================================

13.1 NODE REWARD
----------------
At node n:

    reward[n]
      =
      expected/weighted tactical manager points
      - transfer hit
      + optional explicit immediate price-route term
      + policy-specific utility.

13.2 HORIZON OBJECTIVE
----------------------
    max:
      sum_n probability[n] reward[n]
      + expected terminal value
      - robust regret penalty
      - lock-in/operational penalties
      + flexibility value

13.3 NO PRICE DOUBLE COUNT
-------------------------
Price affects:

- bank/affordability;
- terminal/marginal future points;
- selling value.

Do not also add arbitrary "team value points."

13.4 DISCOUNT
-------------
FPL points do not inherently need economic discounting.

A planning discount MAY reflect:

- forecast deterioration;
- rolling re-optimisation;
- terminal approximation.

It must be interpreted and calibrated, not chosen for convenience.

13.5 FUTURE LINEUP VALUE
------------------------
At future node:

- exact tactical subproblem if computationally feasible;
- generated lineup-value column;
- conservative linear approximation;
- terminal value.

Approximation error is measured.

14. SCENARIO-BASED STOCHASTIC PROGRAM
======================================================================

14.1 SAMPLE AVERAGE
-------------------
Given scenarios omega with weights w:

    max_a sum_omega w_omega U(a, omega)

subject to legal and nonanticipative decisions.

14.2 REPLICATION
----------------
Run multiple independently generated SAA sets.

For each:

- solve;
- record action/objective;
- evaluate on larger common holdout;
- estimate optimism and action stability.

14.3 TRAIN/EVALUATION SCENARIOS
-------------------------------
Optimisation scenarios and evaluation scenarios are separate where practical.

Do not report the in-sample SAA objective as unbiased true utility.

14.4 HOLDOUT
------------
Top plans are evaluated on a larger untouched scenario set.

14.5 STABILITY
--------------
Required:

- selected action frequency across SAA replicates;
- out-of-sample utility;
- regret;
- confidence interval;
- solver gap.

14.6 SAMPLE SIZE
----------------
Adaptive based on:

- plan stability;
- objective gap;
- rare event;
- horizon;
- scenario weights;
- compute budget.

14.7 COMMON RANDOM NUMBERS
--------------------------
Use common evaluation scenarios for plan differences.

15. NONANTICIPATIVITY AND RECOURSE
======================================================================

15.1 RULE
---------
Two scenario paths sharing a decision node must select identical actions at that
node.

15.2 IMPLEMENTATION
-------------------
Node-index decisions naturally satisfy nonanticipativity.

If leaf-index variables are used, add equality constraints for shared
information histories.

15.3 CURRENT ACTION
-------------------
Root transfer/lineup/captain is fixed across every scenario.

15.4 FUTURE RECOURSE
--------------------
After revealed information, future nodes may:

- transfer injured player;
- respond to price;
- change lineup;
- exploit blank/double;
- preserve/consume FT.

15.5 PERFECT-INFORMATION BUG
----------------------------
A common invalid model lets every scenario choose future actions with knowledge
of its full leaf outcome.

Automated tests must detect this optimistic upper bound.

15.6 EVPI UPPER BOUND
---------------------
A perfect-information solve may be calculated only as a diagnostic upper bound,
never as the achievable plan.

21. MULTI-OBJECTIVE PLAN MODES
======================================================================

21.1 RECOMMENDED PLAN
---------------------
Objective:

DMFP-10 robust-points score.

Must remain close to pure expected-points optimum and report price of robustness.

21.2 CONSERVATIVE PLAN
----------------------
Use epsilon-constraint:

- expected utility >= recommended expected utility - delta_conservative;
- minimise robust regret/CVaR shortfall;
- minimise P(field < target);
- prefer higher minutes/source confidence;
- limit irreversible/hit actions.

Do not define conservative as "low variance players" universally.

21.3 HIGH-UPSIDE PLAN
---------------------
Subject to:

- expected utility >= recommended expected utility - delta_upside;
- legal/availability fragility constraints;

maximise one selected upside objective:

- P(points exceed baseline by K);
- upper-tail expected gain;
- rank utility from DMFP-14;
- positive CVaR of gain.

Do not maximise raw variance.

21.4 NO-TRANSFER BASELINE
-------------------------
Constraint:

    current permanent transfer count = 0

Then exactly optimise:

- XI;
- bench;
- captain;
- vice.

It remains the baseline even if rolling one FT has future value.

21.5 DIVERSITY
--------------
Alternative plans should differ in meaningful root actions.

Use:

- Hamming-distance constraint;
- no-good cuts;
- required distinct transfer;
- objective epsilon.

Do not make a worse plan merely to populate the UI.

21.6 PLAN PARETO FRONT
----------------------
Return non-dominated plans across:

- expected utility;
- robust regret;
- upside;
- hit count;
- flexibility;
- price route.

======================================================================
22. MARGINAL VALUE OF EACH MOVE
======================================================================

22.1 ATOMIC MOVE
----------------
An atomic permanent transfer move is:

    OUT player A
    IN player B

of a compatible FPL position.

A multi-transfer bundle is a set of atomic swaps.

22.2 DROP-ONE RE-OPTIMISATION
-----------------------------
For move j in selected plan M:

    marginal_drop_j
      =
      V*(M)
      -
      V*(best legal plan with j forbidden)

This measures necessity while allowing alternatives.

22.3 ADD-ONE FROM BASELINE
--------------------------
    marginal_add_j
      =
      V*(baseline plus j, reoptimised)
      -
      V*(baseline)

Can differ from drop-one due interactions.

22.4 BUNDLE INTERACTION
-----------------------
Two moves can jointly unlock budget/position routes.

Therefore:

    total plan value
    != sum naive single-transfer values.

22.5 SHAPLEY ALLOCATION
-----------------------
For a selected bundle of small size, allocate total bundle value using Shapley
values across legal atomic moves:

    phi_j
      =
      average marginal contribution of j over move-order coalitions.

For up to five moves:
exact subset evaluation is feasible.

For larger bundles:
sampled permutation approximation.

Coalition value must preserve legality and reoptimise tactical choices.

22.6 ILLEGAL SUBSET
-------------------
If a partial transfer subset is not a valid FPL action:

- define atomic swaps so each subset is balanced; or
- use path/permutation attribution;
- do not assign arbitrary zero.

22.7 COMPONENT ATTRIBUTION
--------------------------
For each move:

- current GW points;
- horizon points;
- captain/lineup effect;
- hit/FT;
- selling/buying price;
- future budget value;
- flexibility;
- injury/rotation protection;
- interaction value.

22.8 MARGINAL PLAYER VALUE
--------------------------
Player inclusion marginal:

    V*(best plan requiring player)
    -
    V*(best plan forbidding player)

This can be more informative than raw expected points.

sample optimism and instability.

Mitigation:
replication/holdout/adaptive sample.

36.5 MODEL-PREDICTIVE CONTROL
-----------------------------
Decision:
SELECTED CONTROL WRAPPER.

Best for:
- rolling deadlines;
- updated state;
- finite horizon.

Weakness:
terminal-value/horizon sensitivity.

36.6 MONTE CARLO TREE SEARCH
----------------------------
Decision:
RESEARCH CHALLENGER.

Best for:
- large adaptive tree where exact formulation difficult.

Weakness:
branching, noisy value, reproducibility, legal action generation, no MIP bound.

36.7 ROBUST OPTIMISATION
------------------------
Decision:
SELECTED OVERLAY THROUGH DMFP-10.

Not a replacement for scenarios.

36.8 GENETIC/EVOLUTIONARY METHODS
---------------------------------
Decision:
FALLBACK/CHALLENGER ONLY.

Useful for:
- warm starts;
- complex non-linear objectives.

Not preferred because:
- no optimality bound;
- constraint repair;
- reproducibility;
- exact MILP structure exists.

36.9 REINFORCEMENT LEARNING
---------------------------
Decision:
DEFERRED.

Could learn terminal policy/value after enough prospective episodes, but one FPL
season provides little independent data and off-policy evaluation is difficult.

39. EXAMPLE MATHEMATICAL FORMULATION — DETERMINISTIC CORE
======================================================================

39.1 PLAYER SQUAD
-----------------
For Gameweek t:

    sum_p x[p,t] = SQUAD_SIZE

    sum_{p in pos q} x[p,t] = SQUAD_POSITION_COUNT[q]

    sum_{p in club c} x[p,t] <= MAX_CLUB

39.2 TRANSFER
-------------
    x[p,t] = x[p,t-1] + tin[p,t] - tout[p,t]

    tin[p,t] + tout[p,t] <= 1

    sum_p tin[p,t] = sum_p tout[p,t]

39.3 BANK
---------
    bank[t]
      =
      bank[t-1]
      + sum_p sale[p,t] tout[p,t]
      - sum_p buy[p,t] tin[p,t]

    bank[t] >= 0

39.4 LINEUP
-----------
    sum_p start[p,t] = XI_SIZE

    start[p,t] <= x[p,t]

    sum_{GK} start = 1

    sum_{DEF} start >= MIN_DEF
    sum_{MID} start >= MIN_MID
    sum_{FWD} start >= MIN_FWD

39.5 CAPTAIN
------------
    sum_p captain[p,t] = 1
    sum_p vice[p,t] = 1

    captain[p,t] <= start[p,t]
    vice[p,t] <= start[p,t]

    captain[p,t] + vice[p,t] <= 1

39.6 EXPECTED-POINT OBJECTIVE BASELINE
--------------------------------------
    max sum_t discount[t] [
        sum_p projected_points[p,t] start[p,t]
        + sum_p projected_points[p,t] captain[p,t]
        - hit_cost x paid_transfers[t]
    ]
    + terminal_value

This baseline is not the final production model because it ignores automatic
substitution, captain fallback and joint scenarios.
