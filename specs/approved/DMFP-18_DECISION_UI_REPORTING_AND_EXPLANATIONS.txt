PURPOSE
-------
This document defines how Pulse communicates decisions.

The interface must not simply output:

    "Buy Player X."

It must answer:

- What should Sebastian do?
- When should he do it?
- What is the expected value over the selected horizon?
- How much downside and upside are present?
- How confident is Pulse, and why?
- What assumptions matter?
- What price risk exists?
- What are the best alternatives?
- Why did the recommendation change since yesterday?
- What new information could reverse it?
- How do the scenarios compare?
- What is the opportunity cost of using a chip?
- What is the final-rank distribution when rank mode is active?
- What data, models, rules and overrides produced the answer?
- Is the recommendation fresh and safe to act on?

The interface must make uncertainty visible without burying the action.

The selected design is a DECISION COCKPIT with progressive disclosure:

LEVEL 1 — ACT
A fast, clear action and timing instruction.

LEVEL 2 — UNDERSTAND
Value, uncertainty, alternatives, assumptions and switch conditions.

LEVEL 3 — INVESTIGATE
Scenario distributions, model evidence, change attribution and provenance.

LEVEL 4 — AUDIT
Complete immutable Decision Bundle, sources, versions, diagnostics and replay.

GOVERNING PRINCIPLE
-------------------
The UI is not a decoration over model output.

It is the final decision-support component of Pulse.

Its job is to improve appropriate human reliance:

- neither blind automation;
- nor reflexive rejection after one bad outcome;
- nor false confidence from a precise mean;
- nor paralysis from excessive detail.

The interface must preserve the difference between:

FORECAST:
What might happen?

DECISION:
What action best serves the selected objective?

EXPLANATION:
Why does that action beat the alternatives?

UNCERTAINTY:
What is not known, how much can outcomes vary, and how fragile is the choice?

ASSURANCE:
Is the decision fresh, valid, reproducible and legally displayable?

The interface follows four explanation principles adapted from NIST:

1. EXPLANATION
   Provide evidence or reasons for outputs and processes.

2. MEANINGFULNESS
   Tailor explanations to Sebastian's task and level of detail.

3. EXPLANATION ACCURACY
   Explanations must faithfully reflect the actual system process.

4. KNOWLEDGE LIMITS
   Show when Pulse is outside its intended conditions or lacks sufficient
   confidence.

The UI MUST NOT optimise for "trust" as a vanity measure.

It should optimise for:

- comprehension;
- calibrated reliance;
- decision quality;
- timely action;
- error detection;
- contestability;
- reproducibility.

CRITICAL EXPLANATION RULE
-------------------------
No natural-language explanation may be the primary source of a numerical claim.

Every displayed number and substantive reason must come from a structured,
versioned explanation object derived from the Decision Bundle.

An optional language model may paraphrase approved fields only.

It must not:

- create a new number;
- infer an unrecorded cause;
- conceal a warning;
- strengthen uncertainty language;
- recommend an action not in the bundle;
- read external sources during rendering;
- change the plan;
- overwrite the deterministic explanation.

NORMATIVE LANGUAGE
------------------
MUST / MUST NOT:
A non-negotiable requirement.

SHOULD / SHOULD NOT:
The default. Deviations require an architecture decision record.

MAY:
Optional, provided no MUST requirement is violated.

0. EXECUTIVE INTERFACE DECISIONS
======================================================================

0.1 PRIMARY SURFACE
-------------------
The default screen is the DEADLINE DECISION COCKPIT.

It begins with one decision card:

- action status;
- exact transfer/tactical actions;
- execution timing;
- expected value versus no-transfer baseline;
- downside/upside;
- confidence;
- one-sentence reason;
- one-sentence warning or switch condition;
- freshness/deadline state.

0.2 PRIMARY ACTION STATES
-------------------------
ACT_NOW
WAIT_FOR_INFORMATION
HOLD_NO_TRANSFER
ROLL_TRANSFER
EXECUTE_BEFORE_SAFE_TIME
MANUAL_REVIEW
BLOCKED
AUDIT_ONLY
SUPERSEDED.

0.3 RECOMMENDATION LANGUAGE
---------------------------
The first line is imperative and operational.

Examples:

"WAIT. Recheck after Arsenal's press conference tomorrow; the expected value of
the information is greater than the modeled £0.1m price risk."

"MAKE ONE FREE TRANSFER: Player A -> Player B. Start B, captain C, first bench
D. Complete before 17:45 UK time."

"ROLL THE TRANSFER. No alternative robustly clears the value of holding two free
transfers next week."

"BLOCKED. Current squad state has not been verified since the last official
price update."

0.4 DEFAULT COMPARATOR
----------------------
Every recommendation is compared with:

    NO-TRANSFER BASELINE

that still optimises:

- starting XI;
- bench order;
- captain;
- vice-captain.

0.5 VALUE DISPLAY
-----------------
Default headline:

    EXPECTED HORIZON POINTS GAIN VERSUS NO TRANSFER

not:

- player xP alone;
- total squad xP without comparison;
- team value;
- model score;
- solver objective without interpretation.

0.6 UNCERTAINTY DISPLAY
-----------------------
Show:

- paired difference distribution;
- p10 / median / p90;
- probability recommended plan beats baseline;
- probability it loses by at least four points;
- robust regret or action instability;
- major uncertainty source.

Do not display only:

    +2.37 expected points

without a distribution.

0.7 CONFIDENCE DISPLAY
----------------------
Confidence is a multidimensional evidence grade.

It is not:

- the probability the player will return;
- the probability the recommendation is "correct";
- the inverse of variance;
- a decoration.

Default:

    B — Strong recommendation, but target minutes remain material.

Expandable dimensions:

- data;
- rules;
- lineup/minutes;
- football model;
- price;
- rank;
- decision stability;
- operational freshness.

0.8 VISUALISATION DECISION
--------------------------
Preferred:

- quantile dotplots for discrete plan-difference outcomes;
- CDF/exceedance curves for thresholds;
- percentile bands/fan charts across horizons;
- small-multiple scenario cards;
- exact tables with text alternatives;
- optional hypothetical-outcome animation for joint outcomes.

Error bars alone are not the default.

0.9 CHANGE EXPLANATION
----------------------
"Why changed?" is generated from controlled old-versus-new re-runs.

It separates:

- changed evidence;
- changed model/rules/objective;
- changed manager state;
- changed optimisation;
- Monte Carlo/solver noise.

A narrative guess is prohibited.

0.10 COUNTERFACTUAL DECISION EXPLANATION
-----------------------------------------
"What could change this decision?" displays the smallest plausible changes that
switch the plan.

Examples:

- Player B p_start below 74%;
- Player A avoids the expected price fall;
- fixture moved out of the Gameweek;
- price rise makes the route unaffordable;
- target-rank objective activated;
- press conference confirms no minutes limit.

These are model-decision counterfactuals, not necessarily causal statements
about real football.

0.11 RANK DISPLAY
-----------------
When rank mode is active, show:

- points-optimal and rank-optimal plans;
- expected-points difference;
- probability of target rank;
- final-rank distribution;
- target threshold distribution;
- named-rival win probabilities;
- effective ownership and leverage;
- confidence in opponent model.

0.12 CHIP DISPLAY
-----------------
Chip cards show:

- gross current incremental points;
- preparation/unwinding costs;
- continuation value;
- opportunity cost;
- net policy value;
- P(use now is optimal);
- competing chip opportunity;
- expiry pressure.

Never show only total Gameweek points with the chip.

0.13 ACCESSIBILITY DECISION
---------------------------
Target:

    WCAG 2.2 LEVEL AA

No information is conveyed by colour alone.

Every chart has:

- meaningful title;
- direct labels;
- table/text alternative;
- keyboard access;
- screen-reader summary;
- sufficient contrast;
- visible focus;
- reduced-motion fallback.

0.14 MOBILE DECISION
--------------------
The actionable summary must work on a phone near deadline.

Deep scenario/audit views can be desktop-first but remain accessible.

1. USER, TASKS AND DECISION CONTEXT
======================================================================

1.1 PRIMARY USER
----------------
Sebastian Greenhalgh.

1.2 PRIMARY TASK
---------------
Make a timely, informed and legally valid FPL decision before the deadline.

1.3 SECONDARY TASKS
-------------------

- compare alternatives;

- decide ACT versus WAIT;
- inspect chip timing;
- select points or rank objective;
- record human action/override;
- review yesterday's change;
- audit a past decision.

1.4 TIME PRESSURE
-----------------
Interface mode changes by time to deadline:

NORMAL:
more than 72 hours.

PREDEADLINE:
72–6 hours.

CRITICAL:
6 hours to safe execution cutoff.

FINAL:
inside the final hour.

AUDIT:
after action cutoff/deadline.

1.5 COGNITIVE LOAD
------------------
Near deadline:

- fewer default numbers;
- action and warning first;
- no modal labyrinth;
- no animation by default;
- deterministic fallback;
- latest safe time visible;
- one-tap plan copy/checklist.

1.6 EXPERTISE
-------------
The interface supports:

QUICK:
one-minute decision.

ANALYST:
full distributions and assumptions.

AUDITOR:
lineage, models and diagnostics.

The system does not require statistical notation for the primary task.

1.7 APPROPRIATE RELIANCE
------------------------
Research on algorithm aversion shows people can reject an algorithm after
seeing inevitable errors even when it outperforms a human comparator.

Research also finds that limited ability to adjust algorithmic forecasts can
increase willingness to use them, though adjustments can worsen accuracy.

Pulse response:

- show calibration and historical benchmark performance;
- show knowledge limits and mistakes;
- allow structured what-if/constraints and manual action;
- keep model output immutable;
- evaluate override outcomes;
- never imply perfection.

3. DEADLINE DECISION COCKPIT
======================================================================

3.1 HEADER
----------
- Gameweek;
- official deadline;
- current UK time;
- time to safe execution;
- Decision Bundle issue time;
- information cutoff;
- recommendation state;
- assurance status.

3.2 ACTION CARD
---------------
Required:

ACTION:
transfer(s), chip, captain, vice, XI, bench.

TIMING:
ACT NOW / WAIT / latest safe time / recheck event.

VALUE:
expected horizon gain relative to baseline.

RANGE:
p10 / median / p90 paired gain.

WIN PROBABILITY:
P(recommended beats baseline).

CONFIDENCE:
grade and short reason.

KEY ASSUMPTION:
highest-impact unresolved assumption.

FALLBACK:
best action if the assumption fails.

3.3 EXAMPLE
-----------
RECOMMENDED — WAIT

Recheck after the 13:30 manager press conference tomorrow. If Player B remains
projected above 78% to start, make Player A -> Player B before 17:45.

Expected five-Gameweek gain versus rolling: +2.1 points
Paired range: -3 / +2 / +8 points (p10 / median / p90)
Probability of beating roll: 61%
Confidence: C — role evidence is incomplete
Price route closes before deadline: 18%
Most important assumption: Player B starts at least four of five fixtures.

3.4 CURRENT TACTICS
-------------------
Always visible:

- formation;
- XI;
- first/second/third bench;
- captain;
- vice;
- P(field 11);
- captain fallback probability.

3.5 BASELINE
------------
Show no-transfer plan beside recommendation.

3.6 ACTION CHECKLIST
--------------------
Copyable:

1. Confirm official current squad and bank.
2. Make transfer.
3. Set XI.
4. Set bench order.
5. Set captain and vice.
6. Confirm chip.
7. Save team before latest safe time.
8. Record execution.

3.7 BLOCKED STATE
-----------------
A blocked state replaces action controls with:

- blocking reason;
- last valid recommendation and age;
- safe manual fallback;
- expected resolution;
- no green success styling.

3.8 DEGRADED STATE
------------------
Prominent banner:

"Player-prop markets are unavailable. Pulse is using its team-to-player model;
confidence reduced from B to C."

3.9 SUPERSEDED
--------------
Old Decision Bundle:

- superseded badge;
- link to current;
- change summary;
- cannot be mistaken for latest.

5.5 PAIRED COMPARISON
---------------------
Compare plans on identical scenarios:

5.6 ROUNDING
------------
UI:

- expected points to one decimal;
- probabilities to whole percent normally;
- prices to £0.1m;
- rank with appropriate significant precision.

Full values accessible in audit.

5.7 FALSE PRECISION
-------------------
Do not display:

    2.371948 expected points

as actionable precision.

5.8 SMALL DIFFERENCE
--------------------
If difference is below decision/Monte Carlo precision:

"Plans are effectively tied."

======================================================================
6. DOWNSIDE AND UPSIDE
======================================================================

6.1 RELATIVE DISTRIBUTION
-------------------------
Default downside/upside is relative to no-transfer or selected comparator.

6.2 CORE METRICS
----------------
- p10;
- median;
- p90;
- P(gain >0);
- P(gain >=4);
- P(loss <=-4);
- expected shortfall in worst 10%;
- upside expected gain in best 10%;
- maximum plausible validated range.

6.3 CONSERVATIVE
----------------
Explain downside protection:

"Reduces the probability of fielding fewer than 11 from 13% to 5%, costing
0.4 expected points."

6.4 HIGH UPSIDE
----------------
Explain explicit tail objective:

"Raises P(beating baseline by 10+) from 12% to 17%, costing 0.6 expected
points."

Do not say "riskier" without defining the risk.

6.5 HORIZON FAN
---------------
Cumulative plan-difference fan by Gameweek:

- median;
- 50%;
- 80%;
- 90% intervals.

6.6 TAIL WARNING
----------------
If Monte Carlo tail ESS is weak:
mark approximate and show diagnostic.

======================================================================
7. UNCERTAINTY VISUALISATION
======================================================================

7.1 DESIGN PRINCIPLE
--------------------
A point estimate remains visible but is not visually dominant enough to suppress
the distribution.

Research finds that people often misinterpret standard error bars and that
frequency-based quantile dotplots can support better probability extraction and
decision performance in some tasks.

7.2 QUANTILE DOTPLOT
--------------------
Default plan-difference visual:

- 20 or 50 equal-probability dots;
- each dot represents 5% or 2% of scenarios;
- aligned to integer FPL-point difference;
- zero/reference clearly marked;
- direct counts:

"31 of 50 representative outcomes favour the transfer."

7.3 CDF/EXCEEDANCE
------------------
Answer:

- chance gain is positive;
- chance gain is at least four;
- chance final rank reaches target.

7.4 FAN CHART
-------------
Use for:

- cumulative horizon points;
- team value;
- final rank percentile trajectory.

7.5 HYPOTHETICAL OUTCOME PLOTS
------------------------------
Optional for:

- side-by-side plan outcomes;
- rank evolution;
- correlated squad/rival outcomes.

HOPs animate individual draws and have performed well for some multivariate
probability judgments.

Rules:

- optional;
- pause/control;
- no default in final-minute mode;
- reduced-motion alternative;
- fixed representative seed;
- static small multiples/table.

7.6 DENSITY/VIOLIN
------------------
Analyst view only.

Discrete FPL-point support must remain clear.

7.7 ERROR BARS
--------------
Not used alone.

Label interval meaning exactly.

7.8 COLOUR
----------
- colour plus icon/text/pattern;
- no red/green-only semantics;
- accessible palette;
- consistent meanings;
- user colour theme cannot alter status semantics.

7.9 SCREEN-READER SUMMARY
-------------------------
Example:

"The recommended plan has a 61% probability of outscoring no transfer over five
Gameweeks. Ten percent of scenarios lose three points or more; ten percent gain
eight points or more."

7.10 DATA TABLE
----------------
Every visual can be opened as a sortable/downloadable accessible table.

11. COUNTERFACTUAL AND SWITCH-THRESHOLD EXPLANATIONS
======================================================================

11.1 PURPOSE
------------
Explain what minimal plausible change reverses the recommendation.

Counterfactual explanations can help a user understand a decision and what
would need to change to obtain a different result without requiring full
exposure of every model computation.

11.2 DECISION COUNTERFACTUALS
-----------------------------
Derived from actual reoptimisation.

Examples:

- p_start;
- minutes;
- team goals;
- player price;
- FT count;
- fixture;
- model weight;
- rank target;
- chip future opportunity.

11.3 SINGLE-VARIABLE
--------------------
Report smallest switch:

"Transfer becomes preferred when Player B's expected minutes rise from 63 to
67."

11.4 MULTIVARIABLE
------------------
When no single plausible change:

"Requires both Player B p_start above 80% and no target price rise."

11.5 PLAUSIBILITY
-----------------
Only show counterfactuals inside approved plausible uncertainty ranges unless
explicitly labelled hypothetical.

11.6 ACTIONABILITY
------------------
Separate:

OBSERVABLE/ACTIONABLE:
price, information, target objective.

OBSERVABLE/NOT CONTROLLABLE:
injury, fixture.

MODEL-SENSITIVITY:
model weights, terminal value.

11.7 CAUSAL CAUTION
-------------------
A model counterfactual does not prove:

"If Player B gets three extra minutes, the real-world decision is caused to
improve."

It states how the current model/optimiser decision boundary behaves.

11.8 STABILITY
-------------
Show broad switch region when optimiser is discontinuous or Monte Carlo noise
material.

12.4 CONTROLLED RE-RUN ATTRIBUTION
----------------------------------
Create hybrid runs:

- old state with one change group updated;
- new state with one change group reverted.

Calculate action/value effects using common random numbers.

12.5 PATH DEPENDENCE
--------------------
One-at-a-time contributions depend on order and interactions.

Primary display:

- canonical operational order;
- interaction/residual.

Analyst display:

- grouped Shapley attribution over a manageable number of change groups;
- uncertainty;
- runtime.

12.6 ZERO RESIDUAL STANDARD
---------------------------
Numerical value change must reconcile:

    old value
    + attributed main effects
    + interactions
    + numerical/Monte Carlo residual
    =
    new value.

Unexplained residual beyond tolerance is an error.

12.7 DECISION FLIP
------------------
Explain both:

- value movement;
- constraint/threshold flip.

Example:

"Player B's price rise reduced bank below the route threshold. This—not a
projection change—made the previous two-transfer plan infeasible."

12.8 MODEL VERSION
------------------
Prominent:

"Recommendation changed because the champion minutes model was promoted."

Do not imply new football evidence.

12.9 RANDOMNESS
---------------
If only simulation/solver variation changes a near tie:

"Plans remain statistically tied; display ordering changed due to numerical
precision."

Do not frame as substantive football change.

12.10 CHANGE TIMELINE
---------------------
Chronological events with impact.

38. ACCEPTANCE CRITERIA
======================================================================

A. ACTION
[ ] Primary action and timing are immediately visible.
[ ] No-transfer is an explicit comparator/plan.
[ ] XI, bench, captain, vice and chip are included.
[ ] Blocked/degraded/stale cannot look normal.
[ ] Mobile checklist is complete.

B. VALUE AND UNCERTAINTY
[ ] Horizon and objective are explicit.
[ ] Expected gain uses a comparator.
[ ] Paired p10/median/p90 and probability gain are shown.
[ ] Downside/upside are defined, not vague.
[ ] Confidence is separate and decomposed.
[ ] Monte Carlo/solver uncertainty is visible.

C. EXPLANATIONS
[ ] Reasons come from the explanation graph.
[ ] Why-changed uses controlled re-runs.
[ ] Change attribution reconciles.
[ ] Switch conditions are actual reoptimisations.
[ ] Model counterfactuals are not described as causal.
[ ] Natural-language rendering cannot invent numbers/reasons.
[ ] Knowledge limits are displayed.

D. DECISION CONTENT
[ ] Important assumptions are impact-ranked.
[ ] Future information has time, EVSI and action branches.
[ ] Price implications are route-specific.
[ ] Alternatives are common-scenario comparisons.
[ ] Chip value includes opportunity cost.
[ ] Final rank distribution appears only with confidence/context.

E. ACCESSIBILITY/RIGHTS
[ ] WCAG 2.2 AA is the target.
[ ] No colour-only status.
[ ] Every chart has table/text alternative.
[ ] Keyboard/screen reader/reduced motion pass.
[ ] Private and licence-restricted data are protected.
[ ] Exports obey provider Rights Profiles.

F. EVALUATION
[ ] User can correctly answer the ten decision questions.
[ ] Appropriate reliance is measured.
[ ] Visuals are evaluated by decision quality.
[ ] UI telemetry is privacy-minimised.
[ ] Old recommendations remain immutable.
[ ] Points/rank modes never alter raw projections.
