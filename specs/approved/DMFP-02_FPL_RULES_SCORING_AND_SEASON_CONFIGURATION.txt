PURPOSE
-------
This document defines how every Fantasy Premier League rule is represented,
validated, versioned and executed inside DMF Pulse.

The governing principle is:

    FPL RULES ARE VERSIONED DATA, NOT MODEL CODE.

The modelling, simulation and optimisation layers must never depend on scattered
numeric constants, hard-coded chip assumptions, hidden formation rules or
season-specific if-statements.

A change in:

- goal points;
- an assist definition;
- a defensive-contribution threshold;
- the Bonus Points System;
- squad composition;
- free-transfer accumulation;
- selling-price treatment;
- chip inventory;
- a chip validity window;
- a Gameweek deadline;
- a one-off transfer grant;

must be implemented by changing and approving configuration, not by rewriting
the engine.

IMPORTANT PRE-LAUNCH STATUS NOTE
--------------------------------
As of 16 July 2026, the official Fantasy Premier League game for 2026/27 had not
yet launched. The Premier League stated that it would launch later in the
summer. The Premier League season itself is scheduled to begin on Friday
21 August 2026.

Consequently:

1. No 2025/26 rule is authoritative for 2026/27.
2. Every 2025/26 value in this document is REFERENCE_ONLY.
3. The 2026/27 production ruleset MUST remain:
       production_eligible: false
   until official target-season rules have been captured, compared, tested and
   human-approved.
4. The first 2026/27 FPL deadline MUST be read from official target-season game
   data or an official target-season rules source. It MUST NOT be inferred from
   the prior season's 90-minute convention.
5. The engine MUST refuse to issue a production recommendation if any required
   target-season rule is UNKNOWN, UNCONFIRMED, CONFLICTED or STALE.
6. The target-season source bundle, compiled ruleset and approval record MUST be
   immutable and hash-addressed.
7. Any later official correction or mid-season special rule MUST create a new
   effective-dated ruleset version or scheduled rule event.

0. EXECUTIVE CONTROL SUMMARY
======================================================================

0.1 THE RULES ENGINE IN ONE SENTENCE
------------------------------------
The DMF Pulse rules engine is a deterministic, pure, versioned state-transition
and scoring system that converts official football/FPL events and manager
actions into legal squads, transfer costs, chip states and FPL points under one
explicit season configuration.

0.2 CONTROLLING ARCHITECTURAL DECISIONS
---------------------------------------
RD-02-01. Rules are external configuration.
No production rule value may exist only as a literal inside scoring,
optimisation, simulation or user-interface code.

RD-02-02. Target-season official sources control.
Official 2026/27 FPL rules, official target-season game data and explicit
official clarifications take precedence over prior-season articles, community
interpretations and model memory.

RD-02-03. The active ruleset is an approved artefact.
The application must not scrape a help page at runtime and silently alter
behaviour. Official sources are captured into a reviewed ruleset that is
validated, compiled, hashed and activated.

RD-02-04. Human-readable YAML, canonical JSON.
Rules are authored and reviewed in YAML 1.2.2-compatible files, then converted
to canonical JSON, validated with JSON Schema Draft 2020-12, hashed and loaded
by the engine.

RD-02-05. Rule values and rule eligibility are separate.
Example:
- an assist is worth three points;
- whether a touch qualifies as an assist is a separate policy.
A season can change either without changing the other.

RD-02-06. Scoring is fixture-scoped before Gameweek aggregation.
Appearance, clean sheets, goals conceded, defensive contributions, BPS and
bonus are calculated per fixture. A player's Gameweek total aggregates all
fixtures assigned to that Gameweek.

RD-02-07. Manager effects are applied after player scoring.
Automatic substitutions, captaincy and chips act at the manager/Gameweek layer,
not inside the player-event scoring layer.

RD-02-08. Bonus is match-relative.
BPS must be calculated for all relevant players in one match before bonus points
can be allocated. Bonus cannot be forecast or recreated as an independent fixed
player add-on.

RD-02-09. Money uses integer price units.
Store prices as integer tenths of a million pounds:
    £5.0m -> 50
    £14.5m -> 145
Never use binary floating-point for affordability or selling-price rules.

RD-02-10. Time uses explicit UTC timestamps.
Deadlines, effective dates and source captures use RFC 3339-compatible UTC
timestamps. Display conversion is separate.

RD-02-11. State transitions are explicit.
Free transfers, hits, chips, squad reversion, special transfer grants and
deadline closure are state-machine transitions, not ad hoc calculations.

RD-02-12. Special seasonal events are declarative.
A one-off event such as the 2025/26 AFCON transfer top-up belongs in
special_events.yaml, not an if statement such as:
    if season == 2025 and gameweek == 16.

RD-02-13. Undisclosed mechanisms remain outside deterministic rules.
FPL does not publish the exact player price-change threshold algorithm. The
rules engine can represent official price and selling-price mechanics; the
probabilistic prediction of future changes belongs to DMFP-11.

RD-02-14. Official outcomes remain the reconciliation authority.
Pulse should model FPL points itself for projection and validation, but after
official points are final it should reconcile to official FPL outcomes. It must
not insist that its own reconstruction overrides official assist or bonus
decisions.

RD-02-15. Fail closed on ambiguity.
A conflicting or unknown BLOCKING rule prevents activation. The engine does not
guess.

1.3 CRITICAL BOUNDARY: RULES VERSUS MODELS
------------------------------------------
RULE:
A defender receives N points for an eligible goal under a particular ruleset.

MODEL:
The probability that a defender scores.

RULE:
A player qualifies for clean-sheet points after a configured appearance
threshold.

MODEL:
The probability that the player reaches that threshold and the team keeps a
clean sheet.

RULE:
A free transfer costs zero points and extra transfers cost a configured amount.

MODEL:
Whether taking a hit has positive expected value.

RULE:
The captain multiplier is configured.

MODEL:
Which player should be captain.

RULE:
A player purchased at one price has a deterministic selling price given current
price.

MODEL:
The probability that current price changes tonight.

This boundary MUST be enforced in package dependencies.

1.4 CRITICAL BOUNDARY: PROJECTION VERSUS OFFICIAL RECONCILIATION
----------------------------------------------------------------
For projections:
- Pulse needs an explicit assist classifier;
- Pulse needs a BPS simulator;
- Pulse needs a defensive-contribution event model.

For official historical outcomes:
- Pulse should ingest the official FPL result;
- compare its reconstruction;
- explain differences;
- preserve the official value as the outcome label unless an official correction
  later changes it.

The engine therefore has two modes:

PROJECTION_MODE
Uses simulated events and configured policies.

RECONCILIATION_MODE
Uses official event/point feeds and reports deviations from Pulse's independent
calculation.

2. RULE AUTHORITY, PROVENANCE AND CONFLICT RESOLUTION
======================================================================

2.1 CLAIM CRITICALITY
---------------------
Every item in this document is BLOCKING or CORE under DMFP-01.

BLOCKING examples:
- goal point weights;
- squad budget;
- formation minimums;
- transfer hit cost;
- captain multiplier;
- chip count;
- deadline;
- selling-price formula.

CORE examples:
- BPS reconstruction;
- detailed assist policy;
- points-finality window;
- treatment of rare edge cases.

2.2 TARGET-SEASON SOURCE ORDER
------------------------------
For a target-season rule:

1. Official FPL rules/help for 2026/27.
2. Official 2026/27 FPL game-update page.
3. Official Premier League/FPL explanatory article.
4. Observable official game behaviour or official API data.
5. Explicit official support clarification.
6. Prior-season official rule, labelled historical only.
7. Reproducible practitioner observation.
8. Community interpretation.

An official explanatory article is useful, but the actual target-season rules
and observable game behaviour must be checked where wording is incomplete.

2.3 SOURCE LOCATOR PER RULE
---------------------------
Every configured rule must link to:

- source_id;
- canonical URL or internal artefact;
- publication/update date;
- date accessed;
- exact section, line, JSON path or screenshot reference;
- verification status;
- verifier;
- next-review trigger.

2.4 CONFLICT TYPES
------------------
TEXT_VS_TEXT:
Two official pages state different rules.

TEXT_VS_GAME:
Official prose conflicts with observed application behaviour.

ARTICLE_VS_RULES:
An explanatory article simplifies or conflicts with formal rules.

PRIOR_VS_TARGET:
The prior season differs from target season.

CONFIG_VS_SOURCE:
Compiled value differs from approved source.

API_VS_UI:
Official API data differs from visible game output.

2.5 CONFLICT PROCEDURE
----------------------
1. Freeze production activation.
2. Record a CONFLICTED claim.
3. Capture both sources and timestamps.
4. Determine whether one is stale or from another season.
5. Construct a minimal official-game test where possible.
6. Seek official clarification if material.
7. Record the selected interpretation and residual risk.
8. Add a golden regression test.
9. Approve a new ruleset version.
10. Preserve the conflict history.

2.6 NO SILENT CORRECTION
------------------------
If an official rule is later corrected, the old config is not edited in place.

Create:
- new source record;
- new claim version;
- new ruleset version;
- effective time;
- migration/recalculation policy;
- supersession link.

3.4 YAML SAFETY RULES

To avoid parser ambiguity:

- quote season codes: "2026/27";

4. RULESET STATUS, VERSIONING AND ACTIVATION
======================================================================

4.1 RULESET STATUS
------------------
DRAFT_PRELAUNCH:
Target-season file exists but official game is not launched.

REFERENCE_ONLY:
Historical ruleset used for testing, not production decisions.

CAPTURED_UNVERIFIED:
Official sources captured but not fully reviewed.

CONFLICTED:
One or more material rules disagree.

VERIFIED:
All required rules checked and tests pass.

ACTIVE:
Verified and approved for production use.

SUPERSEDED:
Replaced by a later effective ruleset.

REVOKED:
Known unsafe or incorrect; must not be used.

4.2 SEMANTIC VERSIONING
-----------------------
Use Semantic Versioning 2.0.0 for the ruleset interface:

MAJOR:
A change that can alter public rules-engine semantics or require downstream
adaptation.

Examples:
- new scoring event;
- changed chip state model;
- changed position set;
- changed transfer transition contract.

MINOR:
Backward-compatible addition.

Examples:
- newly confirmed optional metadata;
- additional special event;
- additional nonrequired diagnostic.

PATCH:
Backward-compatible correction that does not alter intended official semantics,
or provenance/test improvement.

Because a correction can materially change decisions, every release also records:
- effective date;
- source change;
- affected Gameweeks;
- whether historical recomputation is required.

4.3 PRE-RELEASE EXAMPLE
-----------------------
ruleset_id: "fpl-2026-27"
ruleset_version: "0.1.0-prelaunch.1"
season_code: "2026/27"
status: "DRAFT_PRELAUNCH"
production_eligible: false

4.4 ACTIVATION GATE
-------------------
The activation command should resemble:

    dmf rules activate fpl-2026-27 --version 1.0.0

It must verify:
- schema validity;
- zero unknown required fields;
- source manifest completeness;
- source freshness;
- human approval;
- golden tests;
- differential test;
- compiled hash;
- no newer conflicting official source.

4.5 IMMUTABILITY
----------------
An ACTIVE ruleset is immutable.

A change creates a new version. Database records and decision bundles store the
exact ruleset ID and hash.

4.6 ROLLBACK
------------
A new ruleset release must identify:
- prior version;
- rollback command;
- incompatibilities;
- historical data migration;
- affected recommendations;
- reprocessing plan.

---------

integer

Unit:
tenths of £1m

nonnegative integer.

If an in-season reclassification ever occurs, it requires an effective-dated
official rule/event and explicit migration.

7. APPEARANCE POINTS
======================================================================

7.1 REFERENCE 2025/26 VALUES
----------------------------
REFERENCE_ONLY official 2025/26 explanation:

- appearance below the full threshold: 1 point;
- appearance at or above 60 official minutes, excluding stoppage time:
  2 points total.

The target-season configuration must define exact threshold semantics.

7.2 PROPOSED CONFIG SHAPE
-------------------------
appearance:
  eligibility:
    min_minutes_for_any_appearance_points: 1
    minute_source: "OFFICIAL_FPL"
    stoppage_time_included: false

  bands:
    - band_id: "APPEARANCE_SHORT"
      min_minutes_inclusive: 1
      max_minutes_exclusive: 60
      points: 1

    - band_id: "APPEARANCE_LONG"
      min_minutes_inclusive: 60
      max_minutes_exclusive: null
      points: 2

  combination: "HIGHEST_MATCHING_BAND_ONLY"

7.3 EDGE CASES
--------------
- 0 minutes: no appearance points.
- 1 minute: short-appearance band if target rule confirms.
- exactly 60: long band if target rule confirms.
- official minutes, not wall-clock elapsed seconds.
- multiple fixtures: score each fixture independently.
- abandoned/replayed match: official FPL treatment controls.
- added time: excluded from threshold if official target rule confirms.
- goalkeeper substituted: appearance scored normally.
- player sent off: appearance remains based on official minutes.

7.4 TESTS
---------
- minutes 0 -> 0;
- minutes 1 -> 1 reference point;
- minutes 59 -> 1;
- minutes 60 -> 2;
- minutes 90 -> 2;
- no double counting of both bands;
- two fixtures at 30 and 60 -> 1 + 2 before manager multipliers.

8.3 RULES ENGINE BEHAVIOUR
--------------------------
For each official/simulated eligible goal:
    goal_points += goals * position_weight

Penalty status affects BPS in the 2025/26 reference system, not ordinary FPL goal
points.

8.4 EDGE CASES
--------------
- own goal is not an eligible scored goal and instead receives the configured
  own-goal deduction;
- shootout goals are not Premier League match goals;
- voided/abandoned match follows official FPL outcome;
- position is FPL classification, not tactical role;
- a player transferred between clubs retains target-season FPL position unless
  officially changed;
- captain/chip multipliers apply to total player points later.

Penalty goal ordinary FPL points equal position goal points if target rule
confirms.

9. ASSIST SCORING AND ASSIST ELIGIBILITY
======================================================================

9.1 NUMERIC VALUE
-----------------
REFERENCE_ONLY 2025/26:
An eligible assist is worth 3 FPL points for every position.

9.2 WHY ASSISTS REQUIRE A POLICY FILE
-------------------------------------
The points value is simple. Eligibility is not.

Assist allocation can depend on:
- final attacking touch;
- defensive touches;
- location where scorer receives the ball;
- intended target/destination;
- rebound;
- woodwork;
- own goal;
- penalty/free-kick won;
- whether the taker won the foul;
- possession lost and regained;
- attempted defensive pass;
- handball;
- multiple interventions.

The eligibility logic must not be compressed into one hard-coded boolean.

9.3 REFERENCE 2025/26 POLICY SUMMARY
------------------------------------
REFERENCE_ONLY, paraphrased from official 2025/26 guidance:

- The player from the scoring team making the final qualifying pass/touch may
  receive the assist.
- A rebound after a shot is blocked, saved or strikes the woodwork may create an
  assist.
- A player whose shot/pass forces an own goal may receive an assist.
- A player winning a penalty or free kick may receive an assist if it is scored
  directly.
- The taker receives no assist merely for having won the same penalty/free kick.
- If the scorer receives the ball inside the penalty area and there is only one
  defensive touch, the intended target generally does not control.
- If the scorer receives the ball outside the area, intended destination remains
  relevant.
- Two or more defensive touches prevent the assist under the cited 2025/26
  policy.
- Losing and regaining possession prevents an assist.
- Detailed defensive-error and handball cases require exact target-season
  verification.

9.5 IMPLEMENTATION STRATEGY
---------------------------
Projection mode SHOULD not attempt a perfect legalistic event classifier from
minimal aggregate data.

Use one of:
- official/provider event labels;
- a probabilistic assist allocation model;
- scenario event types that map cleanly to configured rules.

Reconciliation mode:
- ingest official assist outcome;
- compare independent classification only when event detail is available.

9.6 DISCRETION AND SUBJECTIVITY
-------------------------------
If official allocation retains judgement:
- configuration must record the policy;
- model uncertainty must remain;
- official final allocation controls historical label;
- differences become reconciliation observations, not engine corruption.

9.7 TEST CATALOGUE

Each target-season expected result needs an official source or verified official
game example.

Do not confuse them.

13.2 REFERENCE 2025/26 BPS TABLE

REFERENCE_ONLY official system updated 1 April 2026:

- playing 1–60 minutes: 3;

- non-penalty goal by MID: 18;
- non-penalty goal by FWD: 24;
- assist: 9;
- GK/DEF clean sheet: 12;
- penalty save: 8;
- save from shot inside box: 3;
- save from shot outside box: 2;
- successful open-play cross: 1;
- big chance created: 3;
- every 2 clearances/blocks/interceptions combined: 1;
- every 3 recoveries: 1;
- key pass: 1;
- successful tackle: 2;
- successful dribble: 1;
- match-winning goal: 3;
- goalline clearance: 9;
- foul won: 1;

- offside: -1;

13.3 MUTUAL EXCLUSIVITY
-----------------------
Penalty goal BPS is a special direct-penalty value in the reference table.

Implementation must not:

Appearance BPS bands are mutually exclusive.

13.5 BONUS ALLOCATION
---------------------
REFERENCE_ONLY:
- highest BPS rank receives 3;
- second receives 2;
- third receives 1.

Tie rules:
- tie for first: all tied first receive 3; the next distinct rank receives
  the remaining appropriate allocation according to official rule;
- official examples show two tied first receive 3 each and the next player gets
  1;
- tie for second: first gets 3, tied second players get 2;
- tie for third: first gets 3, second gets 2, all tied third get 1.

More than three players may receive bonus.

13.6 GENERIC TIE ALGORITHM
--------------------------
Do not implement only three example-specific if-statements.

Represent the rank award slots:
[3, 2, 1]

Group players by distinct BPS descending and use the target-season tie policy.

For the 2025/26 reference policy, golden cases must include:
- no tie;
- two-way tie first;
- three-way tie first;
- two-way tie second;
- multiway tie third;
- two tied first plus three tied next;
- all players tied;
- negative BPS;
- zero BPS.

If official rules are unclear for unusual tie structures, compare against
official historical matches and record the verified algorithm.

13.7 BPS INPUT COMPLETENESS
---------------------------
Bonus cannot be correctly reconstructed from goals/assists alone.

The provider must supply or Pulse must model:
- all configured positive and negative BPS actions;
- pass attempts/completions;
- shot locations;
- errors;
- tackles;
- recoveries;
- match-winning goal;
- player minutes;
- goals conceded.

Projection uncertainty must reflect missing BPS events.

13.8 TESTS
----------
One unit test per BPS event.
Mutual-exclusivity tests.
Grouped-event floor tests.
Pass-band boundaries.
Clean-sheet threshold.
Tie-allocation golden cases.
Comparison with official fixture BPS/bonus records.

18. PRICES AND SELLING-PRICE RULES
======================================================================

18.1 THREE PRICE CONCEPTS
-------------------------
PURCHASE_PRICE:
Price paid when current ownership spell began.

CURRENT_PRICE:
Price another manager pays now.

SELLING_PRICE:
Cash received if sold now.

These must be stored separately.

18.2 REFERENCE 2025/26 SELLING RULE
-----------------------------------
REFERENCE_ONLY official examples:

- if current price is below purchase price, the full fall is borne;
- if current price is above purchase price, the manager receives £0.1m profit
  for every complete £0.2m rise.

Integer formula in price units:

if current_price <= purchase_price:
    selling_price = current_price
else:
    selling_price =
        purchase_price
        + floor((current_price - purchase_price) / 2)

Examples:
- purchase 50, current 54 -> sell 52;
- purchase 50, current 53 -> sell 51;
- purchase 50, current 47 -> sell 47.

18.3 CONFIG SHAPE
-----------------
prices:
  unit: "0.1m_GBP"

  selling:
    when_current_lte_purchase: "CURRENT_PRICE"
    profit_increment_current_units: 2
    profit_increment_selling_units: 1
    rounding: "FLOOR"

  ownership_spell:
    repurchase_resets_purchase_price: true

18.4 REBUY
----------
If a player is sold and later repurchased, purchase price resets to the new
purchase price. Historical ownership spells remain separate.

18.5 PRICE-CHANGE MECHANISM BOUNDARY
------------------------------------
Official guidance states that prices respond to transfer-market popularity and
can change during the season, but the exact threshold mechanism is not publicly
revealed.

Therefore:

DMFP-02 owns:
- current official price;
- purchase price;
- selling formula;
- official change events;
- official limits if confirmed.

DMFP-11 owns:
- probability of change;
- inferred thresholds;
- timing model;
- transfer-volume features.

No deterministic hidden threshold appears in target rules config.

18.6 BANK
---------
Bank is integer price units.

Transfer affordability:
    new_bank =
        old_bank
        + sum(outgoing selling prices)
        - sum(incoming current prices)

Must be >= 0.

18.7 TESTS
----------
- no gain;
- one-unit rise gives no sell profit;
- two-unit rise gives one;
- three gives one;
- four gives two;
- falls passed fully;
- sell and repurchase resets purchase price;
- multi-transfer affordability exact;
- no float rounding.

20.5 BLANK GAMEWEEK
-------------------
A club has zero fixtures assigned to the Gameweek.

No special scoring rule is required; player fixture aggregation yields zero

25. ORDER OF CALCULATION
======================================================================

25.1 FIXTURE PLAYER SCORING
---------------------------
1. Validate player position and fixture.
2. Determine official/simulated minutes.
3. Score appearance.
4. Score goals.
5. Score assists.
6. Score clean sheet.
7. Score saves and penalties.
8. Score defensive contributions.
9. Score negative FPL events.
10. Calculate BPS.
11. Store provisional fixture subtotal excluding bonus.
12. Allocate match bonus across all players.
13. Add bonus.
14. Return fixture breakdown.

25.2 GAMEWEEK PLAYER AGGREGATION
--------------------------------
1. Retrieve all fixtures officially assigned to Gameweek.
2. Sum fixture breakdowns.
3. Determine any appearance.
4. Preserve per-fixture components.
5. Mark provisional/final.

25.3 MANAGER SCORING
--------------------
1. Freeze submitted squad/lineup at deadline.
2. Resolve player Gameweek totals.
3. Resolve automatic substitutions.
4. Resolve captain/vice.
5. Apply captain multiplier or Triple Captain.
6. Include bench only if Bench Boost.
7. Subtract transfer deductions.
8. Return manager total and audit trail.

25.4 WHY ORDER MATTERS
----------------------
Examples:
- bonus requires all player BPS;
- clean sheets require player interval;
- captaincy depends on any appearance;
- auto subs depend on Gameweek appearances;
- Triple Captain modifies effective captain;
- transfer hit is a manager deduction, not player scoring.

28. FAIL-CLOSED AND FALLBACK POLICY
======================================================================

28.1 BLOCKING CONDITIONS
------------------------
- target game not launched;
- ruleset not ACTIVE;
- unknown required rule;
- source conflict;
- deadline missing/stale;
- position mapping missing;
- chip state unknown;
- invalid manager state;
- compiled hash mismatch;
- schema validation failure.

28.2 DEGRADED CONDITIONS
------------------------
- independent BPS reconstruction incomplete;
- detailed assist simulation incomplete;
- official point finality pending;
- noncritical explanatory metadata missing.

The engine may project under a DEGRADED state only if:
- the limitation is visible;
- a safe fallback exists;
- manager legality remains exact;
- no BLOCKING rule is affected.

28.3 FALLBACK
-------------
Examples:
- use official player total outcomes for reconciliation when event details are
  missing;
- exclude bonus projection or use a clearly probabilistic module, never invent
  exact bonus;
- use official selling price from authenticated state if independent formula
  reconciliation is uncertain;
- defer chip recommendation if chip rules conflict.

28.4 NEVER FALL BACK TO LAST SEASON SILENTLY
--------------------------------------------
A missing 2026/27 value cannot silently inherit 2025/26.

inherits_from: "fpl-2025-26"

[ ] No 2025/26 rule is treated as authoritative for 2026/27.

[ ] Squad/formation constraints are central.
[ ] Free transfers use a state machine.

[ ] External club-quota violation is valid-but-restricted.

E. Chips
[ ] Chips are inventory/window/state-transition objects.
[ ] No chip assumptions carry to 2026/27 without verification.
[ ] Special events are declarative.

F. Operations
[ ] ACTIVE rulesets are immutable.
[ ] Every decision stores ruleset version/hash.
[ ] Unknown blocking rules fail closed.
[ ] Official outcomes remain reconciliation authority.

G. Implementation
[ ] Codex will not hard-code rule literals.
[ ] Every active rule has tests and source provenance.
[ ] Launch diff and dry runs are mandatory.
